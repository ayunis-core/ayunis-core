# Route Modules

Page components composing widgets and features for each application route.

The chat page supplies its registered cards, Markdown actions and artifact-opening callback to the shared timeline in `@ayunis/chat/timeline`.

Route-level page modules handle authentication, chat conversations, agent management, prompt libraries, knowledge base management, skill management, user settings, organization admin settings, and super-admin platform management. Each page follows a consistent internal structure with api/, ui/, and model/ subdirectories separating data hooks, components, and types.

Chat file uploads and removals invalidate the subscribed thread query only. Upload mutations await the thread refresh so sending stays blocked until the chat sees the uploaded source and its processing status. A chat started with files opens while they are still processing: `usePendingMessage` shows the deferred first message as pending and sends it once `useChatThread` reports no processing source (ready or failed), with no time limit; Stop returns it to the input. Post-run refetches replace stale requests in one operation, keeping upload callers waiting through the replacement. They do not reload route loaders, whose pending thread fetches can otherwise be cancelled by concurrent uploads.

Existing chats match their bound model to the current effective grant by catalog model id, so switching defaults or moving between equivalent organization and team grants does not incorrectly hide the composer.

The chat overview page places its search control in the content header. Its chat rows, like the open chat's actions menu, offer moving the chat to a workspace, so chats beyond the sidebar's recent list can be assigned without pinning them first. The project overview keeps only the add-project action there without repeating a content title. Project rows expose pinning with an explanatory tooltip.

The web new-chat heading uses the time of day from `greetings-data.ts` through `useTimeBasedGreeting`.

Above the new-chat composer, `OnboardingHint` shows the hint for the user's onboarding stage (`GET /onboarding/stage`, fetched by the route loader on every visit; no hint while the latest fetch failed, so a completed stage is never offered from the cache); it is animated unless the system asks for reduced motion and cannot be dismissed. Clicking it starts a chat with the `onboarding` origin and the stage's fixed opening message: a profile chat always runs non-anonymously on the model the stage names, a first-skill chat on the composer's model and anonymous setting (`lib/onboarding-chat.ts`); no workspace, files, knowledge bases or integrations are attached. The new-chat page combines personal/shared and selected-workspace pinned skills into the same selectable quick-action buttons. Under the composer, `UnreadNotificationsPanel` shows one tab per notification type with unread notifications (failed runs first, each with its count from `useUnreadNotificationCount`). It starts collapsed; a tab opens the type's newest 20 unread notifications (`useUnreadNotifications`, `GET /notifications?unread=true`), each opening its notification, plus a link to the inbox filtered to that type, and the same tab, Escape or a click outside closes it. The open list overlays the content below instead of moving the composer, and `useViewportMaxHeight` caps its scroll height to the viewport. Workspace changes clear only a selected skill belonging to a different workspace; regular skill selections remain available.

The workspace page also includes the Erstellte Inhalte tab for project artifacts; tabs follow the sidebar-oriented order Chats, Erstellte Inhalte, Fähigkeiten, Wissen, Aufzeichnungen (only while `recordingsEnabled` is on), Anweisungen. Artifact rows open the corresponding chat editor through URL search parameters, while artifact lists load within the workspace tabs.

The `workspace/` page slice also includes context tabs for Wissen, Skills and Anweisungen. Skills and knowledge bases are created as workspace-owned resources and open workspace-scoped detail routes after creation. Those detail pages reuse the personal skill and knowledge-base creation dialogs, property cards, assignment card, document card, and header controls while keeping workspace-scoped routes. Both personal and workspace flows use the canonical owner-aware `/skills` and `/knowledge-bases` APIs; persisted detail ownership determines access, while create and list requests carry the explicit owner scope. They assign same-workspace knowledge bases to skills, manage additional documents through canonical skill source endpoints, and manage documents inside workspace knowledge bases, while standalone project files do not exist. Project skill and knowledge-base rows reuse their personal-resource presentations, expose workspace-wide activation controls (plus project pinning for skills), and place creation as the tab's top-right action; `api/useWorkspaceContextActions.ts` sends canonical skill mutations and owns workspace cache invalidation; `useWorkspaceSkills.ts` wraps the paginated workspace skill scope. `GET /workspaces/:id/context` remains the runtime-context source for selected-workspace pinned skills. Workspace controls follow the caller's workspace `role` and `permissions` from the workspace response (`getWorkspaceAccess`): editing details, instructions, skills, knowledge, activation and pins need `manage_workspace` (otherwise tabs and detail pages are read-only), adding members needs `manage_workspace_members`, and deleting and changing roles are for workspace admins. The header's labelled members button links to the members page (`/workspaces/:workspaceId/members`, `WorkspaceMembersPage`), modelled on the team detail page: a members card with a count badge lists every member with role and joined date; holders of `manage_workspace_members` get "Add members" in the page header, opening `AddWorkspaceMembersDialog` (searches colleagues who are not members yet through `GET /workspaces/:id/member-candidates`, since the org user list needs `assign_users_to_teams`, plus a role, `admin` only offered to admins), and admins get the shared `MemberRoleSelect` per member, confirmed before saving, with its "what this role may do" card fed by `GET /workspaces/:id/role-permissions`. Each other member's row has a remove action with a confirmation (`useRemoveWorkspaceMember`), shown for non-admins to holders of `manage_workspace_members` and for admins only to workspace admins (`canRemoveWorkspaceMember`); every member gets "Leave workspace" in the page header (`useLeaveWorkspace`), which drops the workspace, its chats and its favourite from the cached lists and returns to the workspaces list. The last admin's 409 shows as an error toast. Non-members are redirected to the workspaces list, like on the workspace page. Membership changes refresh the member list, the candidates and the workspace, since changing one's own role changes the controls.

The `super-admin-settings/users/` page provides a searchable cross-organization user directory with account lock status, account recovery, password reset, organization navigation, deletion, and CSV export controls. Organization admins see the same lock status and recovery action in their user settings.

Municipal SSO uses separate auth route slices for direct organization links, successful completion, and actionable failures. Every broker callback lands on one of these fixed application routes. SSO connections are managed by Superadmins rather than organization admins from Account Settings.

Account settings reads authenticated SSO link status and offers Connect SSO only when the backend permits it; linked and JIT users see SSO connected. The account-link-required error sends users through local login back to account settings. Broker return query parameters never establish connected state: the card always reads persisted status.

The Superadmin organization SSO tab configures one or more verified email domains for the same broker mapping, reviews the complete set before activation, and controls whether an active organization requires SSO. Enforcing SSO requires an explicit confirmation against the current mapping. For SSO-only organizations, login and invitation acceptance present the organization SSO action without password or password-reset controls.

The Super Admin sidebar keeps incident tooling in a separate Operations group; Queue inspection opens the protected Bull Board route in a new tab.

The `auth/` group contains the login, register, email confirmation, password forgot/reset, and invite acceptance flows. Generated images in chat and in the enlarged dialog sit on a light checkerboard so a transparent background stays visible in dark mode. The `chat/` and `new-chat/` pages manage AI conversation interfaces with message streaming, agent selection, knowledge base attachment (`useKnowledgeBaseAttachment` hook for adding/removing KBs on existing threads, plus pending-KB context state for new threads), an opening timeline hint that summarizes active AI context and opens the context panel, and a resizable tabbed side panel for created-content browsing/editing and lazy thread AI-context inspection (skills and knowledge bases), including guarded dirty-editor transitions and artifact letterhead changes. Streamed message snapshots are applied at most once per animation frame (latest per message; other run events and the end of the run flush pending snapshots first), and `useRenderUnits` reuses unchanged run units so memoized run blocks only re-render the streaming run. The chat run timeline shows a tool as soon as the model names it, before its input is complete; cancelling a run drops an unsaved assistant message that only named tools still being prepared. The timeline displays accumulated raw tool input while it streams, renders malformed terminal calls as non-actionable errors, retains those presentation-only errors across same-thread refetches without treating them as persisted history, formats namespaced MCP capabilities with their readable upstream names, and presents successful document reads as editor cards so older generated documents remain accessible inline. Its page-local `GeoJsonMapWidget` uses MapLibre to render point, line, polygon, and multi-geometries, fit their bounds, expose properties as plain-text popups, and show basemap plus distinct data attribution without duplication; runtime frontend configuration can override the basemap tiles and attribution. The page-local `InstallMarketplaceSkillWidget` renders the assistant's `install_marketplace_skill` call as a confirmation card: it shows only the catalogue entry fetched for the model's identifier (`useMarketplaceSkillEntry`), links to the existing skill when the user already installed that entry (`useInstalledMarketplaceSkill` over `GET /skills/marketplace/:identifier`), installs through `useInstallMarketplaceSkillFromChat` for users with `manage_skills`, and shows an administrator hint to everyone else. The page-local `CreateRoutineWidget` and `EditRoutineWidget` render the assistant's `create_routine` and `edit_routine` calls with the shared `RoutineFormFieldset` (configuration fields only; integrations and knowledge bases are set on the routine page): the create widget starts on the user's default model and saves through `useCreateRoutine` with its tool call ID (`sourceToolCallId`); it looks the proposal up in the routine list (`useRoutineFromProposal` over `GET /routines`), keeps saving disabled until the lookup has answered or while the call has no ID, and once the proposal was saved shows the saved routine locked as created, so a reloaded chat cannot create it again; the edit widget loads the routine (`useRoutineToEdit`) and restarts its form from it once loaded, fills the fields the model left empty or out (`internet_access`, `allowed_domains`) and the model from the stored routine (`lib/routine-widget-fields.ts`), saves through `useUpdateRoutine` and says so when the routine is gone. The page-local `AddAnonymizationExceptionWidget` renders an admin's `add_anonymization_exception` call as a confirmation card, only when the backend accepted it (`isExceptionAccepted`): it resolves the call's placeholders with the thread's masks (`lib/anonymization-exception.ts`), shows the real word, its category, the category's current rule and the rule with the word appended as an escaped literal (`useOrgPiiWhitelist`), and states that it applies to the whole organization. Saving (`useSaveAnonymizationException`, one save at a time per tab through a shared mutation scope) re-reads the whitelist and, unless the category's rule changed since the card showed it (then it saves nothing and the card reloads the rule), appends the exception to its category and sends the whole list to `PUT /anonymization-settings/pii-whitelist`; once the rule matches the word the card shows it as no longer masked instead of offering to save again. The page-local `SendNotificationWidget` renders a routine run's `send_notification` call as its own card outside the collapsed steps, while it streams and once the backend sent the notification (`lib/sent-notification.ts`; a rejected call gets no card): the headline, subheadline and about the first ten lines of the body, and a link to the notification in the inbox when the result carries its ID (older results do not, so their card has no link). The `chats/` page lists conversation threads. The `agents/` and `agent/` pages handle AI assistant browsing and detailed configuration. The `prompts/` page provides prompt library management. The `knowledge-bases/` page lists knowledge bases with creation, deletion, and active toggles (per user for personal and shared ones, for everyone with access for team and org ones, switchable only by their managers), while `knowledge-base/` provides the detail view for a single knowledge base including the same active control, document upload, removal, and property editing. New knowledge bases start active, and active owned or shared knowledge bases are automatically available to chat knowledge tools. The `skills/` page lists available skills, and `skill/` shows skill details. Academy learning spans three page slices: `academy/` lists chapters, `academy-chapter/` shows embedded Loom videos, and `academy-chapter-confirmation/` requires the learner to confirm they watched the videos before completing the chapter. Whole-academy completion offers the KI-Schulung nach EU AI Act participation-confirmation PDF through `useDownloadParticipationConfirmation`. The `install/` page handles app installation flows: `/install?skill=`, `/install?integration=` (admins) and `/install?routine=`, whose `InstallRoutinePage` previews the marketplace routine (name, short description, schedule, internet mode with the allowed domains in `allowlist` mode; no editable fields) and installs it through `POST /routines/install-from-marketplace`, then opens `/routines/$routineId`. It shows its own error states for routines being disabled, a missing `manage_routines` or `install_marketplace_routines`, an unknown entry and an unreachable marketplace (a 503 preview is first retried like a deploy gap). User `settings/` includes account, general preferences, `chat-settings/` for per-user AI conversation configuration (custom system prompts), per-user MCP credentials, and the user's always-allowed MCP tools on `integrations-settings/` (grouped by integration, each removable). While `memoryEnabled` is on, `memory-settings/` (`/settings/memory`; its sidebar entry shows only when at least one of the user's models has memory access, but the route stays reachable so stored entries can always be seen and deleted) lists what the assistant remembers about the user, reserved keys `personal` and `preferences` first, and lets the user edit an entry's content and, for other keys, its description, clear an entry (an emptied entry is deleted) or delete all memory; with the toggle off the entry is hidden and the route redirects to the general settings. The `admin-settings/` group covers organization administration: model configuration, API-key management with per-key monthly credit usage and limits, MCP integrations (including a custom-server field builder for organization and user HTTP headers) with, while `connectorsEnabled` is on, the organization's connections at the top of the same page (`ConnectionsSection`: each connector, Microsoft 365, with whether it is set up, linking to its page; `microsoft-365-connector/` (`/admin-settings/integrations/microsoft-365`) sets up, changes and removes the connection to the organization's own Entra app (tenant ID, client ID, client secret; the stored secret is never shown, and leaving the field empty keeps it; a GUID entered as the secret is flagged as the secret's ID), and shows the connection test returned on save, which the admin can run again (only the latest save, test or removal sets the shown result, so a slow, older test never replaces it): its outcome with a setup hint and Entra's error code, and the Microsoft Graph permissions Ayunis uses with whether each is granted; with the toggle off, it redirects to the integrations) and, while `outlookAddinEnabled` is on, a Microsoft Office add-ins item in the Connections section (shown on its own when only this toggle is on), whatever the state of the MCP list, that opens `office-add-ins/` (`/admin-settings/integrations/office-add-ins`; with the toggle off it redirects to the integrations) with the Outlook add-in's installation (`OutlookAddinSection`: the deployment's manifest URL with copy and download, a link straight to the admin center's Integrated apps page and the deployment steps there, worded like Microsoft's docs) and a coming-soon card for the other Office tools, team/user management, role & permission management (`roles-settings/` — a matrix where admins grant per-permission access to the MANAGER and USER roles; admins implicitly hold all; a catalog section can name a feature toggle, so the Routines group shows only while `routinesEnabled` is on, and saving still sends the role's hidden grants; the last group, "In a workspace (by role in the workspace)", holds the permissions read for the role a member has inside a workspace), security, letterhead management (list in `letterheads-settings/`, detail/edit in `letterhead-detail/`), while `oparlEnabled` is on `oparl-settings/` (`/admin-settings/oparl`, "Council information": the OParl catalog's bodies with their system, searched in the browser, selected and linked to the organization or unlinked; with the toggle off the entry is hidden and the route redirects to the users), and usage analytics. The super-admin `oparl/` page lists under each body the organizations that linked it. The `super-admin-settings/` group provides platform-wide management for the models catalog, organization oversight, and platform configuration including per-tier fair-use message budgets via `FairUseLimitsSection` (with `useFairUseLimits` and `useSetFairUseLimit` hooks performing `windowMs ↔ windowHours` conversion at the hook boundary), and, while `recordingsEnabled` is on, the recording upload limit via `RecordingFairUseSection` (`useRecordingFairUseLimit`, `useSetRecordingFairUseLimit`), which shares `SingleFairUseLimitCard` with the image-generation limit. Each page uses the hooks pattern—one custom hook per operation (create, update, delete)—encapsulating TanStack Query mutations with toast notifications and cache invalidation. Hooks that create or install a resource send its OpenPanel adoption event only after the request succeeded: `knowledge_base_created` (`workspace_context` true from the workspace page), `skill_created` from the skills page, the workspace page and the chat's `create_skill` widget (never with the name; super-admin skill templates send nothing), `skill_installed` with the marketplace slug from the install page and the chat's install widget, `routine_installed` with the marketplace slug from the routine install page, `integration_installed` from the integration install page, and `integration_connected` from the integration install page, the admin create/edit hooks, the per-user credentials form and the OAuth callback (rules in `shared/lib/openpanel-integrations.ts`). The `workspaces/` page slice renders the paginated `/workspaces` list — one row per workspace — plus the create dialog trigger and per-workspace pin buttons. The `workspace/` page slice renders `/workspaces/$workspaceId`: breadcrumb, hero with the workspace's icon and description, pin and settings actions, and the "Ihre Chats" tab whose count badge uses the server's pagination total rather than the loaded page size. The `new-chat/` page gained `ui/WorkspacePicker.tsx`, a dropdown above the composer that files the new chat under a workspace (with inline workspace creation; re-selecting the current one detaches it) — the chosen id flows through `useInitiateChat` into thread creation, and the `/chat` route accepts a `workspaceId` search param to preselect it. The `workspace/` overview page embeds the `widgets/chat-starter` composer with the workspace fixed — sending lands directly in the created chat. `chat/` shows a pin star in the chat header. A chat opened while its run is in progress — after a reload, from another tab, or a routine execution — attaches through the `@ayunis/chat` conversation runtime, unless this page streams that run itself, the active-runs list predates its own run ending, or the user stopped that run and the server has not let it go yet; the Stop button is disabled for runs that cannot be cancelled (routine executions). A failed attach is not retried while the run stays listed and is not reported as a failed send. The shared run lifecycle buffers the latest message snapshots, masks, and title while a running chat is closed, then delivers them when that chat reopens. `useWebRunObserver` binds it to host analytics, error presentation, and cache refresh. The observer also sends the OpenPanel run funnel (`lib/run-funnel-tracking.ts`): `run_started` when a sent message's stream returns that message, with `thread_turn` and `voice_input`, and `ai_output_delivered` at most once per run in a tab when a send or reattach stream reaches the run's closing session event without an error or abort, with the "used" flags of the run's tool calls that did not fail (classified by `getToolUsageKind`; the browser only sees a failed call through the result text the backend saves for it). The chat page also sends `productive_outcome` (through `ProductiveOutcomeProvider`) only after the action succeeded: copying an answer or a code block of an assistant answer, exporting an artifact (`useExportArtifact`), saving a user-authored artifact version (`useUpdateArtifact`, never for AI-authored versions or letterhead changes), downloading a diagram, chart or generated image, handing off an email by mail link or copy, and downloading a calendar event. Artifacts opened from a workspace's artifacts tab open in their chat and are tracked there. Answers and submitted user messages share `CopyMessageButton`; a user message copies the same text as the recalled prompt history (`resolvedPromptText`: Markdown source with masked PII restored, without hidden skill instructions or nudges), while an answer copies its rendered text blocks as HTML and plain text. While `readAloudEnabled` is on, a completed answer with text offers read aloud next to copy (`ReadAloudButton`): `speakableMessageText` reads the same text blocks copy takes, replacing every node with a `data-speech-text` override (PII masks become their category, code blocks and citation chips drop out) and reading tables row by row; `readAloudPlayer` plays one answer at a time, streams the audio from `POST /speech` through Media Source Extensions (`StreamedAudio`, which reads the download at full speed but feeds the browser's capped media buffer only as playback frees room) and keeps the audio of the last 20 answers for replay as soon as it is complete.

In the `chat/` page, a tool call the backend marks `requiresConfirmation` renders as a `ToolCallConfirmationCard` (`agent-run-timeline`): integration logo and name, the upstream tool name and the input as stored (placeholders in anonymous chats). While no run is active and the call has no result it offers Confirm, Reject and an Always allow checkbox applied only on Confirm; the shared `ChatConversation` runtime keeps each decision until every call awaiting confirmation in the last turn is decided, then sends them in one request (`decisions` on `POST /runs/send-message`) and streams the continuation like a message. The timeline row of such a call, and the paused turn's other calls, appear only once they run or ran; a decided card shows Confirmed or Rejected from its result's `decision`. Sending a message instead is allowed, and the backend rejects the waiting calls.

The Web chat page renders the package-owned `ChatConversation` runtime. Web-specific cache refresh, authentication recovery, error presentation, and OpenPanel run analytics enter through `useWebRunObserver`; the page supplies only host slots and adapters. Outlook uses the same package entry from its own app under `apps/outlook`.

Organisation management in `super-admin-settings/org/` includes archive/restore confirmation and irreversible name-confirmed deletion (`OrgLifecycleActions`, `DeleteOrgDialog`, `useSetOrgArchived`, `useDeleteOrg`). The `orgs/` list shows one derived lifecycle badge per organisation (Paying, Expired, Trial, No plan, Archived) and filters by it through `OrgLifecycleFilter` (`orgLifecycle` search param, default all). `OrgLifecycleSummary` renders a muted line under the search bar with the total and per-status counts from the list response (following the search, not the lifecycle filter). The organisation detail card shows the same status through the shared `org-lifecycle-badge` widget; subscription and trial mutations call `invalidateOrgLifecycleQueries` so the list and detail badges refetch. Lifecycle mutations invalidate the affected organisation queries. The organisation details also expose the super-admin-only `UsageVisibilitySection` card titled Nutzungsdaten / Usage data, placed after the Name/ID details and before organisation management; its `UsageVisibilityItem` / `useSetOrgUsageVisibility` switch for hiding individual user usage. Organisation-admin usage pages verify fresh configuration before mounting the user table; the user credit-limit list shows only configured limits when consumed credits are omitted, while team credit-limit lists and the team detail card always show consumption. Visible usage and user/team credit-limit pages poll their TanStack queries every five seconds and refresh on tab focus so cross-session privacy changes appear without reloading; background polling is paused. Background refreshes preserve mounted sections and pagination.

**Usage visibility (AYC-1342).** Hiding individual usage does not restrict team management, membership, team limits, user deletion or invitation team assignments. Normal role and organization ownership checks still apply. Super-admin team management endpoints remain available.

The super-admin organization Users tab includes per-invite deletion and organization-wide pending-invite cleanup with destructive confirmation dialogs. Bulk confirmation explicitly covers invitations outside the current search/page; successful cleanup refreshes the list and resets invite pagination.

Super-admin organization subscription and Academy controls become read-only when the backend advertises external subscription management. Details and subscription history remain visible, trials remain editable, and a notice directs commercial changes to Sales. The `routines/` page (`/routines`, behind the `routinesEnabled` feature toggle and the `manage_routines` permission; the route loader redirects to `/chat` when either is missing, re-reading the permissions so a grant changed in another session applies) lists the user's routines with schedule, the next run (`RoutineScheduleLine`; or "paused after repeated failures" when `pausedAt` is set, cleared by switching the routine back on), internet badge, last run status and failure or skip reason (`lib/failure-reason.ts` maps stored codes to copy), an enable switch and Run now; a row opens the routine's page. The internet badge shows for "all websites" and "only these domains". There is no integration badge on the list. The `routine/` page (`/routines/$routineId`, same toggle and permission check as the list, in `-manage-routines-access.ts`) shows the routine's name with its last run status as a badge (`RoutineRunStatusBadge`, so it stays visible on every tab), the enable switch, Run now and delete (which returns to the list) above three tabs (`?tab=`, with `?page=` for the lists): Configuration (a status card with the last run, its failure or skip reason, the readable schedule and the next run; the configuration form (`RoutineFormFieldset`: name, task, the model (the page passes the `routine-model-field` widget) with "my default model", which sends no model, Auto and Max, which send `mode` and clear a stored model (a mode that resolves to nothing for the user is disabled), or a permitted model, which clears a stored mode, the schedule and internet access Off / All websites / Only these domains, the domain list one per line shown only in the last mode and kept in the others; `ROUTINE_INVALID_ALLOWED_DOMAINS` shows on the domain field) with its own Save button; and the Context card, whose tabs Integrations and Knowledge bases (the latter only with an embedding model enabled) list switches that each save at once through `POST`/`DELETE /routines/:id/mcp-integrations/:id` and `/knowledge-bases/:id`, showing the new state at once and flipping back with an error toast if saving fails. Integrations come from `GET /mcp-integrations/available`; one the user has not connected can only be switched off, with the chat's "authorize first" hint, and a linked one that is no longer available stays listed as unavailable so it can be switched off (`lib/routine-integration-options.ts`). Knowledge bases are the user's own and shared personal ones; there is no edit dialog), Notifications (this routine's notifications including errors, newest first, 20 per page, through `GET /notifications?routineId=`; each opens the notification page) and Chats (this routine's threads, newest first, 20 per page, through `GET /threads?routineId=`; each opens the chat). In the `chat/` page, a `finish_routine` call renders as a compact "Routine finished" marker (`routine-finished` run block) and a user message whose text is marked `isNudge` renders as `RoutineNudgeNotice` instead of a user bubble; nudges are also left out of the recalled prompt history.

The `recordings/` page (`/recordings`) and the `recording/` page (`/recordings/$id`) exist only while `recordingsEnabled` is on; both route loaders redirect to `/chat` otherwise (`-recordings-enabled.ts`). The list shows the user's own recordings plus those of their teams and organisation in `OwnerSections`, with a create dialog whose owner choice offers only the owners the user may manage (grouped like the skill owner select) and a delete action for manageable rows. The create dialog (list page and workspace tab) also takes the audio file (MP3, M4A, WAV or WebM): it creates the recording, uploads the audio straight to storage (`features/recording-audio`) and then opens the recording; a failed upload is reported and the recording kept without audio. The Configuration tab holds `ResourceOwnerCard` (managers only, to move between owners) and `RecordingPropertiesCard` (owner, creator and creation date; rename); it stays mounted, so an unsaved name survives a tab switch, and the upload's progress is held above the tabs for the same reason. Workspace recordings open on the same detail page, with breadcrumbs back to the workspace's Recordings tab, which the `workspace/` page shows (with count) only while the toggle is on (`WorkspaceRecordingsTab`, `api/useWorkspaceRecordings.ts`); managing a workspace recording there or on the detail page takes `manage_recordings` and the workspace's `manage_workspace`. The `release-notes/` page (`/news`, "Neuigkeiten", opened from the bell in the sidebar header) lists Ayunis' product updates newest first, unpaged: each row shows a 16:9 thumbnail (the note's image from `GET /release-notes/:id/image`, or a placeholder for a Loom video or a note without media), a kicker with the note's date, the headline, a two-line plain-text summary and, at the right end, a dot while the update is unread for the user. The `release-note/` page (`/news/$releaseNoteId`) shows one update with a breadcrumb back to the list, the kicker, the headline, its media (`NotificationMedia`), the markdown body and the `widgets/chat-starter` composer, whose first message creates a thread with the origin `{ kind: 'release_note', releaseNoteId }`; opening the page marks the update read, and the chat header of such a thread shows a "Product update" badge linking back, read from its `release_note` origin. Both routes require the `releaseNotesEnabled` toggle (routines on and an Announcable org ID in the backend) and redirect to `/chat` without it. The `inbox/` page is a split view rendered by the `/inbox` layout route: the list of the user's notifications on the left and the open notification (its child route) on the right, so the list stays in place while notifications are opened. The list shows only unread notifications by default, newest first, 20 per page (`?page=`, a compact pager under the list; polled every minute), each with its type icon, headline, unread dot, subheadline (left out when there is none), relative time, a "Needs attention" outline badge plus red alert icon for failed-routine notifications and, on hover (always below `md`), a mark-read button, or a mark-unread button on a read one; the open one is highlighted and stays listed while open even once read (`lib/with-open-notification.ts`). The filter next to the title (`InboxReadFilter`, the sidebar chat filter's pattern) shows read notifications too (`?showRead=true`), unread ones first, each newest first (`GET /notifications?unreadFirst=true`); with read ones hidden, an empty first page says there are no unread notifications. The header offers "Mark all as read". `?type=` filters the list by notification type (the new chat page's unread panel links there); opening a notification, paging and clearing the filter keep the other search params and the open notification. Release notes are not notifications and never appear here. Without an open notification the right pane asks to pick one (`InboxNoSelection`, the `/inbox/` index route), and an empty first page with nothing open shows the empty state instead of the split view. Below `md` only one pane shows: the list, or the open notification with a back link to the list. The `notification/` page (`/inbox/$notificationId`, the right pane of the inbox) shows one notification with its media (`NotificationMedia`: an image from `GET /notifications/:id/image` or a Loom video in a 16:9 iframe) and its markdown body rendered by the shared `Markdown` widget (links open in a new tab, images are not rendered), marks it read when opened (once, so marking the open notification unread keeps it unread), links to the originating routine thread when there is one, offers Open routine (to `/routines/$routineId`) while the routine still exists and the user holds `manage_routines` (the route reloads the notification on every visit, since deleting the routine clears the link), and embeds the `widgets/chat-starter` composer below it, asking what the user wants to know about the notification: the first message creates a thread outside any workspace with the origin `{ kind: 'notification', notificationId }` and opens it, using the user's usual model, mode and anonymous defaults. The chat header shows a "Notification" badge linking back to it, read from the thread's `notification` origin. Both routes and the badge require the `routinesEnabled` toggle; the inbox layout route redirects to `/chat` without it, before the notification route loads.

Chat files stay as badges above the chat input. Uploading is unchanged: the badge shows the transfer percentage and Send is disabled until the upload is done. Processing no longer blocks Send: a message sent while a file is still being processed is deferred (`deferThreadRun`) and shown as pending, and the conversation shows a temporary progress block (`source_processing` steps in the agent activity timeline, built by `sourceProcessingSteps` from the thread's processing sources and `GET /threads/:id/sources/progress`: stage plus pages or parts read). The block is frontend state only and disappears once the files are ready; a failed file is marked on its badge.

The chat page supplies the shared chat shell with its header, actions and artifact-opening callbacks. Workspaces, routine navigation, favorites and the resizable side panel remain app-owned. The new-chat layout uses typed slots for its header and empty state, while the greeting is passed as content to the shared `NewChatShell`.
