# Route Modules

Page components composing widgets and features for each application route.

Route-level page modules handle authentication, chat conversations, agent management, prompt libraries, knowledge base management, skill management, user settings, organization admin settings, and super-admin platform management. Each page follows a consistent internal structure with api/, ui/, and model/ subdirectories separating data hooks, components, and types.

Chat file uploads and removals invalidate the subscribed thread query only. Upload mutations await the thread refresh so sending stays blocked until the chat sees the uploaded source and its processing status. Post-run refetches replace stale requests in one operation, keeping upload callers waiting through the replacement. They do not reload route loaders, whose pending thread fetches can otherwise be cancelled by concurrent uploads.

Existing chats match their bound model to the current effective grant by catalog model id, so switching defaults or moving between equivalent organization and team grants does not incorrectly hide the composer.

The chat overview page places its search control in the content header. The project overview keeps only the add-project action there without repeating a content title. Project rows expose pinning with an explanatory tooltip.

The new-chat page combines personal/shared and selected-workspace pinned skills into the same selectable quick-action buttons. Workspace changes clear only a selected skill belonging to a different workspace; regular skill selections remain available.

The workspace page also includes the Erstellte Inhalte tab for project artifacts; tabs follow the sidebar-oriented order Chats, Erstellte Inhalte, Fähigkeiten, Wissen, Anweisungen. Artifact rows open the corresponding chat editor through URL search parameters, while artifact lists load within the workspace tabs.

The `workspace/` page slice also includes context tabs for Wissen, Skills and Anweisungen. Skills and knowledge bases are created as workspace-owned resources and open workspace-scoped detail routes after creation. Those detail pages reuse the personal skill and knowledge-base creation dialogs, property cards, assignment card, document card, and header controls while keeping workspace-scoped routes. Both personal and workspace flows use the canonical owner-aware `/skills` and `/knowledge-bases` APIs; persisted detail ownership determines access, while create and list requests carry the explicit owner scope. They assign same-workspace knowledge bases to skills, manage additional documents through canonical skill source endpoints, and manage documents inside workspace knowledge bases, while standalone project files do not exist. Project skill and knowledge-base rows reuse their personal-resource presentations, expose workspace-wide activation controls (plus project pinning for skills), and place creation as the tab's top-right action; `api/useWorkspaceContextActions.ts` sends canonical skill mutations and owns workspace cache invalidation; `useWorkspaceSkills.ts` wraps the paginated workspace skill scope. `GET /workspaces/:id/context` remains the runtime-context source for selected-workspace pinned skills.

The `super-admin-settings/users/` page provides a searchable cross-organization user directory with account lock status, account recovery, password reset, organization navigation, deletion, and CSV export controls. Organization admins see the same lock status and recovery action in their user settings.

Municipal SSO uses separate auth route slices for direct organization links, successful completion, and actionable failures. Every broker callback lands on one of these fixed application routes. SSO connections are managed by Superadmins rather than organization admins from Account Settings.

Account settings reads authenticated SSO link status and offers Connect SSO only when the backend permits it; linked and JIT users see SSO connected. The account-link-required error sends users through local login back to account settings. Broker return query parameters never establish connected state: the card always reads persisted status.

The Superadmin organization SSO tab configures one or more verified email domains for the same broker mapping, reviews the complete set before activation, and controls whether an active organization requires SSO. Enforcing SSO requires an explicit confirmation against the current mapping. For SSO-only organizations, login and invitation acceptance present the organization SSO action without password or password-reset controls.

The Super Admin sidebar keeps incident tooling in a separate Operations group; Queue inspection opens the protected Bull Board route in a new tab.

The `auth/` group contains the login, register, email confirmation, password forgot/reset, and invite acceptance flows. Generated images in chat and in the enlarged dialog sit on a light checkerboard so a transparent background stays visible in dark mode. The `chat/` and `new-chat/` pages manage AI conversation interfaces with message streaming, agent selection, knowledge base attachment (`useKnowledgeBaseAttachment` hook for adding/removing KBs on existing threads, plus pending-KB context state for new threads), an opening timeline hint that summarizes active AI context and opens the context panel, and a resizable tabbed side panel for created-content browsing/editing and lazy thread AI-context inspection (skills and knowledge bases), including guarded dirty-editor transitions and artifact letterhead changes. Streamed message snapshots are applied at most once per animation frame (latest per message; other run events and the end of the run flush pending snapshots first), and `useRenderUnits` reuses unchanged run units so memoized run blocks only re-render the streaming run. The chat run timeline shows a tool as soon as the model names it, before its input is complete; cancelling a run drops an unsaved assistant message that only named tools still being prepared. The timeline displays accumulated raw tool input while it streams, renders malformed terminal calls as non-actionable errors, retains those presentation-only errors across same-thread refetches without treating them as persisted history, formats namespaced MCP capabilities with their readable upstream names, and presents successful document reads as editor cards so older generated documents remain accessible inline. Its page-local `GeoJsonMapWidget` uses MapLibre to render point, line, polygon, and multi-geometries, fit their bounds, expose properties as plain-text popups, and show basemap plus distinct data attribution without duplication; runtime frontend configuration can override the basemap tiles and attribution. The page-local `InstallMarketplaceSkillWidget` renders the assistant's `install_marketplace_skill` call as a confirmation card: it shows only the catalogue entry fetched for the model's identifier (`useMarketplaceSkillEntry`), links to the existing skill when the user already installed that entry (`useInstalledMarketplaceSkill` over `GET /skills/marketplace/:identifier`), installs through `useInstallMarketplaceSkillFromChat` for users with `manage_skills`, and shows an administrator hint to everyone else. The `chats/` page lists conversation threads. The `agents/` and `agent/` pages handle AI assistant browsing and detailed configuration. The `prompts/` page provides prompt library management. The `knowledge-bases/` page lists knowledge bases with creation, deletion, and per-user active toggles, while `knowledge-base/` provides the detail view for a single knowledge base including the same active control, document upload, removal, and property editing. New knowledge bases start active, and active owned or shared knowledge bases are automatically available to chat knowledge tools. The `skills/` page lists available skills, and `skill/` shows skill details. Academy learning spans three page slices: `academy/` lists chapters, `academy-chapter/` shows embedded Loom videos, and `academy-chapter-confirmation/` requires the learner to confirm they watched the videos before completing the chapter. Whole-academy completion offers the KI-Schulung nach EU AI Act participation-confirmation PDF through `useDownloadParticipationConfirmation`. The `install/` page handles app installation flows. User `settings/` includes account, general preferences, `chat-settings/` for per-user AI conversation configuration (custom system prompts), and per-user MCP credentials. The `admin-settings/` group covers organization administration: model configuration, API-key management with per-key monthly credit usage and limits, MCP integrations (including a custom-server field builder for organization and user HTTP headers), team/user management, role & permission management (`roles-settings/` — a matrix where admins grant per-permission access to the MANAGER and USER roles; admins implicitly hold all; a catalog section can name a feature toggle, so the Routines group shows only while `routinesEnabled` is on, and saving still sends the role's hidden grants), security, letterhead management (list in `letterheads-settings/`, detail/edit in `letterhead-detail/`), and usage analytics. The `super-admin-settings/` group provides platform-wide management for the models catalog, organization oversight, and platform configuration including per-tier fair-use message budgets via `FairUseLimitsSection` (with `useFairUseLimits` and `useSetFairUseLimit` hooks performing `windowMs ↔ windowHours` conversion at the hook boundary). Each page uses the hooks pattern—one custom hook per operation (create, update, delete)—encapsulating TanStack Query mutations with toast notifications and cache invalidation. The `workspaces/` page slice renders the paginated `/workspaces` list — one row per workspace — plus the create dialog trigger and per-workspace pin buttons. The `workspace/` page slice renders `/workspaces/$workspaceId`: breadcrumb, hero with the workspace's icon and description, pin and settings actions, and the "Ihre Chats" tab whose count badge uses the server's pagination total rather than the loaded page size. The `new-chat/` page gained `ui/WorkspacePicker.tsx`, a dropdown under the composer that files the new chat under a workspace (with inline workspace creation; re-selecting the current one detaches it) — the chosen id flows through `useInitiateChat` into thread creation, and the `/chat` route accepts a `workspaceId` search param to preselect it. The `workspace/` overview page embeds the `widgets/chat-starter` composer with the workspace fixed — sending lands directly in the created chat. `chat/` shows a pin star in the chat header. A chat opened while its run is in progress — after a reload, from another tab, or a routine execution — attaches to it through `useThreadRunReattach` (`useMessageSend.attach`), unless this page streams that run itself, the active-runs list predates its own run ending, or the user stopped that run and the server has not let it go yet; the Stop button is disabled for runs that cannot be cancelled (routine executions). A failed attach is not retried while the run stays listed and is not reported as a failed send. Events a run streams while its chat is not open are kept by `useMessageSend` (the latest snapshot of each message, plus masks and title) and delivered when that chat opens again. While `readAloudEnabled` is on, a completed answer with text offers read aloud next to copy (`ReadAloudButton`): `speakableMessageText` reads the same text blocks copy takes, replacing every node with a `data-speech-text` override (PII masks become their category, code blocks and citation chips drop out) and reading tables row by row; `readAloudPlayer` plays one answer at a time, streams the audio from `POST /speech` through Media Source Extensions (`StreamedAudio`, which reads the download at full speed but feeds the browser's capped media buffer only as playback frees room) and keeps the audio of the last 20 answers for replay as soon as it is complete.

Organisation management in `super-admin-settings/org/` includes archive/restore confirmation and irreversible name-confirmed deletion (`OrgLifecycleActions`, `DeleteOrgDialog`, `useSetOrgArchived`, `useDeleteOrg`). The `orgs/` list shows one derived lifecycle badge per organisation (Paying, Expired, Trial, No plan, Archived) and filters by it through `OrgLifecycleFilter` (`orgLifecycle` search param, default all). `OrgLifecycleSummary` renders a muted line under the search bar with the total and per-status counts from the list response (following the search, not the lifecycle filter). The organisation detail card shows the same status through the shared `org-lifecycle-badge` widget; subscription and trial mutations call `invalidateOrgLifecycleQueries` so the list and detail badges refetch. Lifecycle mutations invalidate the affected organisation queries. The organisation details also expose the super-admin-only `UsageVisibilitySection` card titled Nutzungsdaten / Usage data, placed after the Name/ID details and before organisation management; its `UsageVisibilityItem` / `useSetOrgUsageVisibility` switch for hiding individual user usage. Organisation-admin usage pages verify fresh configuration before mounting the user table; the user credit-limit list shows only configured limits when consumed credits are omitted, while team credit-limit lists and the team detail card always show consumption. Visible usage and user/team credit-limit pages poll their TanStack queries every five seconds and refresh on tab focus so cross-session privacy changes appear without reloading; background polling is paused. Background refreshes preserve mounted sections and pagination.

**Usage visibility (AYC-1342).** Hiding individual usage does not restrict team management, membership, team limits, user deletion or invitation team assignments. Normal role and organization ownership checks still apply. Super-admin team management endpoints remain available.

The super-admin organization Users tab includes per-invite deletion and organization-wide pending-invite cleanup with destructive confirmation dialogs. Bulk confirmation explicitly covers invitations outside the current search/page; successful cleanup refreshes the list and resets invite pagination.

Super-admin organization subscription and Academy controls become read-only when the backend advertises external subscription management. Details and subscription history remain visible, trials remain editable, and a notice directs commercial changes to Sales. The page-specific `org/lib/useSubscriptionReadOnly` hook keeps manual controls blocked while configuration is unresolved or failed, and allows editing only when external management is explicitly disabled.

The `routines/` page (`/routines`, behind the `routinesEnabled` feature toggle and the `manage_routines` permission; the route loader redirects to `/chat` when either is missing, re-reading the permissions so a grant changed in another session applies) lists the user's routines with schedule, the next run (`RoutineScheduleLine`; or "paused after repeated failures" when `pausedAt` is set, cleared by switching the routine back on), internet badge, last run status and failure or skip reason (`lib/failure-reason.ts` maps stored codes to copy), an enable switch and Run now; a row opens the routine's page. `CreateRoutineMenu` opens `CreateRoutineDialog` blank or prefilled from a fixed premade routine (`model/premade-routines.ts`, currently the German Verkündungsplattform prompt with bracketed placeholders) and lands on the new routine's page after saving; the model select offers "my default model", which sends no model so the backend stores the user's default. Below the internet switch, the form (`RoutineIntegrationsField`) offers one switch per integration from `GET /mcp-integrations/available` (hidden when there are none and while the list loads; an error line if it fails, and the stored selection is saved unchanged either way); one the user has not connected can only be switched off, with the chat's "authorize first" hint, and a selected one that is no longer available stays listed as unavailable so it can be switched off (`lib/routine-integration-options.ts`). There is no integration badge on the list. The `routine/` page (`/routines/$routineId`, same toggle and permission check as the list, in `-manage-routines-access.ts`) shows the routine's name with its last run status as a badge (`RoutineRunStatusBadge`, so it stays visible on every tab), the enable switch, Run now and delete (which returns to the list) above three tabs (`?tab=`, with `?page=` for the lists): Configuration (a status card with the last run, its failure or skip reason and the next run, and the definition form; there is no edit dialog), Notifications (this routine's notifications including errors, newest first, 20 per page, through `GET /notifications?routineId=`; each opens the notification page) and Chats (this routine's threads, newest first, 20 per page, through `GET /threads?routineId=`; each opens the chat). It polls the routine like the list and refreshes both tabs on every poll, since a running run posts notifications without the routine changing. Another user's routine answers 404, so its page shows the error fallback. `useRoutines` polls every 3 s while a run is queued or running and every 30 s otherwise (scheduled runs start in the background), and refreshes the chat lists on every status change, since a run creates its routine thread in the background. In the `chat/` page, a `finish_routine` call renders as a compact "Routine finished" marker (`routine-finished` run block) and a user message whose text is marked `isNudge` renders as `RoutineNudgeNotice` instead of a user bubble; nudges are also left out of the recalled prompt history.

The `inbox/` page (`/inbox`) lists the user's notifications newest first with pagination (`?page=`, 20 per page; polled every minute), unread dot, headline, subheadline (left out when there is none, as for release notes), time and an "Error" badge plus alert icon for failed-routine notifications, and offers "Mark all as read". `?type=` filters it by notification type (the unread buttons on the new chat page link there); the release-note filter only exists with the `releaseNotesEnabled` toggle (routines on and the backend's release-note source configured), otherwise the route drops it. The `notification/` page (`/inbox/$notificationId`) shows one notification with its media (`NotificationMedia`: an image from `GET /notifications/:id/image` or a Loom video in a 16:9 iframe) and its markdown body rendered by the shared `Markdown` widget (links open in a new tab, images are not rendered), marks it read when opened, links to the originating routine thread when there is one, offers Open routine (to `/routines/$routineId`) while the routine still exists and the user holds `manage_routines` (the route reloads the notification on every visit, since deleting the routine clears the link), and embeds the `widgets/chat-starter` composer below it, asking what the user wants to know about the notification: the first message creates a thread outside any workspace with `sourceNotificationId` and opens it, using the user's usual model, mode and anonymous defaults. The chat header shows a "Notification" badge linking back to it. Both routes and the badge require the `routinesEnabled` toggle; the routes redirect to `/chat` without it.
