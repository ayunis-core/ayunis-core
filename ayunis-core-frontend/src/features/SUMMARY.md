# Cross-Cutting Logic

Self-contained business logic modules shared across multiple pages and widgets.

The `feature-toggles/` feature exposes `useFeatureToggles`, including `externalSubscriptionsEnabled` for billing controls and `routinesEnabled` for the routines page, the inbox, sidebar entries and routine chat filter. It exposes loading, error, and retry state. The generic `useIsFeatureEnabled` defaults unknown features to disabled. Subscription editing uses the page-specific `useSubscriptionReadOnly` policy: controls stay blocked until configuration explicitly allows manual management, while a distinct loading or retry notice avoids claiming external ownership during a configuration failure.

Feature modules and standalone hooks provide cross-cutting concerns: theme management (dark/light mode persistence), language switching (German/English via i18next), model/provider configuration with provider icon utilities, usage analytics data hooks for statistics, charts, and distribution metrics, skill action hooks for toggling skill active/pinned state, marketplace configuration for exposing marketplace availability and destination URLs, fair use limit editing for shared limit validation and edit state, permission gating for hiding UI controls the current user lacks access to, super-admin user mutations, and active thread-run cancellation.

The `super-admin-user-actions/` feature centralizes password-reset and deletion mutations, including cache invalidation and error handling, for super-admin user tables.

The `bulk-user-invite/` feature provides the shared CSV upload, preview, and invitation result flow used by organization Admins and Super Admins. Its optional `teams` column accepts pipe-separated team names and routes the request through the role-appropriate bulk invite endpoint.

The `sso/` feature owns generated-client discovery and account-linking hooks, browser navigation to backend SSO endpoints, tab-scoped memory of the last successful SSO organization for returning sign-in, and conversion of stable, non-secret callback error codes into user-facing categories.

The `anonymous-mode-default/` feature provides `useAnonymousModeDefault`, the org-wide default for starting new chats in anonymous mode. The admin anonymization settings page sets it, and the new-chat page and the workspace chat starter use it to prefill their anonymous toggle; users can still turn it off per chat, and a model's `anonymousOnly` enforcement keeps precedence. The value is persisted per organization through chat settings. Route loaders await the member-readable default before the composers initialize; saves invalidate both admin settings and member-default queries.

The `theme/` feature manages dark/light mode with localStorage persistence through `useTheme`, `setTheme`, and `getTheme` utilities. The `language/` feature wraps i18next language switching in a `useLanguage` hook. The `models/` feature provides `useLanguageModels`, `useEmbeddingModels`, `useImageGenerationModels`, and `useProviders` hooks for fetching AI model configurations by type, plus provider constants and icon utilities for Ollama, Mistral, Anthropic, and OpenAI. The `usage/` feature contains analytics hooks (`useUsageStats`, `useUserUsage`, `useProviderUsage`, `useProviderUsageChart`, `useModelDistribution`, `useUsageConfig`) powering admin dashboard charts. The `skill-actions/` feature provides `useSetSkillActivation` and `useSetSkillPin` hooks for idempotently setting personal skill activation and pin state, plus `useImproveSkillText`, which asks Ayunis Core to rewrite a skill's trigger or instructions and maps the improver's error codes (empty answer, no usable model, usage limit reached) to toasts. The `marketplace/` feature provides a `useMarketplaceConfig` hook that returns marketplace availability plus the configured destination URL for marketplace entry points. The `fair-use-limit-editor/` feature provides `useFairUseLimitEditor` for reusable fair use limit edit state and validation. The `academy/` feature exposes the add-on gate, the org-level Academy completion status that gates Core chat, per-chapter confirmation and whole-academy progress, and `useDownloadParticipationConfirmation` for the KI-Schulung nach EU AI Act participation-confirmation PDF. For annual renewal it also owns the pure expiry-notice calculation; rendering remains in the expiry widgets. The `permissions/` feature centralizes frontend authorization through the pure `createAuthorization(role, permissions, teams)` helper and its React adapter `useAuthorization` (`lib/`, `api/`), exposing `can`, `canAny`, and `hasRole` without conflating delegatable permissions with admin-only role policy. Team roles add team-scoped checks: `useMyTeams` reads `GET /teams/me` (each team with the user's team role and effective permissions there), and `canInTeam`, `canAnyInTeam`, `canAnyInSomeTeam` and `canManageTeamRoles` mirror the backend's team access; `TeamPermissionGate` (`ui/`) is the team-scoped `PermissionGate`. `useMyPermissions` fetches the current user's effective RBAC permissions from `GET /permissions/me` for gating UI controls — e.g. hiding the create-skill / create-knowledge-base controls from members who lack the permission; the `PermissionGate` component (`ui/`) renders its children only for holders of any of the given permissions; and `allowedSettingsSections(authorization)` with the `MANAGER_SETTINGS_SECTIONS` map (`lib/`) is the single answer to "may this user open this admin-settings section?" used by the `admin-settings` route guard and both sidebars (admins get the settings root, which prefixes every section, while other roles get only permission-backed sections; `teamScoped` sections such as Teams also open for a permission held only through a team role). The `thread-run/` feature owns thread deletion, the `POST /runs/send-message` request (`postRunMessage`), attaching to a run in progress (`attachThreadRun`, `GET /runs/threads/:id/events`, 204 when there is none), and the browser-local active-run registry. Runs continue on the server when the browser stops listening, so `stopThreadRun` (the chat's Stop and a cancelled new-chat initiation) cancels the run there (`POST /runs/threads/:id/cancel`) before dropping the local stream and marks it stopped (`stopped-thread-runs.ts`) until the active-runs list no longer shows it, so reopening the chat cannot replay it (a failed cancel removes the mark again, so the chat follows the run that kept going); `useLocalActiveThreadRunIds` exposes the threads this tab is streaming; and `useActiveThreadRuns` polls the user's runs in progress (`GET /runs/active`) every 3 seconds while there are any and every 30 seconds otherwise; `expectActiveThreadRun` refetches it and polls every second for 30 seconds, so a run a queued job is about to start (Run now on a routine) shows in the sidebar without waiting for the idle poll. Starting a streamed send registers its `AbortController`; `startThreadRun` sends a new chat's first message before its chat page exists and keeps the unread response until that page takes it once (`takeStartedThreadRun`) or the initiation is cancelled; deleting that thread from either the chat header or sidebar aborts the stream before issuing the delete request, then clears its local prompt draft after deletion succeeds. Standalone hooks at the feature root include `useAgents` for agent listing, `useRenameThread` for thread management, `useAutoScroll` for chat scrolling behavior, `useContentScrollHeader` for tracking whether scrolled content sits under the frosted overlay header, `useSidebarGroupOpen` for persisting a sidebar group's collapsed state in localStorage under a caller-supplied key (favorites and chats each pass their own), `useKeyboardShortcut` for hotkey bindings, `usePermittedModels` for org-scoped model access, `useModelModes` for which model each mode (Auto, Max) currently resolves to for the user, `useReleaseNotes` for the Announcable release-notes widget (shown only while routines are off; with routines on, release notes arrive in the inbox), `useRedirectNotification` for post-navigation toasts, and `useGtm` for Google Tag Manager integration. The `workspaces/` feature holds only the workspace ("Projekt") hooks that are genuinely shared across slices — `useWorkspace` for loading one workspace by id, `useWorkspaces` for listing workspaces, and `useDeleteWorkspace` — plus the `Workspace` type and the `WORKSPACES_PER_PAGE` page size in `model/`, shared by the overview route and the getting-started tour helper `findPinTourWorkspace` in `widgets/onboarding` so both agree on which rows are on page one; single-consumer mutation hooks live in their consumer widget's `api/` segment instead (`useCreateWorkspace`, `useUpdateWorkspace` in the dialog widgets). The `favorites/` feature provides the shared pinning hooks, `useFavorites` and `useToggleFavorite`, used by the sidebar, the chat header, and the workspace pages; favorites form a strict, user-specific ordered list, and reordering is submitted by the sidebar's own `useReorderFavorites` hook in `widgets/app-sidebar/api/`. The `model-mode-defaults/` feature provides `useModelModeDefault` to read and set the mode default on the personal, team or organization level; setting a model default on a level clears its mode default on the server, so those mutations invalidate `getModelModeDefaultQueryKey`. The `notifications/` feature holds what the inbox pages and the sidebar share: `useUnreadNotificationCount` (only queried with `routinesEnabled` on, polled every minute since routines post in the background), `invalidateNotificationQueries` (list and unread count), `formatUnreadCount` for the badge, `NotificationTypeIcon`, which marks error notifications (`routine_error`) with a destructive alert icon and release notes (`release_note`) with a megaphone (`NOTIFICATION_TYPE_APPEARANCE` gives each type its icon and the order of the unread buttons on the new chat page), and `NotificationListItem`, the inbox row the routine page's Notifications tab reuses. The `routines/` feature holds what the routines list and the routine page share: the definition fields (`RoutineFormFieldset`, used by the create dialog and the Configuration tab, with `lib/routine-form-values.ts`), the enable switch and Run now button, the last-run and schedule lines (`lib/failure-reason.ts` maps stored codes to copy), the polling interval (`routinesRefetchInterval`) and `useUpdateRoutine` / `useRunRoutineNow`, which refresh both the list and the routine's own query. The `chat-initiation/` feature owns `useInitiateChat`, which starts a chat with either a `modelId` or a `mode` (and, for "Chat about this", the `sourceNotificationId`), the full new-chat pipeline (create the thread — optionally filed under a workspace — upload sources, attach knowledge bases and integrations, send the first message, navigate to the created chat), shared by the new-chat page and the workspace page's embedded composer; the new-chat settle animation is opt-out via its `settleAnimation` option and delays only the navigation, not the send.

The `resource-ownership/` feature (AYC-1642) mirrors the backend's team/org ownership rules for skills and knowledge bases: `manageableOwners` lists the owners a user may create for or move to (themself, the organization with the org share permission, and each of their teams whose effective permissions include the team share permission), `canManageResource` decides whether team- and org-owned items are editable (it requires the manage permission like the backend; shared personal items never are), and `useResourceOwnership(kind)` combines both with `useAuthorization`/`useMyTeams` and owner labels. `OwnerSelect` and `OwnerBadge` (`data-owner-type`) render the choice and the owner. `canLinkKnowledgeBase` applies the same-owner rule to the skill knowledge-base picker, and `ownerChangeErrorKey` maps owner-change error codes to messages.

**Usage visibility (AYC-1342).** Hiding individual usage does not restrict team management, membership, team limits, user deletion or invitation team assignments. Normal role and organization ownership checks still apply. Super-admin team management endpoints remain available.
