Usage Quotas
Fair-use quotas and the admission policy for every paid model call.

Implements a quota enforcement system that tracks user resource consumption within configurable time windows. Currently supports tier-aware fair-use message limits and a separate fair-use image-generation limit, preventing abuse while allowing reasonable platform usage.

This module provides rate-based usage control for Ayunis. The core entity is `UsageQuota`, which tracks a user's consumption count for a specific `QuotaType` (currently `FAIR_USE_MESSAGES_LOW`, `FAIR_USE_MESSAGES_MEDIUM`, `FAIR_USE_MESSAGES_HIGH` — one independent counter per model tier — and `FAIR_USE_IMAGES`, an independent counter for image-generation calls) within a sliding time window defined by `windowStartAt` and `windowDurationMs`. The entity includes business logic methods like `isWindowExpired()` to detect when a window has elapsed. Key components are `CheckQuotaUseCase` for verifying whether a user has remaining quota before allowing an operation, and `QuotaLimitResolverService` for determining the applicable limit and window for a given quota type. `CheckQuotaQuery` carries `userId`, `orgId`, and `quotaType`; `orgId` is used to short-circuit fair-use enforcement for organizations on a usage-based subscription, since those orgs already self-limit via their purchased credit budget (enforced by this module's `CreditBudgetGuardService`) and applying fair-use on top would double-cap them. The usage-based check is delegated to `SubscriptionsModule.IsUsageBasedSubscriptionUseCase`. The resolver reads live tiered limits from `PlatformConfigModule.GetFairUseLimitsUseCase` on every call so super-admin platform-config updates take effect immediately (no restart, no caching); it routes message quota types to the matching tier bucket and `FAIR_USE_IMAGES` to the dedicated `images` bucket. The `domain/tier-to-quota-type.ts` helper maps a `ModelTier` to its message bucket; untiered models default to MEDIUM, and the `ZERO` tier returns `null` to signal that the model is exempt from fair-use enforcement (no bucket, no row in `usage_quotas`). Note that the platform-config layer still persists `FAIR_USE_ZERO_*` rows for UI symmetry — the super admin can configure a value, but the resolver never reads it because ZERO short-circuits before reaching `QuotaLimitResolverService.resolve()`. Image enforcement is independent of the tier mapping. `QuotaExceededError` messages intentionally omit super-admin-configurable details (quota type, limit, window) so they don't leak through logs, HTTP response bodies, or LLM tool results; consumers that need those values read them from the error's `metadata`. It integrates with **platform-config** for live limit/window resolution, **subscriptions** for the usage-based fair-use short-circuit, **users** for user identification, and **domain/runs** and **domain/openai-compat**, which admit paid model calls through `InferenceAdmissionGuard`. The `UsageQuotaRepositoryPort` abstracts persistence with a PostgreSQL implementation that supports atomic increment operations.

## Paid-call admission

`InferenceAdmissionGuard` is the single entry point every caller uses before a paid model call. It separates run-admission fair-use gating (`preflight`, user-scoped via `CheckQuotaUseCase`, skipped for API-key principals) from monetary call-boundary gating (`ensureModelCallAllowed`, checked immediately before every paid provider call including retries and later tool turns). Credit gating is skipped when `model.consumesCredits` is false so free open-source models remain available after the budget is exhausted. Recording what a call consumed is not this module's job: callers invoke the usage module's `CollectUsageAsyncService` directly, awaiting it where a completed paid attempt must fail closed without usage.

- **CreditBudgetGuardService** — Combines `GetMonthlyCreditLimitUseCase` (from subscriptions) and `GetMonthlyCreditUsageUseCase` (from usage) at each paid call boundary. It throws `CreditBudgetExceededError` when the organization's monthly credit limit is reached and tells the principal-limit guards whether the active subscription is usage-based, avoiding a duplicate subscription lookup.
- **CreditLimitGuardService** — Enforces a user's personal and team-pool monthly credit limits, most restrictive wins, through the credit-limits module's resolver use case; team pools are measured through one batched membership query and one batched per-user usage query.
- **ApiKeyCreditLimitGuardService** — Resolves the acting key's optional monthly limit and current UTC-month consumption, then applies the same post-hoc threshold semantics as user/team limits: absent means unlimited, zero freezes paid-model inference, and usage at or above the limit throws `ApiKeyCreditLimitExceededError` (429). It deliberately does not reserve credits, so concurrent requests retain the existing possible overshoot behavior.

> **Deliberate cross-context dependency (iam → domain):** the credit guards read consumption through exported `domain/usage` use cases, so `QuotasModule` imports `UsageModule` and `CreditLimitsModule`. Nothing in either module's closure imports quotas, so the graph stays acyclic.
