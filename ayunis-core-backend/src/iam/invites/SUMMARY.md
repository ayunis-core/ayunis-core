User Invitations
Manages organization member invitations with email and token workflow.

Handles the full invitation lifecycle for onboarding users into organizations. Supports creating single and bulk invites, sending invitation emails with JWT tokens, accepting invites, resending expired invites, and deletion. Only tenant administrators may create invitations; the single-invite application flow also verifies the active user's role and organization before reserving a seat, so non-HTTP callers cannot bypass the policy.

This module manages how new users join existing organizations in Ayunis. The core entity is `Invite`, containing email, target org, assigned role (admin/manager/user), inviter reference, expiration date, and acceptance timestamp. Key use cases include `CreateInviteUseCase` and `CreateBulkInvitesUseCase` for issuing invitations, `SendInvitationEmailUseCase` for dispatching email with a signed JWT link, `AcceptInviteUseCase` for processing token-based acceptance and creating the user account, `ResendExpiredInviteUseCase` for refreshing expired invitations, `GetInvitesByOrgUseCase` for listing pending invites, and `GetInviteByTokenUseCase` for token validation. The public invite detail response includes the token-bound organization and its authentication policy so the acceptance page never infers routing from the invitee's email domain. For passwordless SSO admission, `FindPendingInviteByEmailAndOrgUseCase` resolves an exact pending invite and `AcceptPendingInviteUseCase` claims it inside the provisioning transaction. When an organization requires SSO, public password acceptance is rejected without consuming the invite, leaving it available for that federated admission path. Invite creation and password acceptance use the same organization lock as SSO admission and seat-count updates, so an invitation cannot be claimed concurrently by local and federated account creation. Password acceptance acquires the authentication-policy row before the seat-allocation lock, matching SSO admission and avoiding opposing database lock order. Password hashing happens before those locks; expiry and account conflicts are rechecked afterward. Bulk validation, capacity changes, and invite persistence commit before email delivery begins, so no network request holds the allocation lock or database transaction. `CountPendingInvitesByOrgIdUseCase` provides a context-free `COUNT(*)` boundary for capacity checks; pending invitations continue to reserve seats until accepted or deleted. It integrates with **users** for account creation upon acceptance, **orgs** for organization membership, and **authentication** for the invite JWT service. The `InvitesRepositoryPort` abstracts persistence with a local PostgreSQL implementation using TypeORM.
