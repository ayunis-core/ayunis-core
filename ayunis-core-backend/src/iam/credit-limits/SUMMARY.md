Credit Limits
Configurable per-user, per-team, and per-API-key monthly credit allowances enforced on top of the organization budget.

This module lets organization admins cap monthly credit consumption for individual users, shared team pools, and programmatic API keys. Limits apply only to usage-based subscriptions and supplement the organization-wide budget enforced by `CreditBudgetGuardService`.

The abstract, organization-scoped `CreditLimit` entity carries `monthlyCredits`; concrete `UserCreditLimit`, `TeamCreditLimit`, and `ApiKeyCreditLimit` subclasses own `userId`, `teamId`, and `apiKeyId` respectively. Subclass identity is the discriminant, making both/neither-target states unrepresentable in the domain. Persistence mirrors that model through TypeORM single-table inheritance (`CreditLimitRecord` plus one `@ChildEntity` per scope). Each target has a partial unique `(orgId, targetId)` index and a cascading foreign key, so every principal has at most one limit and deleting the target removes its policy. Presence of a row means capped, absence means unlimited within the organization budget, and `monthlyCredits === 0` freezes paid-model inference. Values use the same credit unit as `UsageBasedSubscription.monthlyCredits` and `usage.creditsConsumed`.

Scope-specific set use cases upsert while preserving row identity and reject negative or non-finite values. Scope-specific remove use cases are idempotent. Admin endpoints are `GET /credit-limits/{users|teams|api-keys}` and `PUT|DELETE /credit-limits/{users|teams|api-keys}/:targetId`; every management operation takes `orgId` from `ContextService`, requires `UserRole.ADMIN`, and requires a usage-based subscription. API-key target validation composes `ListApiKeysByOrgUseCase`, preventing an administrator from attaching policy to another organization's key.

Two application read models serve enforcement and administration. `ResolveCreditLimitsForUserUseCase` returns a user's personal limit and all current team limits; `ResolveCreditLimitForApiKeyUseCase` returns one key's optional limit. The user, team, and API-key overview use cases enrich configured limits with names and current UTC-month consumption. User and API-key overviews use batched usage reads; API-key names come from `ApiKeysModule.ListApiKeysByOrgUseCase`. Overview use cases accept an optional `since` bound for internal consumers, while HTTP uses the current calendar month.

Enforcement lives in **runs** because it combines IAM policy with domain usage. `InferenceUsageGuard.preflight()` checks the organization budget first, then delegates user principals to `CreditLimitGuardService` and API-key principals to `ApiKeyCreditLimitGuardService`. User enforcement is most-restrictive-wins across the personal limit and every team pool. API-key enforcement compares only that key's attributed usage. Both apply only to credit-consuming models and use the existing post-hoc threshold logic: usage at or above the limit returns 429, while an admitted request and concurrent requests may overshoot before asynchronous usage persistence completes. User fair-use quotas remain user-only and are still skipped for API keys.

Integrations: **teams** (membership and names), **users** (names), **api-keys** (target validation and names), **domain/usage** (single and batched consumption reads), and **domain/runs** (enforcement services). The frontend exposes API-key limit usage and management on the API Keys settings page only for usage-based subscriptions.

> **Deliberate cross-context dependency (iam → domain):** The three admin overview use cases inject exported `domain/usage` use cases to show live consumption, so `CreditLimitsModule` imports `UsageModule`. The dependency remains acyclic (`UsageModule` does not import this module). Enforcement keeps the conventional domain→iam direction: runs imports `CreditLimitsModule` and composes its exported resolver use cases.
