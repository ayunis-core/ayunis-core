SSO
Persists organization SSO configuration and links validated broker identities to Ayunis users.

See the repository-level [authentication architecture](../../../../docs/architecture/authentication.md)
for the end-to-end broker, admission, MFA, session, and logout paths.

Each organization can have one SSO connection with one or more globally unique verified email domains, their verification timestamps, an optional unique Zitadel organization ID, and an optional Zitadel identity provider ID. The domain collection is authoritative for exact routing; the legacy primary-domain columns remain a rollback-compatible mirror. Exact domain matching routes every configured domain to the same connection. The enabled flag is the runtime login switch and requires a broker organization mapping. JIT provisioning is an independent opt-in through `jitProvisioningEnabled`; invitations remain available regardless of that setting. Local password login remains enabled by default and can be disabled independently only while the SSO mapping is active and valid. A configured identity provider ID sends users directly to the customer IdP; connections without one retain the broker UI fallback.

Federated identities use the exact validated OIDC issuer and subject as their durable unique key and reference the internal Ayunis user. Organization and user deletion cascade to their corresponding SSO records. This module does not persist customer IdP credentials or the future self-service onboarding lifecycle.

`FederatedIdentitiesRepository` persists those mappings through the ambient transaction manager, allowing the provisioning phase to commit a user, its identity mapping, and invitation consumption as one unit. The database uniqueness constraint on `(issuer, subject)` remains the concurrency backstop.

`OidcBrokerClient` is the application port for OIDC authorization and callback validation. `ZitadelOidcBrokerClient` is its single relying-party adapter. It uses Authorization Code with PKCE, state, and nonce; pins the selected Zitadel organization and requests the configured customer IdP directly when present; validates the response through `openid-client`; loads profile claims from UserInfo; and keeps access tokens inside the adapter. The validated ID token crosses only into SSO application orchestration so its encrypted logout hint can be stored separately from identity data. Authorization requests carry the configured 24-hour `max_age`, and callback validation requires the signed `auth_time` to satisfy the same bound. The validated ID-token `amr` values cross the application boundary only as authentication evidence. Core skips its own MFA challenge only when ZITADEL explicitly asserts `mfa`; `otp` alone and missing or unrecognized methods do not satisfy the policy. Its environment values are optional as a group so local authentication remains available before SSO is configured.

`SsoLoginTransaction` stores a state hash, browser-binding hash, fixed post-login path, encrypted PKCE verifier and nonce, pinned Ayunis and Zitadel organization IDs, login or account-link purpose, optional linking user, and a ten-minute expiry. `SsoLoginTransactionsRepository` atomically consumes only a transaction matching both hashes, `SsoEncryptionPort` protects its secrets at rest, and `SsoLoginTransactionCleanupTask` removes expired records.

`SsoBrokerSessionService` stores one encrypted ID-token logout hint under the validated ZITADEL `sid`, separate from the user identity and Core refresh-token rows. The record covers the SSO reauthentication window plus the maximum pending-MFA delay, cascades with user deletion, and is removed after expiry by `SsoBrokerSessionCleanupTask`; access and refresh tokens are never persisted. Hint persistence is best-effort because legacy sessions already support interactive broker logout.

The login orchestration use cases discover an enabled connection from a validated email domain, start an organization-pinned broker authorization request, and complete only a matching one-time callback whose verified email domain and Zitadel organization match that connection. Existing accounts still require explicit authenticated linking while password login remains additive. Once an operator enforces SSO-only, the reviewed municipal IdP becomes authoritative and the first matching SSO login links the validated issuer-subject identity to the existing same-organization account, so enforcement does not strand users who have not linked yet. `CompleteSsoAuthenticationUseCase` owns callback validation, user admission, and the cross-module call to Authentication's session boundary; the HTTP controller only translates requests, cookies, and responses.

`SsoLoginController` (`presenters/http/`) serves `auth/sso/discover` for email-domain routing, `auth/sso/organizations/:orgId/start` for the organization-pinned authorization redirect, authenticated `auth/sso/link/start` for explicit account linking, and `auth/sso/oidc/callback` for both purpose-bound completions. Start responses are marked `Cache-Control: no-store` and set the short-lived host-prefixed correlation cookie the callback consumes and then clears. Discovery returns only availability, the routing organization ID, and whether local password login is allowed. Login completion enters Authentication's shared MFA-aware session boundary and sets either the normal Core cookies or the MFA-pending cookie while preserving the SSO source and Zitadel session ID. Link completion requires the same organization and exact verified email as the authenticated Core account and never creates a user or session. Successful login and account-link transactions return only their purpose-specific fixed frontend path; MFA and callback failures likewise redirect to fixed frontend routes with a stable error code rather than provider or internal messages.

Logout is backend-owned. The feature-independent `LogoutController` serves `auth/logout`, revokes the Core refresh-token family first, and returns a ZITADEL end-session URL only for an SSO-origin session; the frontend follows that URL when present and otherwise returns directly to local login. For new SSO sessions the URL carries the stored `id_token_hint`, allowing ZITADEL to terminate the exact broker session and return directly to Core. Existing sessions without a hint and unreadable hints retain the interactive ZITADEL fallback. The public `auth/sso/oidc/backchannel-logout` endpoint also remains available so ZITADEL can revoke sessions. It accepts ZITADEL's form-encoded logout token, verifies its signature, issuer, audience, expiry, issued-at time, required `jti`, event, and absence of nonce, then revokes the exact indexed `sid`. A signed subject fallback revokes only SSO sessions for its mapped user, preserving local password sessions. Unknown signed subjects and repeated notifications are idempotent.

`ProvisionOrgSsoUserUseCase` performs first-login admission in one transaction. Existing issuer/subject mappings retain their user and organization; passwordless invitations work independently of JIT and preserve USER, MANAGER, or ADMIN; unknown identities require JIT and receive USER after serialized seat admission. `SsoProvisioningLock`, implemented by `PostgresSsoProvisioningLock`, serializes issuer/subject and normalized-email admissions with transaction-scoped advisory locks. Existing local accounts require explicit linking while password login is additive; under SSO-only, the use case locks and re-reads the current policy, atomically marks the broker-matching Core email as verified, and only then creates the identity mapping. Cross-organization moves are rejected, and user creation, email verification, identity mapping, and invitation consumption roll back together. Canonical user-created and user-updated events are published only after the transaction commits.

`SsoConnectionPolicyModule` owns connection persistence and exports the authentication-policy use cases consumed by Authentication, Users, and Invites. `GetOrgAuthenticationPolicyUseCase` reads whether local password login is allowed; `SetOrgLocalPasswordLoginEnabledUseCase` changes that policy and revokes password-origin sessions when SSO-only is enforced. `ReviewedSsoMapping` captures the operator-reviewed domains and broker identifiers so a concurrent remap cannot activate an unseen policy. The module is an internal Nest composition boundary within SSO; its repository port is shared only with other SSO use cases.

`OrgSsoConnection` owns normalized connection state, including `localPasswordLoginEnabled`, which defaults to true so existing password users are unaffected. `OrgSsoConnectionsRepository` defines lookups, persistence, and conditional updates for routing and runtime flags. The Postgres adapter reports database constraint violations without deciding application conflicts and uses conditional writes to prevent stale operator changes from overwriting newer state.

For V1, reusable application use cases read and configure the verified domains, Zitadel organization, and optional direct-IdP hint in one write. Omitting the hint preserves it when the mapping is unchanged, explicit `null` clears it, and a remap without a hint drops the stale value. `SetOrgSsoIdpUseCase` independently changes that hint on an existing connection while password login remains available; an SSO-only organization must restore password login before changing its reviewed provider. New mappings are disabled by default, repeated configuration is idempotent, and an enabled mapping must be disabled before its routing configuration can change through the configure boundary. Separate use cases control runtime enablement, JIT provisioning, and local password login so Superadmin HTTP adapters and later automation can reuse the same boundary. Changing the password-login policy never requires disabling SSO. SSO disablement takes the connection mutation lock and is rejected while local passwords are disabled or any organization member has no password; SSO admission takes the corresponding shared lock and rechecks enablement before linking or creating a user.

When an unchanged disabled connection exists only in the rollback-compatible legacy columns, configuration materializes its canonical domain rows instead of returning early. Enablement requires those rows to exist. Public routing remains canonical-table-only, so stale legacy values cannot become active domains.

`SuperAdminSsoConnectionsController` (`presenters/http/`) is the operator surface over those use cases, serving `super-admin/orgs/:orgId/sso` for reading and configuring the mapping, `sso/idp` for direct-IdP routing, and `sso/enabled`, `sso/jit-provisioning`, and `sso/local-password-login` for independent runtime switches. Every route is restricted to `SystemRole.SUPER_ADMIN`; this is not a customer-admin surface. Request DTOs enforce the shared email-domain and Zitadel identifier patterns and require an explicit domain-verification acknowledgement. Enforcing SSO-only requires confirmation carrying the reviewed domains, Zitadel organization, and nullable direct-IdP hint, so a concurrent remap cannot activate a policy the operator never saw. It atomically changes the policy and revokes password-origin refresh sessions; re-enabling password login preserves existing hashes. `OrgSsoConnectionResponseDtoMapper` (`presenters/http/mappers/`) projects a connection to its non-secret representation, so no customer IdP credential, broker token, or duplicated IdP type crosses the boundary. Each mutation emits a structured audit log naming the acting superadmin, the organization, the operation, the reviewed mapping where one applies, and the authoritative resulting state; password-policy changes include non-secret before and after values.
