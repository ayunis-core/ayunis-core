Organization Management
Creates, updates, deletes, and queries multi-tenant organization entities.

Manages organizations as the top-level multi-tenancy boundary in Ayunis. Supports CRUD operations, super-admin listing of all organizations, and lookup by ID. Each user belongs to exactly one organization.

This module defines the `Org` entity—the fundamental tenant unit containing a name, associated users, and timestamps. Key use cases include `CreateOrgUseCase` (provisions a new organization and seeds its default role permissions in one transaction, whether called during registration or directly by a super-admin), `UpdateOrgUseCase` (renames an organization; rejects a blank name and persists through `OrgsRepository.updateName`, a targeted `UPDATE ... RETURNING` — saving a mapped `OrgRecord` would cascade over the `users` relation), `DeleteOrgUseCase` (removes an organization and cascades cleanup), `AdmitOrgProcessingUseCase` (takes a short lifecycle read lock before a queue worker begins organisation-scoped work), `FindOrgByIdUseCase` (single org lookup), `FindAllOrgIdsUseCase` (batch ID retrieval), and `SuperAdminGetAllOrgsUseCase` (paginated listing for platform administration). The HTTP layer includes a `SuperAdminOrgsController` for admin-only endpoints (create, paginated list, lookup by ID, and rename via `PATCH /super-admin/orgs/:id`).

Domain events are defined in `application/events/`: `OrgCreatedEvent` (emitted by `CreateOrgUseCase` whenever a new organization is created — during registration or via super-admin — and includes the `Org` entity) and `OrgDeletionRequestedEvent` (emitted by `DeleteOrgUseCase` _before_ the org row is deleted, carrying the `orgId`; listeners must not act irreversibly but register cleanup via `deferCleanup` — see the deletion cascade contract below). The event class exposes a static `EVENT_NAME` string for type-safe listener registration.

It integrates with **users** (each user references an orgId), **subscriptions** and **trials** (org-scoped billing), **invites** (org-scoped invitations), **teams** (org-scoped team grouping), **permissions** (`OrgsModule` imports `PermissionsModule` so `CreateOrgUseCase` can seed the new org's default role grants inline), and **authentication** (org creation during registration). The `OrgsRepositoryPort` abstracts persistence with a PostgreSQL implementation.

**Deletion cascade contract.** `DeleteOrgUseCase` holds an organisation lifecycle write lock across listener preflight and a single `DELETE` on the `orgs` row, then relies entirely on PostgreSQL `ON DELETE CASCADE` foreign keys for relational cleanup. The lock serializes with `AdmitOrgProcessingUseCase`, which takes the corresponding lifecycle read lock after BullMQ marks a job active and permits work only while the organisation still exists. The locks are released before processing or external cleanup begins. Every org-scoped table therefore MUST declare a `@ManyToOne(() => OrgRecord, { onDelete: 'CASCADE' })` (directly, or transitively through a parent that cascades from the org). Conversation data cascades through `users` (`threads.userId → users`, then messages/artifacts/assignments via `threadId`); knowledge-base data cascades through `knowledge_bases.orgId → orgs`, then `sources.knowledgeBaseId → knowledge_bases` and the RAG parent/child chunks below sources; MCP data cascades through `mcp_integrations.orgId → orgs`. When adding a new org-scoped table, wire its cascade here — a plain `orgId`/`userId` column without an FK silently orphans data on org deletion (a data-protection defect). Note that cascades cover relational rows and pgvector embeddings (all in Postgres) but NOT external blob storage (uploaded files, generated images, letterhead PDFs), which live in MinIO. To close that gap `DeleteOrgUseCase` follows the two-phase cleanup contract (`DeferredCleanupEvent` in `src/common/events/`): it emits `OrgDeletionRequestedEvent` before the row delete, the storage module's `StorageOrgDeletionRequestedListener` defers a `PurgeOrgStorageUseCase` run (sweeping every object under `<orgId>/`, `generated-images/<orgId>/`, `letterheads/<orgId>/`), and the use case executes the deferred purge only after the row transaction commits. A failed delete therefore never leaves a surviving org with its blobs already gone. Internal callers use best-effort cleanup and log purge failures; super-admin deletion requires complete cleanup and throws an incomplete-cleanup error if any deferred task fails after row deletion. Neither mode can roll back the deleted rows when external cleanup fails.

**Archive and super-admin deletion (AYC-35).** `SetOrgArchivedUseCase` updates `archived` and increments `sessionVersion` only on active-to-archived transitions, then revokes all organisation refresh sessions in the same transaction. Archive and restore never replace membership relations. `AssertOrgActiveUseCase` guards password/SSO/MFA issuance and lifecycle writes; `AssertCachedOrgActiveUseCase` guards JWT and API-key requests; access tokens include the organisation session generation. Restore allows fresh sessions without reviving pre-archive tokens. Shared lifecycle row locks serialize session issuance and queue enqueueing against archive/deletion. Organisation-scoped uploads avoid holding a database connection during object-store I/O: they check the active lifecycle generation before and after the upload, then remove the late object if archive or deletion won the race.

`SuperAdminOrgLifecycleController` exposes `PATCH /super-admin/orgs/:id/archive` and name-confirmed `DELETE /super-admin/orgs/:id`. Both controller and use cases enforce super-admin access. Listing defaults to active organisations and accepts `status=active|archived|all`. Deletion accepts active or archived organisations, validates the current exact name, and uses a conditional SQL delete to protect concurrent renames. Active document-processing jobs reject deletion with `ORG_PROCESSING_ACTIVE` before any rows are removed. Deferred cleanup removes MinIO prefixes and retained processing queue payloads; super-admin deletion awaits all cleanup and reports incomplete cleanup instead of success on failure. PostgreSQL and external stores cannot roll back together: rows are already gone if external cleanup fails, and the orphan storage sweep remains the recovery safety net.

**Request authentication cache.** JWT and API-key strategies use `AssertCachedOrgActiveUseCase`: successful active organisation generations are cached in memory per backend instance for a fixed 30 seconds, shared across that organisation’s users. Token generations are compared on every JWT request; a newer token generation forces an authoritative reread so fresh post-restore sessions work immediately. Failures are not cached. Concurrent misses share a read, expiry starts before the read, and the cache is bounded to 1,000 entries. Existing credentials may pass the organisation gate for up to 30 seconds after archive or deletion. Login (password/SSO/MFA), refresh, uploads and queue enqueueing continue using the authoritative `AssertOrgActiveUseCase`; lifecycle locks never use cached state. API-key validity and expiry are still checked on each request.
