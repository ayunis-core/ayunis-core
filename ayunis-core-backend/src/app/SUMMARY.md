Application Bootstrap
Root NestJS module wiring all domain modules and infrastructure together.

The app module is the application entry point. It imports and configures all domain modules (models, agents, threads, runs, messages, tools, prompts, sources, RAG, retrievers, storage, MCP, usage, transcriptions, shares, knowledge-bases, artifacts, letterheads), IAM, scheduling, static file serving, CLS transactional support, structured Pino logging, metrics, and all configuration modules. It also provides the health check and cloud-detection endpoints.

The `AppModule` is the root NestJS module that composes the entire application. It loads all configuration via `ConfigModule.forRoot()` with numerous config factories (models, auth, typeorm, embeddings, storage, web, app, admin, legal, subscriptions, emails, internet-search, MCP, tools). Database connectivity uses `TypeOrmModule.forRootAsync()` with the shared `dataSource`. Request-scoped context is initialized via `ClsModule.forRoot()` with `ClsPluginTransactional` for TypeORM transaction propagation. `LoggingModule` installs the shared Pino configuration; bootstrap buffers framework logs, calls `installNestLogger` to point Nest's `Logger` at the Pino adapter, and flushes the buffer before startup continues. `ScheduleModule` is included for cron jobs; AppSignal monitoring is bootstrapped outside the module graph via `--require ./appsignal.cjs`; after `app.listen` succeeds, bootstrap starts the continuous `backend_process` process-monitor heartbeat. Public `AppController` endpoints include `GET /` for deployment/registration status, `GET /health`, and `GET /feature-toggles` for the current user-facing feature toggle states. Middleware (`AppsignalNamespaceMiddleware`, `CookieParserMiddleware`, `SecurityHeadersMiddleware`) is applied globally. `serveSurfaces` registers static builds after the controllers, from `dist/frontend/<surface-id>`. Only web gets a client-route fallback. Other prefixes return 404 for missing files or when their flag is off. All surface HTML is `Cache-Control: no-store` and uses the registry's framing policy. Outlook's task pane and events documents add the configured Outlook origins, while the sign-in dialog and the two explicit web sign-in routes stay self-framed. A surface framing policy can resolve approved origins asynchronously for each request.

`SubscriptionSyncModule` is registered after IAM so its internal sync dependencies do not change public OpenAPI discovery order. Its controller is excluded from public API generation.
