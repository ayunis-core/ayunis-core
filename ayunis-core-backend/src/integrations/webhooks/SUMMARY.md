Event Webhooks
Deliver lifecycle webhook events to external systems via HTTP.

The webhooks module dispatches domain lifecycle and product events (user, org, subscription and add-on changes; usage and chat activity; skill and integration usage/installs; onboarding progress; academy progress) to a configured external URL. Webhook dispatch is triggered by `WebhookDispatchListener`, which subscribes to domain events emitted by use cases — no domain or IAM code imports from this module directly.

**Key files:**

- `webhooks.module.ts` — NestJS module wiring. Registers `SendWebhookUseCase`, `WebhookHandler` port/adapter binding, and `WebhookDispatchListener`. Imports `UsersModule` for `FindUserByIdUseCase` and `OrgsModule` for `FindOrgByIdUseCase` (payload enrichment). Implements `OnModuleInit` to validate at boot time that `WEBHOOK_SIGNING_SECRET` is present when a webhook URL is configured in production (fails loud); outside production a warning is logged instead. Depends on `ConfigService` for reading app configuration.
- `listeners/webhook-dispatch.listener.ts` — Central listener that subscribes to domain events (`UserCreatedEvent`, `InviteCreatedEvent`, `UserUpdatedEvent`, `UserDeletedEvent`, `OrgCreatedEvent`, subscription events, `UsageCollectedEvent`, `MonthlyCreditsSnapshotEvent`, `UserMessageCreatedEvent`, `SkillUsedEvent`, `ToolUsedEvent`, marketplace install events, `OnboardingUpdatedEvent`, `AcademyProgressUpdatedEvent`, `AddonActivatedEvent`, `AddonDeactivatedEvent`) and dispatches them as webhook HTTP calls via `SendWebhookUseCase`. `InviteCreatedEvent` becomes a distinct `user.invited` webhook so Startdeliver can create pending invitees without triggering sinks that handle real account creation, such as Brevo onboarding. Subscription webhooks are sequenced per organization so replacement cancellation reaches the receiver before replacement creation. `SubscriptionExpiredEvent` becomes `subscription.expired` when the subscriptions module's daily sweep finds a fixed term that ran out without a cancellation; every subscription payload carries `endsAt` so receivers can also see the planned end on `subscription.created`. Usage events that need a Startdeliver user identity, including `chat.sent`, `onboarding.updated`, and `academy.progress_updated`, are enriched via `FindUserByIdUseCase`; `user.created` is enriched with a best-effort `orgName` via `FindOrgByIdUseCase` (AYC-445, consumed by the Brevo onboarding sink). Enrichment lookups are skipped when no webhook URL is configured. Non-idempotent credit webhooks are attempted once; daily monthly snapshots provide omission recovery instead of blind retries.
- `application/use-cases/send-webhook/send-webhook.use-case.ts` — Receives a `SendWebhookCommand` and delegates to the `WebhookHandler` port.
- `application/ports/webhook.handler.ts` — Abstract port defining the webhook delivery contract.
- `infrastructure/http/http-webhook.handler.ts` — Infrastructure adapter that performs the actual HTTP POST to the configured webhook URL. Signs outbound payloads with HMAC-SHA256 when `WEBHOOK_SIGNING_SECRET` is configured, producing a Stripe-style `X-Webhook-Signature` header (`t=<unix_seconds>,v1=<hex>`). Uses `ConfigService` to read the webhook URL and signing secret.
- `infrastructure/services/webhook-delivery-sequencer.service.ts` — Maintains per-organization promise chains for subscription webhook delivery and drains outstanding chains during graceful shutdown.
- `domain/webhook-event.entity.ts` — Abstract `WebhookEvent` entity with UUID, event type enum, data payload, and timestamp. Concrete event types cover organization, user, subscription lifecycle, usage, chat, skill/integration product activity, academy progress, and add-ons.

**Architecture:**

Use cases emit domain events → `WebhookDispatchListener` handles them → constructs `WebhookEvent` subclasses → calls `SendWebhookUseCase` → `HttpWebhookHandler` delivers via HTTP POST (with HMAC-SHA256 signature when a signing secret is available). This decouples business logic from webhook infrastructure. Domain and IAM modules have no dependency on webhook code.

**Error handling:** Ordinary lifecycle and activity listeners log delivery failures without re-throwing, so webhook issues cannot disrupt user-facing operations. Expiry delivery propagates failures to the subscription sweep, which retries uncommitted expiries on a later run; `SubscriptionExpiredWebhookEvent` uses the subscription ID as its stable event ID so receivers can deduplicate retries. The scheduled monthly credit snapshot also propagates delivery failures to the reconciliation task so its AppSignal check-in fails and a later run can retry from the durable ledger.

Add-on payloads allow `actorUserId: null` for service-originated External subscription synchronization; manual changes still identify their super admin.

External subscription synchronization applies local domain effects transactionally under `runWithDeferredWebhookDelivery`;
the listener suppresses immediate HTTP dispatch only for the specific queued event objects. Unrelated nested events and parallel flows are unaffected. The context is private to the webhook application layer. Its outbox calls
`DeliverBillingWebhookUseCase` with a stable event ID/timestamp. That use case maps
billing events through `application/mappers`, propagates HTTP failures to the retry
owner, and does not replay domain listeners. Legacy event delivery remains best effort.

Wire event names and JSON payload schemas are owned by `@ayunis-core/connect-sdk` in `packages/core-connect-sdk`. JSON-only event payload types are inferred from that package through type-only imports; the only runtime import is the event-name constant from the package's Zod-free `event-types` entry, so the backend does not load Zod. The HTTP adapter signs and sends the serialized envelope without validating it; the SDK's fixture specs and Connect's receive-side parsing cover the wire shape. Producer fixtures instantiate every concrete webhook event and are distributed with the package for Connect compatibility checks.

Webhook producers bind a literal event name to the SDK-inferred payload type. User and organization mappers build explicit JSON data (ISO dates and an empty legacy password field); domain entities are never delivered directly. Payload serialization runs once before network retries, while signature timestamps are refreshed for each attempt.

IAM owns the pending-event types and the class-validator shape readers for subscriptions and add-ons. The webhook application combines the types as `PendingBillingEvent` and keys the readers by persisted event name in `persisted-billing-event.validation.ts`. Persisted entries expose `{ name: string; event: unknown }` until delivery validates the name, payload shape, access model, dates and organization consistency. Invalid data raises `INVALID_PERSISTED_BILLING_EVENT` before any HTTP attempt. Class prototypes are not required after V8 deserialization; the shapes describe event data, not behavior. Failure handling and ordered recovery belong to the subscription-sync outbox.
