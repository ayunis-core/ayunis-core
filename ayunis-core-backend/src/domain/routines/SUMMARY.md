Routines
Prompts that run unattended on a user's behalf and record how each run ended

A routine is a user-owned prompt that runs without anyone watching. Each execution creates a routine thread and runs the routine profile from the runs module on it; the outcome is stored on the routine as its last run status.

The `Routine` entity belongs to one user (`userId`, FK with ON DELETE CASCADE, so deleting a user deletes their routines) and their organization (`orgId`, CASCADE). It carries `name`, `prompt` (the task, sent as the run's first user message), `modelId` (a permitted model id; ON DELETE SET NULL, after which runs fall back to the owner's default model), `dailyTime` (`HH:mm`, Europe/Berlin), `internetEnabled`, `enabled`, and the run bookkeeping `lastRunStatus` (`queued` / `running` / `succeeded` / `failed`, null before the first run), `lastRunAt` (when the last run finished), `lastRunFailureReason` (an application error code, `timeout` or `finish_routine_not_called`) and `consecutiveFailureCount` (reset on success). There is no schedule yet: `dailyTime` and `enabled` are stored for the daily sweep that a later change adds; `enabled` does not affect Run now.

All routines endpoints (`/routines`) sit behind the `routines` feature flag (`FEATURE_ROUTINES_ENABLED`, default off; disabled → 404) and the academy certificate gate, like chat. CRUD is owner-scoped: every read and write filters by the current user, so another user's routine is indistinguishable from a missing one (`ROUTINE_NOT_FOUND`, 404). `CreateRoutineUseCase` and `UpdateRoutineUseCase` check a chosen model against the user's effective grants through `RoutineModelService` (models module's `GetPermittedLanguageModelUseCase`); an omitted model on create resolves to the user's default (`GetDefaultModelUseCase`) and is stored explicitly. Updates write only the definition fields in one `UPDATE … RETURNING`, so an edit never overwrites the status of a run that finishes meanwhile.

`POST /routines/:id/run` (`RunRoutineNowUseCase`, also behind `@RequireSubscription()`) marks the routine `queued` and adds a job to the `routine-execution` BullMQ queue (`RoutineExecutionProducer` behind the `RoutineExecutionQueue` port). Jobs run once (`attempts: 1` — a retry would execute the routine again with new credits and a new thread) and are deduplicated per routine while one is waiting or running, so repeated clicks queue one run. If enqueuing fails, the previous status is restored.

`RoutineExecutionConsumer` (concurrency `ROUTINES_WORKER_CONCURRENCY`, default 2) starts its worker only when the flag is on, so an instance with routines disabled takes no jobs. Each job calls `ExecuteRoutineUseCase`, which loads the routine and its owner (skipping if either is gone), sets the owner's full user context through `UserContextRunner`, marks the routine `running`, and then executes it as a chat message would run: a locked owner fails the run (`ROUTINE_OWNER_LOCKED`); `RoutineSubscriptionGate` applies the send-message subscription gate (active subscription, else trial messages left, consuming one trial message per execution through `IncrementTrialMessagesUseCase`; nudges do not count again); `CreateThreadUseCase` creates a routine thread (`type = routine`, `routineId`, title "<name> – <dd.MM.yyyy>" in Berlin time, never generated) and re-checks model access; `ExecuteUnattendedRunUseCase` runs the routine profile with the routine's name and internet toggle under an `AbortSignal.timeout` of `ROUTINES_RUN_TIMEOUT_MINUTES` (default 15). `done` records success, `failed` records the policy's reason, `aborted` records `timeout`, and any thrown error records its code. Expected failures (application errors below 500) complete the job; others are recorded and rethrown so the queue reports them. The queue is registered with queue inspection (Bull Board) and queue telemetry like the source processing queues.

The module imports threads, runs, models, users, subscriptions and trials and calls only their exported use cases.
