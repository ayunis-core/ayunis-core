Routines
Prompts that run unattended on a user's behalf and record how each run ended

A routine is a user-owned prompt that runs without anyone watching. Each execution creates a routine thread and runs the routine profile from the runs module on it; the outcome is stored on the routine as its last run status. While it runs, the owner can watch the execution live in the routine thread through the runs module's active runs, but cannot stop it there.

The `Routine` entity belongs to one user (`userId`, FK with ON DELETE CASCADE, so deleting a user deletes their routines) and their organization (`orgId`, CASCADE). It carries `name`, `prompt` (the task, sent as the run's first user message), `modelId` (a permitted model id, or null for the owner's default model, resolved at run time so runs follow later changes of it; ON DELETE SET NULL, so a removed model also falls back to the default), `mode` (`auto` / `max`, or null; stored instead of a model and resolved for each run, so runs follow the mode's list; a check constraint allows at most one of `modelId` and `mode`, migration `AddModeToRoutines`), `schedule` (see below), `internetAccess` (`off` / `all` / `allowlist`), `allowedDomains` (normalized hosts, applied only in `allowlist` mode and kept while another mode is set), `mcpIntegrationIds` (the integrations whose tools its runs may use; join table `routine_mcp_integrations`), `knowledgeBaseIds` (personal knowledge bases its runs may query; join table `routine_knowledge_bases`; both join tables CASCADE on both sides, so a deleted integration or knowledge base drops out of the routine and a deleted routine loses its links), `enabled`, and the run bookkeeping `lastRunStatus` (`queued` / `running` / `succeeded` / `failed` / `skipped`, null before the first run), `lastRunAt` (when the last run finished), `lastRunFailureReason` (why the last run failed: an application error code such as `ROUTINE_INTEGRATION_UNAVAILABLE`, `timeout`, `interrupted` or `finish_routine_not_called`; or why it was skipped: `permission_missing`), `consecutiveFailureCount` (reset on success), `lastRunStartedAt`, `nextRunAt` and `pausedAt`. The record also keeps `recentExecutionKeys` (the last 10 queue job ids whose run started, newest first), which only persistence uses. `enabled` governs only the schedule; Run now works on a disabled routine too.

**Schedule** (`domain/routine-frequency.ts`): a `RoutineSchedule` is `daily`, `weekly` with ISO `weekdays` (1 = Monday to 7 = Sunday, at least one, stored ascending and deduplicated) or `monthly` with a `monthDay` (1–28, so no month is too short, or `last`), each with a `time` (`HH:mm`, Europe/Berlin); a strict subset of RRULE (FREQ=DAILY, FREQ=WEEKLY;BYDAY, FREQ=MONTHLY;BYMONTHDAY=n or -1), so a calendar export can convert it. `routineSchedule` checks a received schedule and reports the first problem as a field (`frequency`, `time`, `weekdays`, `monthDay`) and a reason (`invalid`, `required` for missing weekdays or month day, `not-allowed` for a field of another frequency, `null` included). `RoutineScheduleDto` applies it per field with the reason as the class-validator constraint, so requests get a `VALIDATION_ERROR` on e.g. `schedule.weekdays` (400); the use cases apply it again (`ROUTINE_INVALID_SCHEDULE`, 400) and store the normalized schedule. It is persisted in the columns `frequency` (enum, default `daily`), `dailyTime` (the time, named from when routines only ran daily), `weekdays` (`smallint[]`, empty unless weekly) and `monthDay` (`smallint`, -1 for the last day, null unless monthly); writing a schedule always writes all four, so a changed frequency leaves none of the previous one's fields. The `AddWeeklyAndMonthlySchedulesToRoutines` migration turned every existing routine into `daily` at its time and kept its `nextRunAt`; its down migration drops the new columns, which makes every routine daily again. Computation (`domain/routine-schedule.ts`, pure functions of an explicit `now`): a routine runs at its time on every Berlin date the schedule matches (`matchesRoutineSchedule`; `nextRoutineRunAt` checks one candidate day after another from yesterday on, at most 62) plus a start offset of 0–9 minutes derived from its id (`routineStartOffsetMinutes`), so routines that share a time do not all start at once. A time skipped by the switch to summer time runs an hour later; a time repeated by the switch back runs at its first occurrence. `nextRunAt` (timestamptz, indexed) is the next start; it is null while the routine is disabled. Create sets it for an enabled routine; routines created before the column existed were marked as missed by the `ScheduleExistingRoutines` data migration, so the first sweep schedules them. `UpdateRoutineUseCase` reads the routine with a row lock (`findByIdForUpdate`, inside `@Transactional()`) and applies `scheduleChangesForEdit`: disabling clears `nextRunAt`; re-enabling schedules the next run and resets `consecutiveFailureCount` and `pausedAt`; any change to the schedule (time, frequency, weekdays or month day; `sameRoutineSchedule`) reschedules an enabled routine; saving the same schedule keeps a pending run.

**Sweep**: `RoutineSweepConsumer` registers a BullMQ job scheduler (`sweep-due-routines`, every minute, on its own `routine-sweep` queue so sweeps never wait behind runs) and starts its worker, both only when the flag is on. The scheduler adds one job per minute for all replicas together, and one worker takes it. Each job runs `SweepDueRoutinesUseCase`: it first fails runs still `running` more than `ROUTINES_RUN_TIMEOUT_MINUTES` + 5 minutes after `lastRunStartedAt` (reason `interrupted`; their worker died), then reads up to 500 enabled routines with `nextRunAt <= now` (earliest first). For each, it moves `nextRunAt` to the next start with a conditional write (`moveNextRunAt`, `WHERE "nextRunAt" = <seen>`), so of two overlapping sweeps only one acts on a due run. A run due earlier the same Berlin day is caught up and enqueued with job id `routine-<id>-<YYYY-MM-DD>-<HHmm>` (the scheduled start in Berlin time; BullMQ ignores a repeated add while that job is kept, and ids may not contain `:`); a run due on an earlier day is skipped. Each scheduled start runs once; a time changed to later the same day is a new start and runs that day. If enqueuing fails, `nextRunAt` is moved back and the sweep fails, so the next sweep retries.

**Failures and pause**: `recordRunOutcome` (Run now and scheduled runs alike) resets the failure count on success, increments it on failure and leaves it unchanged on a skip; the failure that reaches 3 (`ROUTINE_PAUSE_AFTER_FAILURES`) on an enabled routine also sets `enabled = false`, `nextRunAt = null` and `pausedAt` in the same `UPDATE` and reports `paused`. Interrupted runs are counted the same way. Only re-enabling clears `pausedAt`.

**Error notifications**: every recorded failure (a failed or thrown run, a Run now job that could not start, and an interrupted run the sweep fails) posts a `routine_error` notification to the owner's inbox through `RoutineFailureNotifier` (notifications module's `CreateNotificationUseCase`). Its text (`domain/routine-failure-notification.ts`) is German, like the backend's emails: the headline names the routine ("… fehlgeschlagen", or "… pausiert" when this failure paused it), the subheadline gives the reason in the routines page's wording, and a paused routine's body says it was paused after 3 failed runs in a row and links to the routines page to switch it back on. The notification links the run's routine thread when the run got that far; interrupted runs have none, since the routine does not keep its runs' threads. Skips post nothing, and a scheduled job that fails before its run starts is left to its retry without a notification. Posting is best effort: a failure to post is logged and never fails the run's bookkeeping. Nothing is posted with the `routines` flag off.

All routines endpoints (`/routines`) sit behind the `routines` feature flag (`FEATURE_ROUTINES_ENABLED`, default off; disabled → 404), the academy certificate gate, like chat, and the `manage_routines` permission (`@RequirePermission` on the controller, 403 without it; listing and reading too, since they only serve routine management). Global guards run before the controller's feature guard, so with the flag off a caller without the permission gets 403 rather than 404, as with the academy and subscription gates. Routine threads stay readable through the threads module without the permission. CRUD is owner-scoped: every read and write filters by the current user, so another user's routine is indistinguishable from a missing one (`ROUTINE_NOT_FOUND`, 404). `CreateRoutineUseCase` and `UpdateRoutineUseCase` check a chosen model against the user's effective grants through `RoutineModelService` (models module's `GetPermittedLanguageModelUseCase`); a chosen mode must resolve for the user now, to a regular or anonymous-only permit, as when a chat starts in it (`ResolveModelModesUseCase`; else `ROUTINE_MODEL_MODE_UNAVAILABLE`, 422); a model and a mode together are `ROUTINE_CONFLICTING_MODEL_SELECTION` (400). Choosing the user's default (neither on create, both null on update) checks that a default resolves (`GetDefaultModelUseCase`) and stores neither. On update a sent `modelId` or `mode` replaces the choice as a whole, so choosing one clears the other; omitting both keeps it. `POST /routines` takes `name`, `prompt`, `schedule` and optionally `modelId` or `mode`, `internetAccess` (default `off`), `allowedDomains` and `enabled` (default on); `PATCH /routines/:id` changes only the sent configuration fields and `enabled`; a sent `schedule` replaces the stored one as a whole, an omitted one keeps it, and `null` is rejected. **Internet access** (`domain/routine-internet-access.ts`): `routineInternetSettings` normalizes and deduplicates the allowed domains with the retrievers module's `normalizeAllowedDomain` (lowercase ASCII host, scheme, path, port and query removed; IP addresses, wildcards and hosts without a dot rejected), allows at most 20 (Staan's `include_domains` limit) and needs at least one in `allowlist` mode; a violation is `ROUTINE_INVALID_ALLOWED_DOMAINS` (400, metadata `reason` `required` / `too-many` / `ip-address` / `wildcard` / `missing-dot` / `invalid` and the `domain`). An update checks the mode and the list together as they will be stored, so an omitted one keeps its stored value (switching to `allowlist` works with the domains the routine already has). The migrations `AddInternetAccessAndKnowledgeBasesToRoutines`, `BackfillRoutineInternetAccess` (former `internetEnabled` true → `all`, false → `off`; its down migration turns every mode but `off` back into internet on) and `RemoveInternetEnabledFromRoutines` replaced the former boolean. Updates write only the definition fields, so an edit never overwrites the status of a run that finishes meanwhile.

**Integrations and knowledge bases** are set through their own endpoints, each switch on the routine page saving on its own: `GET /routines/:id/mcp-integrations` and `POST` / `DELETE /routines/:id/mcp-integrations/:integrationId` (`RoutineMcpIntegrationsController`), `GET /routines/:id/knowledge-bases` and `POST` / `DELETE /routines/:id/knowledge-bases/:knowledgeBaseId` (`RoutineKnowledgeBasesController`), with the same flag, academy and permission guards and owner scope as `/routines` (POST and DELETE answer 204). Adding reads the routine with a row lock, so it cannot be deleted before the link is written, and inserts the link with `ON CONFLICT DO NOTHING`, so adding one twice changes nothing; removing always works. `RoutineIntegrationService.assertAddable` admits an integration that is enabled in the org and connected for the user (`ListAvailableMcpIntegrationsUseCase`, `userAuthorized`), else `ROUTINE_INTEGRATION_UNAVAILABLE` (422); one the routine already has is accepted without the check, and the list includes integrations that are no longer usable, so the page can show them for switching off (the run fails until then). `RoutineKnowledgeBaseService` admits a personal knowledge base the user can access, their own or shared with them (knowledge-bases module's `FindAccessibleKnowledgeBaseUseCase`), else `KNOWLEDGE_BASE_NOT_FOUND` (404); team, organization and workspace knowledge bases are refused the same way. A knowledge base whose access was lost counts as removed: the list (`FindAccessibleKnowledgeBasesByIdsUseCase`, then `GetAccessibleKnowledgeBaseContextsUseCase` for the response) and the run get only the accessible ones, the link stays, and the knowledge base is back once access is granted again.

**Task improver**: `POST /routines/improve-prompt` (`ImproveRoutinePromptUseCase`) rewrites a draft task (`prompt`, with the optional `name` as context) into one that can run unattended: a goal sentence, numbered steps, decisions the assistant can take alone, and when to notify; it keeps the author's facts, restrictions and bracketed placeholders and adds no new ones. Nothing is persisted. It works like the skills module's text improver: the optional `language` (`en` or `de`) is the fallback for draft text without an identifiable language; `RoutineModelService.forPromptImprovement` picks the organization default model first and never an anonymous-only one (anonymized placeholders would end up in the stored task), failing with `ROUTINE_PROMPT_IMPROVEMENT_UNAVAILABLE` (422) when every permitted model is anonymous-only and passing `NO_DEFAULT_MODEL_FOUND` through; besides the controller's guards it requires a subscription or trial messages left (`@RequireSubscription()`), and a rewrite admitted on trial capacity consumes one trial message (fire-and-forget); admission goes through the quotas module's `InferenceAdmissionGuard` and the tokens used are recorded through the usage module's `CollectUsageAsyncService` before the answer is handed out (a paid call without reported usage, or whose usage cannot be stored, fails). An answer that is empty after stripping surrounding quotes fails with `ROUTINE_PROMPT_IMPROVEMENT_FAILED` (502) instead of clearing the field.

`POST /routines/:id/run` (`RunRoutineNowUseCase`, also behind `@RequireSubscription()`) marks the routine `queued` and adds a job to the `routine-execution` BullMQ queue (`RoutineExecutionProducer` behind the `RoutineExecutionQueue` port). Run now jobs get one attempt; their failure is recorded and the user can run again. Scheduled jobs get 3 attempts with backoff, since the sweep has already moved `nextRunAt` on and a job failing before its run starts would otherwise lose the day's run. Retries never execute a routine twice: the worker claims each job's run once (`markRunStarted` prepends the job id to `recentExecutionKeys` in the same conditional `UPDATE`, only if it is not there yet; Run now jobs get a random job id, so keys never repeat even when Redis loses its data). A scheduled job that fails before its run starts (owner lookup, claim) records nothing and is left to the retry, so retries do not count as consecutive failures; a Run now job records the failure so it does not stay shown as queued. Run now jobs are deduplicated per routine while one is waiting or running, so repeated clicks queue one run; a Run now and the same day's scheduled run are separate jobs. If enqueuing fails, the previous status is restored.

`RoutineExecutionConsumer` (concurrency `ROUTINES_WORKER_CONCURRENCY`, default 2) starts its worker only when the flag is on, so an instance with routines disabled takes no jobs. A stalled job (its worker died) is delivered again: it runs if its run had not started and is skipped otherwise, in which case the sweep records the run left `running` as `interrupted`. Each job calls `ExecuteRoutineUseCase` with its trigger (`run_now` / `scheduled`), which loads the routine and its owner (skipping if either is gone), sets the owner's full user context through `UserContextRunner`, claims the run and marks the routine `running` from now (skipped when this job's run already started, or for a scheduled run whose routine was disabled after it was queued), and then executes it as a chat message would run. Scheduled runs have no request, so the global academy certificate and subscription guards cannot apply; the worker applies both itself, for every run: a locked owner fails the run (`ROUTINE_OWNER_LOCKED`); an owner whose role lacks `manage_routines` (permissions module's `HasPermissionUseCase`; admins always hold it) is skipped (`skipped`, reason `permission_missing`): nothing runs, no trial message is consumed, and the failure count and pause are untouched, so the routine resumes on its next scheduled start once the permission is granted again; `RoutineAcademyGate` applies the academy certificate rule (academy-access module's `EvaluateAcademyAccessUseCase`; `ACADEMY_CERTIFICATE_REQUIRED`); `RoutineIntegrationService.assertUsable` fails the run (`ROUTINE_INTEGRATION_UNAVAILABLE`) when a selected integration is no longer enabled, no longer connected for the owner, or its capability discovery fails (server unreachable), before any trial message is consumed, so a run never quietly goes ahead without a tool it was set up to use; `RoutineSubscriptionGate` applies the send-message subscription gate (active subscription, else trial messages left, consuming one trial message per execution through `IncrementTrialMessagesUseCase`; nudges do not count again); `CreateThreadUseCase` creates a routine thread (origin `routine` with the routine's id, title "<name> – <dd.MM.yyyy>" in Berlin time, never generated) and re-checks model access, or binds the model the routine's mode resolves to now and records the mode on the thread (a mode that resolves to nothing fails the run with `MODEL_MODE_UNAVAILABLE`, explained like a model that is no longer available); the thread is created with the routine's integrations and the knowledge bases the owner can still access (`CreateThreadCommand.mcpIntegrationIds` and `knowledgeBaseIds`, stored like ones a chat adds directly), so a chat continuing the routine thread keeps them and a revoked share neither fails the run nor reaches it; `ExecuteUnattendedRunUseCase` runs the routine profile with the routine's name, internet on for `all` and `allowlist`, and the allowed domains in `allowlist` mode under an `AbortSignal.timeout` of `ROUTINES_RUN_TIMEOUT_MINUTES` (default 15). `done` records success, `failed` records the policy's reason, `aborted` records `timeout`, and any thrown error records its code. Expected failures (application errors below 500) complete the job; others are recorded and rethrown so the queue reports them. The execution queue is registered with queue inspection (Bull Board) and queue telemetry like the source processing queues; the sweep queue with queue inspection.

The routine profile offers the web tools by internet access (none for `off`, unrestricted for `all`, limited to the allowed domains for `allowlist`; the org's internet setting still overrides), the routine thread's integrations and knowledge bases (never the user's activated ones), and `send_notification` (tools module), so a run can post up to 3 notifications of its own per execution (nudges included); the premade Verkündungsplattform prompt tells the model to send one notification with a summary and links to the original documents when something relevant was published, and to finish without one otherwise.

**Chat widgets**: the runs module's chat profile offers `create_routine` and `edit_routine` widgets (see the runs module). `FindManageableRoutinesUseCase`, the module's only export, lists the current user's routines for them and returns null where the routines endpoints would refuse the user (flag off, no user context, no `manage_routines`), so the chat offers no routine widgets. The widgets show the configuration fields, the schedule included, and save through `POST /routines` and `PATCH /routines/:id` like the routines page; integrations and knowledge bases are set on the routine page only. A routine created from the chat stores the `create_routine` tool call it came from (`sourceToolCallId`, unique per user), so a reloaded chat shows the proposal as created, and a second create from the same proposal fails with `ROUTINE_ALREADY_CREATED` (409).

The module imports threads, runs (through `forwardRef`, as runs imports routines for the chat widgets), models, mcp, knowledge bases, users, subscriptions, trials, quotas, usage, academy access, permissions and notifications and calls only their exported use cases.
