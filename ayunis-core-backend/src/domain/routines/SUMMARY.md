Routines
Prompts that run unattended on a user's behalf and record how each run ended

A routine is a user-owned prompt that runs without anyone watching. Each execution creates a routine thread and runs the routine profile from the runs module on it; the outcome is stored on the routine as its last run status.

The `Routine` entity belongs to one user (`userId`, FK with ON DELETE CASCADE, so deleting a user deletes their routines) and their organization (`orgId`, CASCADE). It carries `name`, `prompt` (the task, sent as the run's first user message), `modelId` (a permitted model id; ON DELETE SET NULL, after which runs fall back to the owner's default model), `dailyTime` (`HH:mm`, Europe/Berlin), `internetEnabled`, `enabled`, and the run bookkeeping `lastRunStatus` (`queued` / `running` / `succeeded` / `failed` / `skipped`, null before the first run), `lastRunAt` (when the last run finished), `lastRunFailureReason` (why the last run failed: an application error code, `timeout`, `interrupted` or `finish_routine_not_called`; or why it was skipped: `permission_missing`), `consecutiveFailureCount` (reset on success), `lastRunStartedAt`, `nextRunAt` and `pausedAt`. The record also keeps `recentExecutionKeys` (the last 10 queue job ids whose run started, newest first), which only persistence uses. `enabled` governs only the daily schedule; Run now works on a disabled routine too.

**Schedule** (`domain/routine-schedule.ts`, pure functions of an explicit `now`): a routine runs daily at `dailyTime` in Europe/Berlin plus a start offset of 0–9 minutes derived from its id (`routineStartOffsetMinutes`), so routines that share a time do not all start at once. A time skipped by the switch to summer time runs an hour later; a time repeated by the switch back runs at its first occurrence. `nextRunAt` (timestamptz, indexed) is the next start; it is null while the routine is disabled. Create sets it for an enabled routine; routines created before the column existed were marked as missed by the `ScheduleExistingRoutines` data migration, so the first sweep schedules them. `UpdateRoutineUseCase` reads the routine with a row lock (`findByIdForUpdate`, inside `@Transactional()`) and applies `scheduleChangesForEdit`: disabling clears `nextRunAt`; re-enabling schedules the next run and resets `consecutiveFailureCount` and `pausedAt`; a changed time reschedules an enabled routine; saving the same time keeps a pending run.

**Sweep**: `RoutineSweepConsumer` registers a BullMQ job scheduler (`sweep-due-routines`, every minute, on its own `routine-sweep` queue so sweeps never wait behind runs) and starts its worker, both only when the flag is on. The scheduler adds one job per minute for all replicas together, and one worker takes it. Each job runs `SweepDueRoutinesUseCase`: it first fails runs still `running` more than `ROUTINES_RUN_TIMEOUT_MINUTES` + 5 minutes after `lastRunStartedAt` (reason `interrupted`; their worker died), then reads up to 500 enabled routines with `nextRunAt <= now` (earliest first). For each, it moves `nextRunAt` to the next start with a conditional write (`moveNextRunAt`, `WHERE "nextRunAt" = <seen>`), so of two overlapping sweeps only one acts on a due run. A run due earlier the same Berlin day is caught up and enqueued with job id `routine-<id>-<YYYY-MM-DD>-<HHmm>` (the scheduled start in Berlin time; BullMQ ignores a repeated add while that job is kept, and ids may not contain `:`); a run due on an earlier day is skipped. Each scheduled start runs once; a time changed to later the same day is a new start and runs that day. If enqueuing fails, `nextRunAt` is moved back and the sweep fails, so the next sweep retries.

**Failures and pause**: `recordRunOutcome` (Run now and scheduled runs alike) resets the failure count on success, increments it on failure and leaves it unchanged on a skip; the failure that reaches 3 (`ROUTINE_PAUSE_AFTER_FAILURES`) on an enabled routine also sets `enabled = false`, `nextRunAt = null` and `pausedAt` in the same `UPDATE` and reports `paused`. Interrupted runs are counted the same way. Only re-enabling clears `pausedAt`.

**Error notifications**: every recorded failure (a failed or thrown run, a Run now job that could not start, and an interrupted run the sweep fails) posts a `routine_error` notification to the owner's inbox through `RoutineFailureNotifier` (notifications module's `CreateNotificationUseCase`). Its text (`domain/routine-failure-notification.ts`) is German, like the backend's emails: the headline names the routine ("… fehlgeschlagen", or "… pausiert" when this failure paused it), the subheadline gives the reason in the routines page's wording, and a paused routine's body says it was paused after 3 failed runs in a row and links to the routines page to switch it back on. The notification links the run's routine thread when the run got that far; interrupted runs have none, since the routine does not keep its runs' threads. Skips post nothing, and a scheduled job that fails before its run starts is left to its retry without a notification. Posting is best effort: a failure to post is logged and never fails the run's bookkeeping. Nothing is posted with the `routines` flag off.

All routines endpoints (`/routines`) sit behind the `routines` feature flag (`FEATURE_ROUTINES_ENABLED`, default off; disabled → 404), the academy certificate gate, like chat, and the `manage_routines` permission (`@RequirePermission` on the controller, 403 without it; listing and reading too, since they only serve routine management). Global guards run before the controller's feature guard, so with the flag off a caller without the permission gets 403 rather than 404, as with the academy and subscription gates. Routine threads stay readable through the threads module without the permission. CRUD is owner-scoped: every read and write filters by the current user, so another user's routine is indistinguishable from a missing one (`ROUTINE_NOT_FOUND`, 404). `CreateRoutineUseCase` and `UpdateRoutineUseCase` check a chosen model against the user's effective grants through `RoutineModelService` (models module's `GetPermittedLanguageModelUseCase`); an omitted model on create resolves to the user's default (`GetDefaultModelUseCase`) and is stored explicitly. Updates write only the definition fields in one `UPDATE … RETURNING`, so an edit never overwrites the status of a run that finishes meanwhile.

`POST /routines/:id/run` (`RunRoutineNowUseCase`, also behind `@RequireSubscription()`) marks the routine `queued` and adds a job to the `routine-execution` BullMQ queue (`RoutineExecutionProducer` behind the `RoutineExecutionQueue` port). Run now jobs get one attempt; their failure is recorded and the user can run again. Scheduled jobs get 3 attempts with backoff, since the sweep has already moved `nextRunAt` on and a job failing before its run starts would otherwise lose the day's run. Retries never execute a routine twice: the worker claims each job's run once (`markRunStarted` prepends the job id to `recentExecutionKeys` in the same conditional `UPDATE`, only if it is not there yet; Run now jobs get a random job id, so keys never repeat even when Redis loses its data). A scheduled job that fails before its run starts (owner lookup, claim) records nothing and is left to the retry, so retries do not count as consecutive failures; a Run now job records the failure so it does not stay shown as queued. Run now jobs are deduplicated per routine while one is waiting or running, so repeated clicks queue one run; a Run now and the same day's scheduled run are separate jobs. If enqueuing fails, the previous status is restored.

`RoutineExecutionConsumer` (concurrency `ROUTINES_WORKER_CONCURRENCY`, default 2) starts its worker only when the flag is on, so an instance with routines disabled takes no jobs. A stalled job (its worker died) is delivered again: it runs if its run had not started and is skipped otherwise, in which case the sweep records the run left `running` as `interrupted`. Each job calls `ExecuteRoutineUseCase` with its trigger (`run_now` / `scheduled`), which loads the routine and its owner (skipping if either is gone), sets the owner's full user context through `UserContextRunner`, claims the run and marks the routine `running` from now (skipped when this job's run already started, or for a scheduled run whose routine was disabled after it was queued), and then executes it as a chat message would run. Scheduled runs have no request, so the global academy certificate and subscription guards cannot apply; the worker applies both itself, for every run: a locked owner fails the run (`ROUTINE_OWNER_LOCKED`); an owner whose role lacks `manage_routines` (permissions module's `HasPermissionUseCase`; admins always hold it) is skipped (`skipped`, reason `permission_missing`): nothing runs, no trial message is consumed, and the failure count and pause are untouched, so the routine resumes on its next scheduled start once the permission is granted again; `RoutineAcademyGate` applies the academy certificate rule (academy-access module's `EvaluateAcademyAccessUseCase`; `ACADEMY_CERTIFICATE_REQUIRED`); `RoutineSubscriptionGate` applies the send-message subscription gate (active subscription, else trial messages left, consuming one trial message per execution through `IncrementTrialMessagesUseCase`; nudges do not count again); `CreateThreadUseCase` creates a routine thread (`type = routine`, `routineId`, title "<name> – <dd.MM.yyyy>" in Berlin time, never generated) and re-checks model access; `ExecuteUnattendedRunUseCase` runs the routine profile with the routine's name and internet toggle under an `AbortSignal.timeout` of `ROUTINES_RUN_TIMEOUT_MINUTES` (default 15). `done` records success, `failed` records the policy's reason, `aborted` records `timeout`, and any thrown error records its code. Expected failures (application errors below 500) complete the job; others are recorded and rethrown so the queue reports them. The execution queue is registered with queue inspection (Bull Board) and queue telemetry like the source processing queues; the sweep queue with queue inspection.

The routine profile offers `send_notification` (tools module), so a run can post up to 3 notifications of its own per execution (nudges included); the premade Verkündungsplattform prompt tells the model to send one notification with a summary and links to the original documents when something relevant was published, and to finish without one otherwise.

The module imports threads, runs, models, users, subscriptions, trials, academy access, permissions and notifications and calls only their exported use cases.
