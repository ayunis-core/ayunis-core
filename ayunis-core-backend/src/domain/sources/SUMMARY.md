Data Sources
External data sources for RAG context enrichment

Sources manage user-uploaded files, URLs, and text content that feed the RAG pipeline. Each source is chunked, indexed, and made available for semantic search during AI conversations. Sources may optionally belong to a knowledge base via the `knowledgeBaseId` foreign key column.

Source citation reads use `FindSourceCitationTargetUseCase`, backed by a single joined repository query that returns the exact persisted content chunk and its owning text-source metadata without loading the full extracted source text. The use case intentionally performs no caller authorization; consuming modules must establish their own access boundary before exposing the result.

Processing failures persist a nullable `processingErrorCode` alongside the existing diagnostic text. Codes are classified from typed exceptions, not their messages; unknown failures use `PROCESSING_FAILED`. Successful status transitions clear the code, and legacy rows remain unclassified rather than guessing from stored text.

The sources module manages external data that enriches AI context through RAG. The abstract `Source` entity specializes into `TextSource` (direct text with URL or content) and `DataSource` (uploaded files with storage references); `UrlSource` further specializes `TextSource` with a `maxDepth` property controlling how many levels of same-site links are crawled. `TextSourceContentChunk` represents indexed content fragments. Each source has an optional `knowledgeBaseId` foreign key linking it to a knowledge base collection; when a knowledge base is deleted its sources are removed with it (`onDelete: CASCADE`, see the AddOrgCascadeToConversationKbMcpData migration). Key use cases include creating text and data sources, creating processing sources (for async document pipelines), creating processing URL sources and crawling them asynchronously (`CreateProcessingUrlSourceUseCase`, `EnqueueUrlCrawlUseCase`), marking sources as failed, querying several text sources with several queries in one semantic search (`QueryTextSourceUseCase` rejects the whole query with `SourceNotFoundError` when any requested source is missing, then returns at most ten matching chunks per query and twenty overall, in ranked order and tagged with the queries that matched), retrieving source details, deleting sources (single or bulk), and finding unreferenced source IDs (`FindUnreferencedSourceIdsUseCase` — accepts candidate IDs via `FindUnreferencedSourceIdsQuery` and returns the subset not attached to any skill or knowledge base, used by cross-module cleanup flows; candidate ids are looked up in chunks so the bind-parameter count stays bounded) and deleting whichever of a set of candidates is unreferenced (`DeleteUnreferencedSourcesUseCase`, the deferred step the threads and skills user-deletion listeners run once the owning rows are gone). A source counts as referenced while a knowledge base, a skill or a thread assignment points at it (`findUnreferencedIds`); only the stale-thread sweep passes `ignoreThreadAssignments`, because its candidates are thread-assigned by construction and every one of those assignments is already proven stale. If that deferred step fails there is no row left to retry from, so `OrphanedSourcesSweepTask` (nightly at 2:45, `SweepOrphanedSourcesUseCase`, `SourceRepository.findOrphanedIds`) deletes sources that no thread assignment, skill or knowledge base has reached for 30 days; the org for the processing-prefix purge is read from the retained original's key and left out when there is none (`DeleteSourcesCommand.orgId` may be null). CSV/spreadsheet uploads are processed asynchronously like documents: `StartDataSourceProcessingUseCase` reads only the workbook's data-sheet names in-request (first-row-only parse that skips empty sheets; zero data sheets → `EmptyFileDataError`), invokes the command's optional `ensureCapacityFor(sourceCount)` callback so the caller can reject an over-capacity workbook with its own limit error while rejection is still free, pre-creates one PROCESSING `CSVDataSource` per data sheet (single sheet → `<base>.csv`, multi-sheet → `<base>_<Sheet_Name>.csv`), stashes the raw file in MinIO, and enqueues one job on the `data-source-processing` BullMQ queue; `DataSourceProcessingConsumer` downloads the file, parses it via `SpreadsheetParserPort` — implemented by `PiscinaSpreadsheetParserAdapter`, which runs the CPU-bound parse in a piscina worker-thread pool (max 2 threads, idle shutdown, 60s abort timeout → `SpreadsheetParseTimeoutError`; malformed, corrupt, encrypted, and unsupported workbook containers → `UnprocessableSpreadsheetError` 422 with a stable parser reason and the original cause retained internally; shared via `SpreadsheetParsingModule` since the BullMQ worker runs in the API process) — fills each source's `data` and CAS-flips it PROCESSING→READY via guarded UPDATEs only (`refreshProcessingHeartbeat`, `updateCsvSourceData` — never `save()`, whose upsert would resurrect a concurrently deleted row); sheets the full parse drops (used range with only blank cells) and final-attempt failures are marked FAILED with a `processingError`, and the MinIO object is removed afterwards. Classified provider failures increment the shared `provider_unavailable_count` AppSignal counter only when the queue settles the operation as failed, never on retryable attempts. The async pipeline uses `DocumentProcessingPort` (application port) implemented by `DocumentProcessingProducer` (BullMQ adapter) to enqueue jobs; the port also exposes `cancelJob()` for best-effort cancellation of waiting or active jobs. The `DocumentProcessingConsumer` processes jobs asynchronously (download from MinIO → extract text → chunk → index → update status). Its `SourceProcessingHeartbeatService` renews the existing guarded heartbeat once per minute while downloading and extracting, including long-running email attachments. Each job owns its timer; writes never overlap, deleted or non-PROCESSING sources stop renewal, refresh errors are logged and retried, and completion drains any in-flight write before saving a freshly re-read source. The email attachment time budget limits starting more work, rather than imposing a hard cancellation deadline; CSV/XLSX/XLS/ODS uploads from knowledge bases take this pipeline instead of the data-source one: the consumer parses them via `SpreadsheetParserPort` and `tableToText` flattens each row to `Header: value | ...` (one `## Sheet` section per sheet for workbooks) into a single text source, rejecting tables without rows with `EmptyFileDataError`. A parallel URL-crawl pipeline (`UrlCrawlModule`) uses `UrlCrawlProcessingPort` implemented by `UrlCrawlProducer` (BullMQ adapter, also exposing `cancelJob()`); the `UrlCrawlConsumer` crawls a root URL up to `maxDepth` levels of same-site links, translates each page's local chunk offsets into the concatenated source text's global coordinates, and indexes the chunks via the shared `SourceProcessingHelper` service (also used by `DocumentProcessingConsumer` for failure-marking and partial-index cleanup); it heartbeats through `refreshProcessingHeartbeat` and persists content with `saveProcessingTextSourceContent`, whose conditional update cannot recreate a deleted source or overwrite a terminal status. `StaleProcessingCleanupTask` runs a cron job every 5 minutes to mark sources stuck in PROCESSING for >15 minutes as FAILED (bounded batches, oldest first, with an in-flight guard against overlapping runs). `CleanupSourceProcessingUseCase` takes source ids plus an explicit org id, cancels both the document-processing and URL-crawl pipelines best-effort, and purges the `<orgId>/processing/<sourceId>/` prefixes via the storage module. It is used by direct source deletion and deferred deletion cleanup without relying on request context, including after owning rows are already cascade-deleted. The `SourceRepository` joins the ambient CLS transaction for related source, detail, and chunk reads and writes; it provides `findStaleProcessingSourceIds()` for stale-source cleanup, `updateStatusConditionally()` for atomic status transitions guarded by an expected current status, and `findUnreferencedIds()` which returns the subset of candidate IDs that are older than a given threshold and not attached to any knowledge base or skill. Sources track their creator (user or system) and support assignment to both agents and threads. The module integrates with **rag** for content ingestion and vector indexing, **retrievers** for extracting text from files and URLs, **storage** for file persistence in MinIO, **models** for requiring a permitted embedding model before document processing is enqueued (`StartDocumentProcessingUseCase` calls `GetPermittedEmbeddingModelUseCase` so unprovisioned orgs fail fast instead of after OCR), **agents** for source assignment to AI assistants, **threads** for per-conversation source attachment enabling contextual document queries, and **knowledge-bases** for grouping sources into named document collections.

CSV cell data is normalized by `SourceMapper.toStoredCsvData` on every write to the jsonb `data` column — the full `save()` used by uploads, code-execution results, and MCP resources, and the processing `updateCsvSourceData` update alike — via the shared `toWellFormedText` helper: NUL is dropped and unpaired UTF-16 surrogates become U+FFFD (PostgreSQL rejects both with 22P05), while valid Unicode including non-BMP characters is preserved.

**Organisation deletion.** Processing producers hold a shared organisation lifecycle row lock while enqueueing, preventing job creation after the owning organisation is deleted. Once BullMQ marks a job active, each consumer takes the same short-lived read lock before doing work. Deletion holds the matching write lock across active-job preflight and the row delete: a job admitted first is visible as active and rejects deletion, while a later job waits and then skips work after seeing that the organisation is gone. No database lock or transaction remains open during document processing. `OrgProcessingDeletionListener` uses unsuppressed Nest event errors for the rejection, cursor-scans stable job hashes with at most 100 job records loaded at once, and removes retained target jobs in batches after the row delete. A late active job that was denied admission gets a bounded removal retry; other locked jobs or Redis failures surface as incomplete cleanup.

**Queue telemetry.** All three consumers wrap each attempt in `observeJob` (`infrastructure/queue/job-telemetry.ts`), which tags the trace with queue, attempt, wait/processing seconds and UUID identifiers, and records `bullmq_queue_wait_seconds`/`bullmq_processing_seconds` distributions. `classifyJobFailure` increments `bullmq_retry_count` or `bullmq_terminal_failure_count` once per failed attempt; failures thrown before classification are counted by `observeJob`. Pipeline steps run inside `processingStage` child spans. Telemetry errors are swallowed so they never replace a job's result or failure. Queue-depth gauges live in the `queue-telemetry` integration.

Knowledge-base URL crawls register discovered PDFs as independent `FileSource` entries (AYC-1031). The nullable `FileSource.url` uses the existing source URL column and flows through the existing citation projection to the dialog. The collection is assigned before enqueueing. After guarded HTML content persistence and indexing, a transaction marks the URL source ready and registers all PDFs with empty details; only the winning delivery processes the files, so retries cannot duplicate or recreate deleted files. Registration respects the remaining knowledge-base capacity and serializes PDF registrations per collection. PDF extraction/indexing runs sequentially, while all registered files are heartbeated, including those waiting their turn. Per-file failures use a guarded processing-to-failed update with a typed error code, preserving HTML readiness; terminal provider failures retain their existing metric. A worker interrupted after registration leaves visible processing files for the existing stale-source cleanup to mark failed. Files have no parent-source relationship and survive deletion of the URL source.

If atomic crawl completion loses after HTML indexing, the PDF handoff re-reads source state and purges vectors only when the source is missing or not READY; a duplicate delivery preserves the ready winner’s index.

**Retained originals (AYC-1541).** `Source.storageKey` keeps the key of a stored original while the source exists. Jobs queued with `retainFile: true` are read through `StoredSourceFileService`, which re-checks the stored size against the job's `expectedSize`, binds the GET response to the job's `expectedETag` and caps the read at the verified size; a mismatch removes the object and fails the source with `STORED_FILE_MISMATCH`. Recordings, PDFs and office documents are not buffered: the consumer streams them into a temporary file with the same size and ETag bounds (`readRetainedToFile`, hashing on the way) and hands the path to the retriever; recordings go under the transcription temp directory. Text-like formats keep the in-memory read (`readRetained`). Consumers never delete retained files, the PDF page preflight runs in `DocumentProcessingConsumer` before OCR, and `CleanupSourceProcessingUseCase` releases a key after deletion only when `SourceRepository.findReferencedStorageKeys` shows no source still points at it (sheet sources share one file; `sources.storageKey` is indexed for that lookup). A retained job is read through `readRetained` or `readRetainedToFile`, which refuse to touch the object unless both the verified size and ETag travelled with the job, and a body that outgrows the verified size mid-download is removed like the other mismatches. Because the release runs after the source row is gone, a failed delete has no retry anchor, and a delete that runs inside a caller's transaction (`RemoveDocumentFromKnowledgeBaseUseCase`, `DeletePermittedModelUseCase`) skips the release because its commit happens after the use case returns; `UnreferencedOriginalsSweepTask` (nightly at 2:30, `SweepUnreferencedOriginalsUseCase`) lists every object under `*/uploads/*` older than eight days, which is past the session retention, and removes those no source references.

**Embedding during extraction (AYC-1813).** `DocumentProcessingConsumer` starts an `EarlyEmbeddingSession` per job and passes its `appendPages` through the processing context’s `onPagesExtracted` callback. The batched PDF OCR reports page texts in document order as soon as every earlier page is read; the handle cuts the text read so far with the same `SOURCE_CHUNKING` settings and, once a blank line fixes the splitter's top-level separator, asks `PrepareContentEmbeddingsUseCase` for the vectors of every chunk but the last, each once. The finished text is still cut and saved as before and `SourceProcessingHelper.index` passes the vectors on, so ingestion reuses vectors only when their model identity matches the current catalog ID, provider, model name and dimensions; a chunk that turned out different is simply embedded at the end. The session never fails a job, is finished exactly once before a failed extraction propagates so nothing of an attempt runs into its retry, and does nothing unless `INGESTION_EARLY_EMBEDDING=true` (default off).

**Documents from disk (AYC-1729).** `DocumentProcessingConsumer` stages PDFs, office documents and recordings in a temporary directory (`StoredSourceFileService.readToFile` / `readRetainedToFile`) and hands the retriever a `LocalFile` (path, size, sha256) instead of bytes, so memory per job no longer grows with the file. Text-like formats (TXT, CSV, spreadsheets, emails) are still read whole. The directory is removed when the job ends, whatever the outcome. Everything a job stages, including the PDF batches qpdf writes, sits in one directory per job that is removed when the job ends (`staging-directory.ts`); a running job refreshes its directory's timestamp every ten minutes, so a `download-*` directory untouched for six hours belongs to a process that was stopped mid-job and is removed when the next job stages a file; nothing else in the root is ever deleted, since `AUDIO_TEMP_DIRECTORY` may point at a shared directory.

**Direct upload sessions (AYC-1541).** Source files reach object storage straight from the browser. A target module authorises the target and checks its source capacity, then `CreateSourceUploadSessionUseCase` validates type and size against the caller's limit (recordings against `AUDIO_MAX_UPLOAD_BYTES` from `transcriptionConfig` and PDFs against `PDF_MAX_UPLOAD_BYTES` from `sourceUploadConfig` instead, so `SourcesModule` imports both configs; the legacy multipart-form endpoints keep the 25 MiB limit for every type), requires an active organisation and (for the document pipeline) a permitted embedding model, and persists a `SourceUploadSession` (`source_upload_sessions`) with a server-chosen key `<orgId>/uploads/<sessionId>/<file>`; files above `SOURCE_UPLOAD_MULTIPART_THRESHOLD_BYTES` are flagged `multipart`. `SourceUploadsController` exposes `POST /source-uploads/:id/sign`, where `SignSourceUploadRequestUseCase` signs exactly one S3 request on the session's key for its owner with the exact `Content-Length` — a whole-object `PUT` for single-request sessions; initiate (`POST ?uploads`), part (`PUT ?uploadId&partNumber`), list (`GET`), complete (`POST`) and abort (`DELETE`) for multipart ones — recording the browser's multipart upload id on the session, and `DELETE /source-uploads/:id` aborts a pending session; `SourceUploadSessionAccessService` reports sessions of other users or organisations as not found. `SourceUploadQueueingService` queues the job(s) of a session whose sources exist with `retainFile: true` and marks it `COMPLETED`; a failure leaves `SOURCES_CREATED` for a retry. `SourceUploadSweepTask` runs `SweepSourceUploadSessionsUseCase` every 5 minutes: expired `PENDING` sessions are marked `EXPIRED` and their parts/object discarded, `SOURCES_CREATED` sessions older than a minute are re-queued, multipart uploads under `*/uploads/` that no pending session claims under that upload id are aborted, and finished sessions age out after 7 days, retrying object deletion for `ABORTED`/`EXPIRED` sessions first and keeping the record when it fails.

Upload sessions survive user deletion with a null user reference. The five-minute sweep cancels unfinished ownerless sessions and retries storage cleanup in rotating batches. Cleanup records remain until organisation deletion: an in-flight PUT can finish even after its signature expires. Completed/source-backed files remain owned by sources. Retry and ordinary retention queries exclude ownerless sessions before applying their batch limits.

**Direct upload completion (AYC-1541).** `CompleteSourceUploadUseCase` (exported for the target modules) verifies the stored object's size, keeps its ETag on the session, plans the sources (one `FileSource` for documents and knowledge-base tables, one `CSVDataSource` per data sheet for thread/skill workbooks, which reads the workbook once in-request), lets the caller enforce its capacity for that count, claims the session with a guarded `PENDING→SOURCES_CREATED` update and attaches newly created sources to the target in the same transaction through the caller's `attach` callback, so attachment failure rolls back the sources, assignments and session state; concurrent or repeated calls create and attach sources exactly once and replays return the committed sources. After commit the queueing service queues the jobs; a queueing failure leaves `SOURCES_CREATED` and the next completion call or the sweep retries it.

**Direct upload targets (AYC-1541).** Completion lives on the target: `POST /threads|skills|knowledge-bases/:id/uploads` reserves a session after the target authorised the caller and checked its source capacity, and `POST .../uploads/:uploadId/complete` runs `CompleteSourceUploadUseCase` with the target's capacity check and attachment callback. The legacy multipart-form endpoints (`POST .../sources/file`, `POST .../documents`) remain for API clients and stage files under `<orgId>/processing/`.

**Direct upload outcome metric (AYC-1772).** `recordSourceUploadOutcome` (`application/util/source-upload-telemetry.helper.ts`) increments the AppSignal counter `source_upload_session_count` with three tags: `outcome` (`created`, `completed`, `aborted`, `expired`), `target_type` (`thread`, `skill`, `knowledge_base`) and `multipart` (`true`, `false`). No user, organisation, file name or storage key is tagged. `created` is counted once the session is saved. The end outcomes are counted only where a guarded transition out of `PENDING` was won, so a session contributes one `created` and at most one end outcome however often a request is replayed: `completed` when a completion claims the session (`PENDING→SOURCES_CREATED`, counted after the transaction so a failed attachment counts nothing; the later `COMPLETED` flip by the queueing service is not an upload outcome), `aborted` when the owner's browser aborts (it does so for a cancel and for any failed transfer or completion), when completion finds mismatched bytes, or when the sweep cancels a deleted user's pending session, and `expired` when the sweep or a completion past the deadline ends an abandoned session, which is up to `SOURCE_UPLOAD_SESSION_TTL_MS` (2 h) plus one sweep interval after `created`. A pending session removed with its organisation gets no end outcome. The call is a no-op while AppSignal is inactive and swallows its own errors.

`ProcessingCheckpointService` supplies the document consumer's extraction context. JSON results are keyed by organization, source and input identity under `<orgId>/processing/<sourceId>/results/`, with bounded reads and source lifecycle checks before and after writes. Completed OCR batches and audio parts survive retry and restart (`TranscribeRecordingUseCase` reads and writes the same context). Results are removed on success, terminal failure, settled-source skips and source deletion while uploaded originals remain retained. Final document content uses `saveProcessingTextSourceContent` so deletion cannot race an upsert and recreate the source. BullMQ progress records completed extraction units.

Queue consumers are registered by `IngestionConsumersModule` in `src/app` (process composition, not part of this module), separate from the queue modules that only register a queue and its producer port. The API imports it through `ConditionalModule` unless `INGESTION_IN_API=false`; with that setting it keeps producers and scheduled cleanup (`StaleProcessingCleanupTask` is a `SourcesModule` provider) but works through no queue. The headless `src/ingestion-worker.ts` entry point always imports it through `IngestionWorkerModule`, with configurable concurrency, no scheduler and no migration runner (`BaseModule.forWorker()`), and needs no ingestion setting of its own.

Thread upload sessions may reserve storage before a thread exists (`targetId = null`). Completion binds the owned session to one authorized thread in the existing guarded claim transaction; concurrent claims for another thread are rejected. `GetSourceProcessingProgressUseCase` exposes actual BullMQ stages and completed extraction units through a port; callers must authorize the owning resource before supplying sources. Persisted ready/failed status takes precedence over queue progress.
