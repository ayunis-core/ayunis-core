Data Sources
External data sources for RAG context enrichment

Sources manage user-uploaded files, URLs, and text content that feed the RAG pipeline. Each source is chunked, indexed, and made available for semantic search during AI conversations. Sources may optionally belong to a knowledge base via the `knowledgeBaseId` foreign key column.

The sources module manages external data that enriches AI context through RAG. The abstract `Source` entity specializes into `TextSource` (direct text with URL or content) and `DataSource` (uploaded files with storage references); `UrlSource` further specializes `TextSource` with a `maxDepth` property controlling how many levels of same-site links are crawled. `TextSourceContentChunk` represents indexed content fragments. Each source has an optional `knowledgeBaseId` foreign key linking it to a knowledge base collection; when a knowledge base is deleted its sources are removed with it (`onDelete: CASCADE`, see the AddOrgCascadeToConversationKbMcpData migration). Key use cases include creating text and data sources, creating processing sources (for async document pipelines), creating processing URL sources and crawling them asynchronously (`CreateProcessingUrlSourceUseCase`, `EnqueueUrlCrawlUseCase`, `StartUrlCrawlUseCase`), marking sources as failed, querying text sources semantically, retrieving source details, deleting sources (single or bulk), and finding unreferenced source IDs (`FindUnreferencedSourceIdsUseCase` — accepts candidate IDs via `FindUnreferencedSourceIdsQuery` and returns the subset not attached to any skill, agent, or knowledge base, used by cross-module cleanup flows). CSV/spreadsheet uploads are processed asynchronously like documents: `StartDataSourceProcessingUseCase` reads only the workbook's data-sheet names in-request (first-row-only parse that skips empty sheets; zero data sheets → `EmptyFileDataError`), invokes the command's optional `ensureCapacityFor(sourceCount)` callback so the caller can reject an over-capacity workbook with its own limit error while rejection is still free, pre-creates one PROCESSING `CSVDataSource` per data sheet (single sheet → `<base>.csv`, multi-sheet → `<base>_<Sheet_Name>.csv`), stashes the raw file in MinIO, and enqueues one job on the `data-source-processing` BullMQ queue; `DataSourceProcessingConsumer` downloads the file, parses it via `SpreadsheetParserPort` — implemented by `PiscinaSpreadsheetParserAdapter`, which runs the CPU-bound parse in a piscina worker-thread pool (max 2 threads, idle shutdown, 60s abort timeout → `SpreadsheetParseTimeoutError`, shared via `SpreadsheetParsingModule` since the BullMQ worker runs in the API process) — fills each source's `data` and CAS-flips it PROCESSING→READY via guarded UPDATEs only (`refreshProcessingHeartbeat`, `updateCsvSourceData` — never `save()`, whose upsert would resurrect a concurrently deleted row); sheets the full parse drops (used range with only blank cells) and final-attempt failures are marked FAILED with a `processingError`, and the MinIO object is removed afterwards. Classified provider failures increment the shared `provider_unavailable_count` AppSignal counter only when the queue settles the operation as failed, never on retryable attempts. Reading a data source's `data` before it is READY is rejected with `SourceNotReadyError` (409). The async pipeline uses `DocumentProcessingPort` (application port) implemented by `DocumentProcessingProducer` (BullMQ adapter) to enqueue jobs; the port also exposes `cancelJob()` for best-effort cancellation of waiting or active jobs. The `DocumentProcessingConsumer` processes jobs asynchronously (download from MinIO → extract text → chunk → index → update status). A parallel URL-crawl pipeline (`UrlCrawlModule`) uses `UrlCrawlProcessingPort` implemented by `UrlCrawlProducer` (BullMQ adapter, also exposing `cancelJob()`); the `UrlCrawlConsumer` crawls a root URL up to `maxDepth` levels of same-site links and indexes each page's chunks via the shared `SourceProcessingHelper` service (also used by `DocumentProcessingConsumer` for failure-marking and partial-index cleanup). `StaleProcessingCleanupTask` runs a cron job every 5 minutes to mark sources stuck in PROCESSING for >15 minutes as FAILED (bounded batches, oldest first, with an in-flight guard against overlapping runs). `CleanupSourceProcessingUseCase` takes source ids plus an explicit org id, cancels both the document-processing and URL-crawl pipelines best-effort, and purges the `<orgId>/processing/<sourceId>/` prefixes via the storage module. It is used by direct source deletion and deferred deletion cleanup without relying on request context, including after owning rows are already cascade-deleted. The `SourceRepository` joins the ambient CLS transaction for related source, detail, and chunk reads and writes; it provides `findStaleProcessingSourceIds()` for stale-source cleanup, `updateStatusConditionally()` for atomic status transitions guarded by an expected current status, and `findUnreferencedIds()` which returns the subset of candidate IDs that are older than a given threshold and not attached to any knowledge base, skill, or agent assignment. Sources track their creator (user or system) and support assignment to both agents and threads. The module integrates with **rag** for content ingestion and vector indexing, **retrievers** for extracting text from files and URLs, **storage** for file persistence in MinIO, **models** for requiring a permitted embedding model before document processing is enqueued (`StartDocumentProcessingUseCase` calls `GetPermittedEmbeddingModelUseCase` so unprovisioned orgs fail fast instead of after OCR), **agents** for source assignment to AI assistants, **threads** for per-conversation source attachment enabling contextual document queries, and **knowledge-bases** for grouping sources into named document collections.
