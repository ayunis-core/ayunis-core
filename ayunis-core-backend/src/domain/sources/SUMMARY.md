Data Sources
External data sources for RAG context enrichment

Sources manage user-uploaded files, URLs, and text content that feed the RAG pipeline. Each source is chunked, indexed, and made available for semantic search during AI conversations. Sources may optionally belong to a knowledge base via the `knowledgeBaseId` foreign key column.

Source citation reads use `FindSourceCitationTargetUseCase`, backed by a single joined repository query that returns the exact persisted content chunk and its owning text-source metadata without loading the full extracted source text. The use case intentionally performs no caller authorization; consuming modules must establish their own access boundary before exposing the result.

Processing failures persist a nullable `processingErrorCode` alongside the existing diagnostic text. Codes are classified from typed exceptions, not their messages; unknown failures use `PROCESSING_FAILED`. Successful status transitions clear the code, and legacy rows remain unclassified rather than guessing from stored text.

The sources module manages external data that enriches AI context through RAG. The abstract `Source` entity specializes into `TextSource` (direct text with URL or content) and `DataSource` (uploaded files with storage references); `UrlSource` further specializes `TextSource` with a `maxDepth` property controlling how many levels of same-site links are crawled. `TextSourceContentChunk` represents indexed content fragments. Each source has an optional `knowledgeBaseId` foreign key linking it to a knowledge base collection; when a knowledge base is deleted its sources are removed with it (`onDelete: CASCADE`, see the AddOrgCascadeToConversationKbMcpData migration). Key use cases include creating text and data sources, creating processing sources (for async document pipelines), creating processing URL sources and crawling them asynchronously (`CreateProcessingUrlSourceUseCase`, `EnqueueUrlCrawlUseCase`, `StartUrlCrawlUseCase`), marking sources as failed, querying text sources semantically (bounded to ten matching chunks per query), retrieving source details, deleting sources (single or bulk), and finding unreferenced source IDs (`FindUnreferencedSourceIdsUseCase` — accepts candidate IDs via `FindUnreferencedSourceIdsQuery` and returns the subset not attached to any skill, agent, or knowledge base, used by cross-module cleanup flows). CSV/spreadsheet uploads are processed asynchronously like documents: `StartDataSourceProcessingUseCase` reads only the workbook's data-sheet names in-request (first-row-only parse that skips empty sheets; zero data sheets → `EmptyFileDataError`), invokes the command's optional `ensureCapacityFor(sourceCount)` callback so the caller can reject an over-capacity workbook with its own limit error while rejection is still free, pre-creates one PROCESSING `CSVDataSource` per data sheet (single sheet → `<base>.csv`, multi-sheet → `<base>_<Sheet_Name>.csv`), stashes the raw file in MinIO, and enqueues one job on the `data-source-processing` BullMQ queue; `DataSourceProcessingConsumer` downloads the file, parses it via `SpreadsheetParserPort` — implemented by `PiscinaSpreadsheetParserAdapter`, which runs the CPU-bound parse in a piscina worker-thread pool (max 2 threads, idle shutdown, 60s abort timeout → `SpreadsheetParseTimeoutError`; malformed, corrupt, encrypted, and unsupported workbook containers → `UnprocessableSpreadsheetError` 422 with a stable parser reason and the original cause retained internally; shared via `SpreadsheetParsingModule` since the BullMQ worker runs in the API process) — fills each source's `data` and CAS-flips it PROCESSING→READY via guarded UPDATEs only (`refreshProcessingHeartbeat`, `updateCsvSourceData` — never `save()`, whose upsert would resurrect a concurrently deleted row); sheets the full parse drops (used range with only blank cells) and final-attempt failures are marked FAILED with a `processingError`, and the MinIO object is removed afterwards. Classified provider failures increment the shared `provider_unavailable_count` AppSignal counter only when the queue settles the operation as failed, never on retryable attempts. The async pipeline uses `DocumentProcessingPort` (application port) implemented by `DocumentProcessingProducer` (BullMQ adapter) to enqueue jobs; the port also exposes `cancelJob()` for best-effort cancellation of waiting or active jobs. Document and URL jobs get a generated job id per run and are deduplicated by source id (`sourceJobOptions`, BullMQ `deduplication`): a second enqueue for a source is dropped only while its earlier run is waiting, delayed or active, and runs normally once that job has completed or failed, however long BullMQ retains it; `cancelJob()` finds the current run through the deduplication key and removes it unless it is already active. Both queues' consumers are thin wrappers around `SourceIngestionService`, which owns one text-source ingestion attempt: claim the PROCESSING row and refresh its heartbeat, extract, prepare (embed), re-read the row, commit, mark READY — skipping without writes when the source is gone or no longer PROCESSING — and, when the queue's `classifyJobFailure` says no retry follows, mark it FAILED and clean up its index. Extraction is pluggable per source type through `TextSourceExtractor`: `FileSourceExtractor` downloads the staged MinIO file, retrieves and splits its text, and deletes the staged file on `release()`, which the service calls once a run is settled (ready, skipped or finally failed) but never before a retry; `UrlSourceExtractor` crawls and splits per page (see below). A new text source type adds an extractor and a consumer, not another lifecycle. Processed content is written through `SourceContentReplacementService`: `prepare()` embeds the chunks with no transaction open, and `commit()` replaces the source's text details, content chunks, and index entries in one transaction (`SourceRepository.replaceTextSource` first locks the source row, then deletes the previous details by `sourceId` — cascading their chunks — before inserting the new ones), so a failure at any point leaves the previously committed content intact and a retry or overlapping commit leaves exactly one set of chunks and index entries. `commit()` only writes onto an existing row: when the source was deleted before the commit it writes nothing and returns null, and `SourceIngestionService` skips marking it ready, so a deleted source is never resurrected (`CreateTextSourceUseCase` inserts its new row in the same transaction first). Replacing chunks means citations in older chats that point to replaced chunk ids stop resolving. A parallel URL-crawl pipeline (`UrlCrawlModule`) uses `UrlCrawlProcessingPort` implemented by `UrlCrawlProducer` (BullMQ adapter, also exposing `cancelJob()`); its `UrlSourceExtractor` crawls a root URL up to `maxDepth` levels of same-site links, translates each page's local chunk offsets into the concatenated source text's global coordinates, and names the source after the root page's title. `SourceIngestionService` heartbeats through `refreshProcessingHeartbeat`, prepares (embeds) the content, and only then re-reads the row right before committing, never saving its claimed copy, because `AddUrlToKnowledgeBaseUseCase` and `AddDocumentToKnowledgeBaseUseCase` assign the knowledge base only after enqueueing and a stale full-record save would clear that link (failure-marking and index cleanup live in the shared `SourceProcessingHelper`). `StaleProcessingCleanupTask` runs a cron job every 5 minutes to mark sources stuck in PROCESSING for >15 minutes as FAILED (bounded batches, oldest first, with an in-flight guard against overlapping runs). `CleanupSourceProcessingUseCase` takes source ids plus an explicit org id, cancels both the document-processing and URL-crawl pipelines best-effort, and purges the `<orgId>/processing/<sourceId>/` prefixes via the storage module. It is used by direct source deletion and deferred deletion cleanup without relying on request context, including after owning rows are already cascade-deleted. The `SourceRepository` joins the ambient CLS transaction for related source, detail, and chunk reads and writes; it provides `findStaleProcessingSourceIds()` for stale-source cleanup, `updateStatusConditionally()` for atomic status transitions guarded by an expected current status, and `findUnreferencedIds()` which returns the subset of candidate IDs that are older than a given threshold and not attached to any knowledge base, skill, or agent assignment. Sources track their creator (user or system) and support assignment to both agents and threads. The module integrates with **rag** for content ingestion and vector indexing, **retrievers** for extracting text from files and URLs, **storage** for file persistence in MinIO, **models** for requiring a permitted embedding model before document processing is enqueued (`StartDocumentProcessingUseCase` calls `GetPermittedEmbeddingModelUseCase` so unprovisioned orgs fail fast instead of after OCR), **agents** for source assignment to AI assistants, **threads** for per-conversation source attachment enabling contextual document queries, and **knowledge-bases** for grouping sources into named document collections.
