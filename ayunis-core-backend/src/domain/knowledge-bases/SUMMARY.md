Knowledge Bases
Document collections for organized RAG retrieval

Knowledge bases group uploaded documents (PDF, DOCX, PPTX) into named collections that can be queried semantically. Each knowledge base belongs to an organization and exactly one user or workspace.

`AbstractKnowledgeBase` holds the shared name, optional description, organization scope (`orgId`), and timestamps. Its concrete `PersonalKnowledgeBase` and `WorkspaceKnowledgeBase` subclasses expose a non-null `userId` or `workspaceId`, respectively; nullable owner columns remain confined to persistence. `FindKnowledgeBaseForThreadUseCase` exposes trusted-thread read access for skill-driven knowledge-base attachment, including knowledge bases in that thread's workspace; direct personal attachment still uses `FindAccessibleKnowledgeBaseUseCase`. Mixed lookups retain the `KnowledgeBase` union, and callers narrow ownership with `instanceof PersonalKnowledgeBase` or `instanceof WorkspaceKnowledgeBase`. Personal and workspace-owned knowledge bases use separate lists. Personal knowledge bases cannot be copied or attached to workspaces; workspace knowledge bases are created directly within their workspace. Activation is stored by row presence in `knowledge_base_activations` for both user and workspace scopes. Personal and shared knowledge-base activation remains per-user, while workspace activation is workspace-wide; ownership remains on `knowledge_bases.userId` or `knowledge_bases.workspaceId`. The activation repository operations support idempotent activation, deactivation, status lookup, and batched active-ID lookup. Run-time active knowledge-base resolution uses one database query with activation, direct org/team share, team-membership, and shared-skill access checks expressed as joins and correlated `EXISTS` clauses built by the TypeORM query helper in `queries/active-knowledge-base-access.db-query.ts`; indexes on both share foreign-key columns support these lookups. The `KnowledgeBaseSummary` interface (in `domain/knowledge-base-summary.ts`) is a lightweight projection containing only `id` and `name`, used by other modules (e.g., threads) to reference knowledge bases without loading the full entity. The `KnowledgeBaseRepository` port defines mixed and ownership-scoped persistence: save, find by ID/IDs with organization and workspace filters, personal/workspace owner lists, accessible paginated lists, and deletion. Personal and workspace activation have separate activate/deactivate methods, active-ID queries, and batched workspace-state lookup. Source operations include assignment, single and bulk knowledge-base source snapshots, scoped document lookup, and single/bulk document counts. A local TypeORM implementation (`LocalKnowledgeBaseRepository`) backs the port with a mapper and `KnowledgeBaseRecord` schema; the source-related methods use `SourceRecord` and `SourceMapper` from the sources module. Domain errors are defined in `knowledge-bases.errors.ts`: `KnowledgeBaseNotFoundError` (404 when a knowledge base is not found), `DocumentNotInKnowledgeBaseError` (404 when a document does not belong to a knowledge base), and `MissingFileError` (400 when no file is provided).

Activation is handled by `SetKnowledgeBaseActivationUseCase`, which validates current-user access before idempotently setting the per-user activation row to the requested state, and `FindActiveKnowledgeBasesUseCase`, which returns only active, currently accessible knowledge bases for run assembly. Five CRUD use cases are provided: `CreateKnowledgeBaseUseCase` (persists a new knowledge base), `UpdateKnowledgeBaseUseCase` (updates name/description, verifies ownership), `DeleteKnowledgeBaseUseCase` (removes by ID, verifies ownership), `FindKnowledgeBaseUseCase` (retrieves a single knowledge base by ID and user), and `ListKnowledgeBasesUseCase` (returns all knowledge bases for a user). Each use case has a corresponding command/query DTO. All knowledge-base use-case boundaries use `@HandleUnexpectedErrors(UnexpectedKnowledgeBaseError)`: expected application and HTTP errors pass through unchanged, while unexpected failures are logged once and wrapped with a stable public error code and a non-serialized internal cause.

Three exported access use cases support cross-module callers: `FindAccessibleKnowledgeBaseUseCase` verifies organization scope and resolves personal ownership, direct sharing, or shared-skill access; `GetAccessibleKnowledgeBaseContextsUseCase` deduplicates requested IDs, resolves access through that use case, and loads the current user's activation IDs once to return knowledge bases with `isShared` and `isActive` state. `FindKnowledgeBaseForThreadUseCase` resolves personal read access or workspace read access through a current-user-owned thread in the same workspace and organization. Direct personal thread assignment uses `FindAccessibleKnowledgeBaseUseCase`; skill-driven assignment, knowledge queries, and document text reads use the thread-aware lookup. Skill knowledge-base listing uses the context lookup.

`KnowledgeBasesUserDeletionRequestedListener` handles `UserDeletionRequestedEvent` (AYC-382) for both personal knowledge bases and knowledge bases in workspaces owned by the user. `KnowledgeBasesWorkspaceDeletionRequestedListener` only handles queued-job and temporary processing-file cleanup after successful workspace deletion. Knowledge bases, their sources, and RAG parent/child chunks (including embeddings) are removed entirely by the existing foreign-key cascade chain; the workspace listener does not call source or index deletion use cases. Both listeners snapshot affected sources in one bulk query before the cascade. The user-deletion listener additionally invokes bulk source/index cleanup. Listener lookup failures are logged and never block deletion.

Four source management use cases handle documents and URLs within a knowledge base: `AddDocumentToKnowledgeBaseUseCase` (uploads a file, validates type, and creates a source linked to the knowledge base), `AddUrlToKnowledgeBaseUseCase` (validates the knowledge base and source limit, then delegates to the sources module's `StartUrlCrawlUseCase` to kick off an asynchronous crawl with an optional `maxDepth`, assigning the resulting PROCESSING source to the knowledge base), `RemoveDocumentFromKnowledgeBaseUseCase` (deletes a document by ID, verifies ownership), and `ListKnowledgeBaseDocumentsUseCase` (returns all documents/sources for a knowledge base). Each has a corresponding command/query DTO. A `GetKnowledgeBasesByIdsUseCase` fetches personal knowledge bases by their IDs in a single query, filtering to the user's organization and excluding workspace-owned rows; it is used by other modules (e.g., skills) to efficiently resolve knowledge base references without crossing module boundaries. Knowledge queries, document text reads, and skill-driven thread attachment resolve access through `FindKnowledgeBaseForThreadUseCase`: personal sharing rules stay unchanged; workspace knowledge requires a current-user-owned execution thread in the same workspace and organization. The thread ID comes from tool execution context, never model input. A `QueryKnowledgeBaseUseCase` performs semantic search across all documents in a knowledge base using the RAG indexer's `SearchContentUseCase`, returning ranked content chunks. A `GetKnowledgeBaseDocumentTextUseCase` retrieves the full source entity for a specific document within a knowledge base, verifying access before returning it; this supports the knowledge-get-text tool's need to extract raw document text. Document listing and single personal knowledge-base detail reads resolve access through `KnowledgeBaseAccessService`, which grants access when the knowledge base is owned by the caller, directly shared with them, or linked to a shared skill owned by the knowledge base's owner (via the skills module's `CheckKnowledgeBaseSkillShareAccessUseCase` — sharing a skill implicitly delegates read access to the owner's own linked knowledge bases, and never to a knowledge base someone else merely attached, AYC-13). Shared detail responses are marked read-only for the frontend. `KnowledgeBaseAccessService` remains internal to this module. Other modules use `FindAccessibleKnowledgeBaseUseCase` for personal/shared access checks and `GetAccessibleKnowledgeBaseContextsUseCase` for access-checked resources with sharing and current-user activation state. The latter deduplicates IDs and loads activation state once per batch. `CountKnowledgeBaseDocumentsUseCase` exposes bulk document counts. Workspace property, activation, and document use cases implement their operations directly. `WorkspaceKnowledgeBaseAccessService.requireInWorkspace` is an internal scoped-resource ownership policy only. `AddDocumentToKnowledgeBaseUseCase` is the single upload operation for personal and workspace knowledge bases: it resolves the actual resource, authorizes write access, checks source capacity, starts processing, and assigns the source. Assignment failures trigger cleanup; cleanup failures are logged without masking the assignment error. The internal `KnowledgeBaseWriteAccessService` requires authenticated organization scope, validates personal ownership directly, and delegates workspace permission to the exported `AssertWorkspaceWriteAccessUseCase`. Read sharing never grants write access. Removal checks document membership before deleting.

The HTTP presenter layer exposes a `KnowledgeBasesController` at `/knowledge-bases` with ten endpoints: the five CRUD endpoints (`POST /`, `GET /`, `GET /:id`, `PATCH /:id`, `DELETE /:id`) plus `PATCH /:id/activation` with an explicit `isActive` value for the current user's activation preference and four source endpoints (`GET /:id/documents` to list documents, `POST /:id/documents` for multipart file upload of PDF/DOCX/PPTX, `POST /:id/urls` to add a URL source which returns 202 Accepted since the crawl runs asynchronously, and `DELETE /:id/documents/:documentId` to remove a document, returns 204). The upload endpoint uses the shared `common/http/document-upload.ts` helpers for multipart storage, file-type/MIME validation, and temporary-file cleanup. Request DTOs (`CreateKnowledgeBaseDto`, `UpdateKnowledgeBaseDto`, `AddUrlToKnowledgeBaseDto`) handle input validation, `KnowledgeBaseResponseDto`, `KnowledgeBaseListResponseDto`, `KnowledgeBaseDocumentResponseDto`, and `KnowledgeBaseDocumentListResponseDto` define response shapes, and `KnowledgeBaseDtoMapper` maps domain entities to response DTOs.

The `KnowledgeBasesModule` imports `LocalKnowledgeBaseRepositoryModule`, `SourcesModule`, `IndexersModule`, `ContextModule`, `StorageModule`, and (via `forwardRef`) `SharesModule`, `SkillsModule`, `ThreadsModule`, and `WorkspacesModule`; it registers all use cases, `KnowledgeBaseAccessService`, `WorkspaceKnowledgeBaseAccessService`, `KnowledgeBaseWriteAccessService`, the share authorization strategy, the listeners, and the DTO mapper as providers, declares the controller, and exports the repository module and use cases for consumption by other modules. Workspace property, activation, page/state, document, and count operations have dedicated exported use cases; the access policy remains module-local. Workspace authorization stays at the calling workspace use case. The module integrates with **sources** for document storage and chunking, **indexers** for semantic indexing and multi-document vector search, **shares** for direct knowledge-base shares, **skills** for the skill-share access path, and **threads** for cleaning up thread assignments when shares are revoked.
