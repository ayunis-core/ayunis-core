Knowledge Bases
Document collections for organized RAG retrieval

Knowledge bases group uploaded documents (PDF, DOCX, PPTX) into named collections that can be queried semantically. Each knowledge base belongs to an organization and exactly one user or workspace.

`AbstractKnowledgeBase` holds the shared name, optional description, organization scope (`orgId`), and timestamps. `KnowledgeBaseReadAccessService` and `KnowledgeBaseWriteAccessService` dispatch authorization from the persisted owner type: personal resources retain local ownership/sharing rules, while workspace resources delegate to exported workspace read, write, or trusted-execution capabilities. Its concrete `PersonalKnowledgeBase` and `WorkspaceKnowledgeBase` subclasses expose a non-null `userId` or `workspaceId`, respectively; nullable owner columns remain confined to persistence. `FindKnowledgeBaseForThreadUseCase` exposes trusted-thread read access for skill-driven knowledge-base attachment, including knowledge bases in that thread's workspace; direct personal attachment still uses `FindAccessibleKnowledgeBaseUseCase`. Mixed lookups retain the `KnowledgeBase` union, and callers narrow ownership with `instanceof PersonalKnowledgeBase` or `instanceof WorkspaceKnowledgeBase`. The canonical create/list boundaries accept an explicit `personal` or `workspace` owner discriminator. Personal knowledge bases cannot be copied or attached to workspaces; workspace knowledge bases are created directly within their workspace. Activation is stored by row presence in `knowledge_base_activations` for both user and workspace scopes. Personal and shared knowledge-base activation remains per-user, while workspace activation is workspace-wide; ownership remains on `knowledge_bases.userId` or `knowledge_bases.workspaceId`. The activation repository operations support idempotent activation, deactivation, status lookup, and batched active-ID lookup. Run-time active knowledge-base resolution uses one database query with activation, direct org/team share, team-membership, and shared-skill access checks expressed as joins and correlated `EXISTS` clauses built by the TypeORM query helper in `queries/knowledge-base-access.db-query.ts`; indexes on both share foreign-key columns support these lookups. The `KnowledgeBaseSummary` interface (in `domain/knowledge-base-summary.ts`) is a lightweight projection containing only `id` and `name`, used by other modules (e.g., threads) to reference knowledge bases without loading the full entity. The `KnowledgeBaseRepository` port defines mixed and ownership-scoped persistence: save, find by ID/IDs with organization and workspace filters, personal/workspace owner lists, accessible paginated lists, and deletion. Personal and workspace activation have separate activate/deactivate methods, active-ID queries, and batched workspace-state lookup. Source operations include assignment, single and bulk knowledge-base source snapshots, scoped document lookup, and single/bulk document counts. A local TypeORM implementation (`LocalKnowledgeBaseRepository`) backs the port with a mapper and `KnowledgeBaseRecord` schema; the source-related methods use `SourceRecord` and `SourceMapper` from the sources module. Domain errors are defined in `knowledge-bases.errors.ts`: `KnowledgeBaseNotFoundError` (404 when a knowledge base is not found), `DocumentNotInKnowledgeBaseError` (404 when a document does not belong to a knowledge base), and `MissingFileError` (400 when no file is provided).

Activation is handled by `SetKnowledgeBaseActivationUseCase`, which dispatches from the persisted owner: personal/shared activation stays per-user, while workspace activation requires workspace write access plus `MANAGE_KNOWLEDGE_BASES` and updates workspace-wide state. `FindActiveKnowledgeBasesUseCase` returns only active, currently accessible knowledge bases for run assembly. The canonical CRUD use cases derive principal scope from `ContextService`; entity-ID operations load the entity before owner-aware authorization. `FindKnowledgeBaseUseCase` returns persisted owner, activation, sharing, and document-count context. `ListKnowledgeBasesUseCase` returns `{ data, pagination }`; omitted search and pagination return the complete personal or workspace scope with deterministic name ordering, while either scope uses the same paginated path when search or pagination is supplied. All knowledge-base use-case boundaries use `@HandleUnexpectedErrors(UnexpectedKnowledgeBaseError)`: expected application and HTTP errors pass through unchanged, while unexpected failures are logged once and wrapped with a stable public error code and a non-serialized internal cause.

Four exported access use cases support cross-module callers: `FindAccessibleKnowledgeBaseUseCase` verifies organization scope and resolves personal ownership, direct sharing, or shared-skill access; `FindAccessibleKnowledgeBasesByIdsUseCase` deduplicates IDs and returns the accessible subset of requested personal knowledge bases; `GetAccessibleKnowledgeBaseContextsUseCase` deduplicates requested IDs, batch-loads organization-scoped personal or workspace resources, authorizes each through `KnowledgeBaseReadAccessService`, and returns `isShared`, `isActive`, and `documentCount` state using per-user personal activation, workspace-wide activation, and batched document counts; and `FindKnowledgeBaseForThreadUseCase` resolves personal read access or workspace read access through a current-user-owned thread in the same workspace and organization. Direct personal thread assignment uses the single-resource lookup; skill-driven assignment, knowledge queries, and document text reads use the thread-aware lookup; skill knowledge-base listing uses the context lookup; and runs use the subset lookup to omit stale thread assignments from user-facing AI context.

`KnowledgeBasesUserDeletionRequestedListener` handles `UserDeletionRequestedEvent` (AYC-382) for both personal knowledge bases and knowledge bases in workspaces owned by the user. `KnowledgeBasesWorkspaceDeletionRequestedListener` only handles queued-job and temporary processing-file cleanup after successful workspace deletion. Knowledge bases, their sources, and RAG parent/child chunks (including embeddings) are removed entirely by the existing foreign-key cascade chain; the workspace listener does not call source or index deletion use cases. Both listeners snapshot affected sources in one bulk query before the cascade. The user-deletion listener additionally invokes bulk source/index cleanup. Listener lookup failures are logged and never block deletion.

Four source management use cases handle documents and URLs within a knowledge base: `AddDocumentToKnowledgeBaseUseCase` (uploads a file, validates type, and creates a source linked to the knowledge base), `AddUrlToKnowledgeBaseUseCase` (validates the knowledge base and source limit, then delegates to the sources module's `StartUrlCrawlUseCase` to kick off an asynchronous crawl with an optional `maxDepth`, assigning the resulting PROCESSING source to the knowledge base), `RemoveDocumentFromKnowledgeBaseUseCase` (deletes a document by ID, verifies ownership), and `ListKnowledgeBaseDocumentsUseCase` (returns all documents/sources for a knowledge base). Each has a corresponding command/query DTO. Knowledge queries, document text reads, and skill-driven thread attachment resolve access through `FindKnowledgeBaseForThreadUseCase`: personal sharing rules stay unchanged; workspace knowledge requires a current-user-owned execution thread in the same workspace and organization. The thread ID comes from tool execution context, never model input. A `QueryKnowledgeBaseUseCase` performs semantic search across all documents in a knowledge base using the RAG indexer's `SearchContentUseCase`, returning ranked content chunks. A `GetKnowledgeBaseDocumentTextUseCase` retrieves the full source entity for a specific document within a knowledge base, verifying access before returning it; this supports the knowledge-get-text tool's need to extract raw document text. Document listing and owner-aware knowledge-base detail reads resolve access through `KnowledgeBaseReadAccessService`, which handles personal knowledge bases owned by the caller, directly shared with them, or linked to a shared skill owned by the knowledge base's owner (via the skills module's `CheckKnowledgeBaseSkillShareAccessUseCase` — sharing a skill implicitly delegates read access to the owner's own linked knowledge bases, and never to a knowledge base someone else merely attached, AYC-13). Shared detail responses are marked read-only for the frontend. Other modules use `FindAccessibleKnowledgeBaseUseCase` for personal/shared access checks and `GetAccessibleKnowledgeBaseContextsUseCase` for access-checked resources with sharing and current-user activation state. The latter deduplicates IDs, batch-loads organization-scoped resources and document counts, and resolves personal and workspace activation according to their respective scopes. `CountKnowledgeBaseDocumentsUseCase` exposes bulk document counts. `AddDocumentToKnowledgeBaseUseCase` is the single upload operation for personal and workspace knowledge bases: it resolves the actual resource, authorizes write access, checks source capacity, starts processing, and assigns the source. Assignment failures trigger cleanup; cleanup failures are logged without masking the assignment error. The internal `KnowledgeBaseWriteAccessService` requires authenticated organization scope, validates personal ownership directly, and delegates workspace permission to the exported `AssertWorkspaceWriteAccessUseCase`. `KnowledgeBaseReadAccessService` applies the equivalent owner-aware read dispatch and uses `AssertWorkspaceExecutionAccessUseCase` for workspace tool access. Workspace denials are translated to knowledge-base not-found errors so ownership details do not leak. Read sharing never grants write access. Removal checks document membership before deleting.

The HTTP presenter layer exposes the only knowledge-base resource API through `KnowledgeBasesController` at `/knowledge-bases`. Create and list requests carry flat `ownerType` (`personal` or `workspace`) and a conditionally required `workspaceId`; entity routes use only the knowledge-base ID and derive ownership from persistence. List responses always use `{ data, pagination }`, and knowledge-base responses include `ownerType`, optional `workspaceId`, activation/sharing state, and `documentCount`. Its ten endpoints are the five CRUD endpoints (`POST /`, `GET /`, `GET /:id`, `PATCH /:id`, `DELETE /:id`) plus `PATCH /:id/activation` and four source endpoints (`GET /:id/documents` to list documents, `POST /:id/documents` for multipart file upload of PDF/DOCX/PPTX, `POST /:id/urls` to add a URL source which returns 202 Accepted since the crawl runs asynchronously, and `DELETE /:id/documents/:documentId` to remove a document, returns 204). The upload endpoint uses the shared `common/http/document-upload.ts` helpers for multipart storage, file-type/MIME validation, and temporary-file cleanup. Request DTOs (`CreateKnowledgeBaseDto`, `UpdateKnowledgeBaseDto`, `AddUrlToKnowledgeBaseDto`) handle input validation, `KnowledgeBaseResponseDto`, `KnowledgeBaseListResponseDto`, `KnowledgeBaseDocumentResponseDto`, and `KnowledgeBaseDocumentListResponseDto` define response shapes, and `KnowledgeBaseDtoMapper` maps domain entities to response DTOs.

The `KnowledgeBasesModule` imports `LocalKnowledgeBaseRepositoryModule`, `SourcesModule`, `IndexersModule`, `ContextModule`, `PermissionsModule`, `StorageModule`, and (via `forwardRef`) `SharesModule`, `SkillsModule`, `ThreadsModule`, and `WorkspacesModule`; it registers the canonical use cases, owner-aware read/write services, share strategy, listeners, and DTO mapper. Legacy workspace-specific knowledge-base wrappers and access services do not exist. Other modules consume exported canonical use cases; workspace authorization remains behind the exported workspace capability use cases. The module integrates with **sources** for document storage and chunking, **indexers** for semantic indexing and multi-document vector search, **shares** for direct knowledge-base shares, **skills** for the skill-share access path, and **threads** for cleaning up thread assignments when shares are revoked.
