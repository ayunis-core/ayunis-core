Knowledge Bases
Document collections for organized RAG retrieval

Knowledge bases group uploaded documents (PDF, DOCX, PPTX, CSV, XLSX, XLS, ODS; tables are flattened to per-row "Header: value" text by the document processing consumer (the file retriever is skipped) and searched like any other document) into named collections that can be queried semantically. Each knowledge base belongs to an organization and exactly one owner: a user, a workspace, a team or the organisation (see the team and organisation section below).

`AbstractKnowledgeBase` holds the shared name, optional description, organization scope (`orgId`), and timestamps. `KnowledgeBaseReadAccessService` and `KnowledgeBaseWriteAccessService` dispatch authorization from the persisted owner type: personal resources are owner-only (reviewers of a pending handover may view them read-only), while workspace resources delegate to exported workspace read, write, or trusted-execution capabilities. Its concrete `PersonalKnowledgeBase` and `WorkspaceKnowledgeBase` subclasses expose a non-null `userId` or `workspaceId`, respectively; nullable owner columns remain confined to persistence. `FindKnowledgeBaseForThreadUseCase` exposes trusted-thread read access for skill-driven knowledge-base attachment, including knowledge bases in that thread's workspace; direct personal attachment still uses `FindAccessibleKnowledgeBaseUseCase`. Mixed lookups retain the `KnowledgeBase` union, and callers narrow ownership with `instanceof PersonalKnowledgeBase` or `instanceof WorkspaceKnowledgeBase`. The canonical create boundary accepts an explicit `personal`, `workspace`, `team` (with `teamId`) or `org` owner discriminator; listing takes `personal` (which also returns the team and organisation knowledge bases the caller may use) or `workspace`. Personal knowledge bases cannot be copied or attached to workspaces; workspace knowledge bases are created directly within their workspace. For personal and workspace knowledge bases, activation is stored by row presence in `knowledge_base_activations`; team and organisation ones use the row's `isActive` flag (see below). Personal knowledge-base activation remains per-user, while workspace activation is workspace-wide; ownership remains on `knowledge_bases.userId` or `knowledge_bases.workspaceId`. The activation repository operations support idempotent activation, deactivation, status lookup, and batched active-ID lookup. Run-time active knowledge-base resolution combines the caller's own activated personal knowledge bases with the usable team and organisation knowledge bases from `CollectiveKnowledgeBaseRepository`; citation authorization constrains the personal query to one knowledge-base and source relationship (`queries/knowledge-base-access.db-query.ts`) instead of loading the full active set. The `KnowledgeBaseSummary` interface (in `domain/knowledge-base-summary.ts`) is a lightweight projection containing only `id` and `name`, used by other modules (e.g., threads) to reference knowledge bases without loading the full entity. The `KnowledgeBaseRepository` port defines mixed and ownership-scoped persistence: save, find by ID/IDs with organization and workspace filters, personal/workspace owner lists, accessible paginated lists, and deletion. Personal and workspace activation have separate activate/deactivate methods, active-ID queries, and batched workspace-state lookup. Source operations include assignment, single and bulk knowledge-base source snapshots, scoped document lookup, and single/bulk document counts. A local TypeORM implementation (`LocalKnowledgeBaseRepository`) backs the port with a mapper and `KnowledgeBaseRecord` schema; the source-related methods use `SourceRecord` and `SourceMapper` from the sources module. Domain errors are defined in `knowledge-bases.errors.ts`: `KnowledgeBaseNotFoundError` (404 when a knowledge base is not found), `DocumentNotInKnowledgeBaseError` (404 when a document does not belong to a knowledge base), and `MissingFileError` (400 when no file is provided).

Activation is handled by `SetKnowledgeBaseActivationUseCase`, which dispatches from the persisted owner: personal activation stays per-user, while workspace activation requires workspace write access plus `MANAGE_OWN_KNOWLEDGE` and updates workspace-wide state. `FindActiveKnowledgeBasesUseCase` returns only active, currently accessible knowledge bases for run assembly. The canonical CRUD use cases derive principal scope from `ContextService`; entity-ID operations load the entity before owner-aware authorization. `FindKnowledgeBaseUseCase` returns persisted owner, activation, viewer rights, and document-count context. `ListKnowledgeBasesUseCase` returns `{ data, pagination }`; omitted search and pagination return the complete personal or workspace scope with deterministic name ordering, while either scope uses the same paginated path when search or pagination is supplied. All knowledge-base use-case boundaries use `@HandleUnexpectedErrors(UnexpectedKnowledgeBaseError)`: expected application and HTTP errors pass through unchanged, while unexpected failures are logged once and wrapped with a stable public error code and a non-serialized internal cause.

Five exported access use cases support cross-module callers: `FindAccessibleKnowledgeBaseUseCase` verifies organization scope and resolves personal ownership; `FindAccessibleKnowledgeBasesByIdsUseCase` deduplicates IDs and returns the accessible subset of requested personal knowledge bases; `GetAccessibleKnowledgeBaseContextsUseCase` deduplicates requested IDs, batch-loads organization-scoped personal or workspace resources, authorizes each through `KnowledgeBaseReadAccessService`, and returns `isActive` and `documentCount` state using per-user personal activation, workspace-wide activation, and batched document counts; and `FindKnowledgeBaseForThreadUseCase` resolves personal, team or organisation read access, or workspace access through a current-user-owned thread in the same workspace and organization — including knowledge bases linked into that workspace. `GetLinkedWorkspaceKnowledgeBasesUseCase` returns the knowledge bases linked into a workspace, sorted by name, for the workspace AI context; it does not authorise, so callers check workspace access first. Direct personal thread assignment uses the single-resource lookup; skill-driven assignment, knowledge queries, and document text reads use the thread-aware lookup; skill knowledge-base listing uses the context lookup; and runs use the subset lookup to omit stale thread assignments from user-facing AI context.

`KnowledgeBasesUserDeletionRequestedListener` handles `UserDeletionRequestedEvent` (AYC-382) for both personal knowledge bases and knowledge bases in workspaces owned by the user. `KnowledgeBasesWorkspaceDeletionRequestedListener` only handles queued-job and temporary processing-file cleanup after successful workspace deletion. Knowledge bases, their sources, and RAG parent/child chunks (including embeddings) are removed entirely by the existing foreign-key cascade chain; the workspace listener does not call source or index deletion use cases. Both listeners snapshot affected sources in one bulk query before the cascade. The user-deletion listener additionally invokes bulk source/index cleanup. Listener lookup failures are logged and never block deletion.

Direct knowledge-base deletion snapshots source IDs and deletes database records in a short transaction. Existing foreign-key cascades remove sources and RAG chunks atomically; only after commit does best-effort queue/processing-storage cleanup run. Cleanup failures cannot fail an already committed deletion, and failed database transactions do not cancel jobs or purge files (AYC-898).

Four source management use cases handle documents and URLs within a knowledge base: `AddDocumentToKnowledgeBaseUseCase` (uploads a file, validates type, and creates a source linked to the knowledge base), `AddUrlToKnowledgeBaseUseCase` (validates the knowledge base and source limit, then delegates to the sources module's `StartUrlCrawlUseCase` to kick off an asynchronous crawl with an optional `maxDepth`, assigning the resulting PROCESSING source to the knowledge base), `RemoveDocumentFromKnowledgeBaseUseCase` (deletes a document by ID, verifies ownership), and `ListKnowledgeBaseDocumentsUseCase` (returns all documents/sources for a knowledge base). Each has a corresponding command/query DTO. Knowledge queries, document text reads, and skill-driven thread attachment resolve access through `FindKnowledgeBaseForThreadUseCase`: personal knowledge is owner-only unless it is linked into the workspace of the execution thread; workspace knowledge and linked knowledge require a current-user-owned execution thread in the same workspace and organization. The thread ID comes from tool execution context, never model input. A `QueryKnowledgeBaseUseCase` performs semantic search across all documents in a knowledge base using the RAG indexer's `SearchContentUseCase`, returning ranked content chunks. A `GetKnowledgeBaseDocumentTextUseCase` retrieves the full source entity for a specific document within a knowledge base, verifying access before returning it; this supports the knowledge-get-text tool's need to extract raw document text. Document listing and owner-aware knowledge-base detail reads resolve access through `KnowledgeBaseReadAccessService`, which handles personal knowledge bases owned by the caller, team and organisation knowledge bases the caller may use, and workspace knowledge bases through workspace read access. Other modules use `FindAccessibleKnowledgeBaseUseCase` for personal access checks and `GetAccessibleKnowledgeBaseContextsUseCase` for access-checked resources with current-user activation state. The latter deduplicates IDs, batch-loads organization-scoped resources and document counts, and resolves personal and workspace activation according to their respective scopes. `CountKnowledgeBaseDocumentsUseCase` exposes bulk document counts. `AddDocumentToKnowledgeBaseUseCase` is the single upload operation for personal and workspace knowledge bases: it resolves the actual resource, authorizes write access, checks source capacity, starts processing, and assigns the source. Assignment failures trigger cleanup; cleanup failures are logged without masking the assignment error. The internal `KnowledgeBaseWriteAccessService` requires authenticated organization scope, validates personal ownership directly, and delegates workspace permission to the exported `AssertWorkspaceWriteAccessUseCase`. `KnowledgeBaseReadAccessService` applies the equivalent owner-aware read dispatch and uses `AssertWorkspaceExecutionAccessUseCase` for workspace tool access. Workspace denials are translated to knowledge-base not-found errors so ownership details do not leak. Removal checks document membership before deleting.

The HTTP presenter layer exposes the knowledge-base resource API through `KnowledgeBasesController` at `/knowledge-bases`; workspace link routes live in `KnowledgeBaseLinksController` (see the workspace links paragraph). Create and list requests carry flat `ownerType` (`personal` or `workspace`) and a conditionally required `workspaceId`; entity routes use only the knowledge-base ID and derive ownership from persistence. List responses always use `{ data, pagination }`, and knowledge-base responses include `ownerType`, optional `workspaceId`, activation state, `viewer` rights, and `documentCount`. Its eleven endpoints are the five CRUD endpoints (`POST /`, `GET /`, `GET /:id`, `PATCH /:id`, `DELETE /:id`) plus `GET /owner-options`, `PATCH /:id/activation` and four source endpoints (`GET /:id/documents` to list documents, `POST /:id/documents` for multipart file upload of PDF/DOCX/PPTX/ODT/ODP/CSV/XLSX/XLS/ODS/TXT/EML/MSG/audio, `POST /:id/urls` to add a URL source which returns 202 Accepted since the crawl runs asynchronously, and `DELETE /:id/documents/:documentId` to remove a document, returns 204). The upload endpoint uses the shared `common/http/document-upload.ts` helpers for multipart storage, file-type/MIME validation, and temporary-file cleanup. Request DTOs (`CreateKnowledgeBaseDto`, `UpdateKnowledgeBaseDto`, `AddUrlToKnowledgeBaseDto`) handle input validation, `KnowledgeBaseResponseDto`, `KnowledgeBaseListResponseDto`, `KnowledgeBaseDocumentResponseDto`, and `KnowledgeBaseDocumentListResponseDto` define response shapes, and `KnowledgeBaseDtoMapper` maps domain entities to response DTOs.

Team (`TeamKnowledgeBase`, `knowledge_bases.teamId`) and organisation (`OrgKnowledgeBase`, no user, workspace or team) knowledge bases follow the ownership module's rules: team members and everyone in the organisation use them, team admins with `team_manage_knowledge` and admins change team knowledge, holders of `manage_org_knowledge` change organisation knowledge. They are active by default; a `knowledge_base_activations` row with `isActive = false` switches one off for one person. `CollectiveKnowledgeBaseRepository` resolves usable and active ones for lists, runs and thread assignments. Create, update, delete and document changes check rights in `KnowledgeBaseWriteAccessService.requireManage` and `CreateKnowledgeBaseUseCase` instead of route decorators. `GET /knowledge-bases/owner-options` lists the owners the caller may create for, and responses carry `viewer` and `ownerDescription`, built by `KnowledgeBaseOwnershipContextService` from the ownership module's lookup.

Handover (handovers module): `TransferKnowledgeBaseOwnershipUseCase` moves a personal knowledge base to a team or the organisation after approval, records `submittedByUserId` and keeps the requester's active state. Reviewers of a pending request may view it and its documents list through `requireView`, never use it.

Workspace links: `workspace_knowledge_base_links` (same shape as skill links) reference personal, team and organisation knowledge bases from a workspace. `KnowledgeBaseLinksController` serves `GET`/`POST /workspaces/:id/linked-knowledge-bases`, `DELETE /workspaces/:id/linked-knowledge-bases/:knowledgeBaseId`, `GET /workspaces/:id/linkable-knowledge-bases` and `GET /knowledge-bases/:id/linked-workspaces`, with the same rules as skills (`requireLinkable`, 400 `KNOWLEDGE_BASE_NOT_LINKABLE` for workspace knowledge, all-or-nothing). `KnowledgeBaseReadAccessService.requireView` and `requireExecution` fall back to links, so a linked knowledge base can be opened read-only and answers, with citations, in threads of the linking workspace. Linked knowledge bases are always active there.

The `KnowledgeBasesModule` imports `LocalKnowledgeBaseRepositoryModule`, `SourcesModule`, `IndexersModule`, `ContextModule`, `PermissionsModule`, `StorageModule`, `OwnershipModule`, and (via `forwardRef`) `SkillsModule`, `ThreadsModule`, `WorkspacesModule`, and `HandoversModule`; it registers the canonical use cases, owner-aware read/write services, listeners, and DTO mapper. Legacy workspace-specific knowledge-base wrappers and access services do not exist. Other modules consume exported canonical use cases; workspace authorization remains behind the exported workspace capability use cases. The module integrates with **sources** for document storage and chunking, **indexers** for semantic indexing and multi-document vector search, **ownership** for team and organisation rights, and **handovers** for reviewer read access and ownership transfer.
