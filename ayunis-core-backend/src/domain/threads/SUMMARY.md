Conversation Sessions
Conversation threads linking messages, models, and sources

Threads are conversation containers that hold message histories, bind to a language model and optional agent, and support source attachments and knowledge base assignments for per-conversation RAG context enrichment.

Chat source responses expose `processingErrorCode` for localized failure guidance. Legacy failures use a generic code; the deprecated `processingError` response contains only a generic message, never stored internal diagnostics. Non-failed sources expose no failure fields.

Thread responses expose both the stored permit id and its stable catalog model id so clients can recognize an equivalent current team or organization grant without rewriting persisted chat state.

The threads module manages conversation sessions. The `Thread` entity holds a message list, optional `PermittedLanguageModel` reference, optional agent binding, source assignments, knowledge base assignments, title, anonymous flag, and the `mode` (`auto` / `max`, null for an individually picked model) the chat was started with, and the nullable `client` (a varchar holding a value of the session client registry in `iam/sessions/domain/value-objects/session-client.ts`, e.g. `outlook`) the chat was started from. `CreateThreadUseCase` sets `client` from the request context's session client (null for the web app). `GET /threads` lists only threads without a client unless `client` is given, which lists only that client's threads, so Outlook chats stay out of the web app's history; the filter lives in `applyThreadListFilters`. `CreateThreadUseCase` accepts either a `modelId` or a `mode`, never both (`CONFLICTING_MODEL_SELECTION`); a mode is resolved to a concrete permit through the models module's `ResolveModelModesUseCase`, using the anonymous resolution when the chat starts in anonymous mode (or when the mode only resolves to an anonymous-only permit, which then makes the thread anonymous), and a mode that currently resolves to nothing fails with `MODEL_MODE_UNAVAILABLE` (422). The resolved permit is bound exactly like a picked model (AYC-441). `FindThreadUseCase` derives the long-chat warning threshold at 90% of that model's configured context window, falling back to 200,000 tokens when the model or value is absent. `SourceAssignment` links data sources to individual threads and carries an optional `originSkillId` provenance field that tracks which skill caused the source to be attached — this enables cleanup when a skill share is revoked. The `KnowledgeBaseAssignment` entity represents a knowledge base attached to a thread; the underlying `thread_knowledge_base_assignments` table stores the thread ID, knowledge base ID, and an optional `originSkillId` provenance column that tracks which skill caused the assignment. This provenance tracking enables targeted cleanup when a skill share is revoked or when a knowledge base is removed from a skill — only assignments originating from that skill are deleted, leaving user-initiated (direct) assignments intact. Key use cases include creating threads, finding threads (single, owner-scoped context references, all, by ids for cross-module batch resolution, by org with sources), updating titles, deleting threads (idempotent — treats already-deleted or not-found threads as success), adding/removing sources, adding uploaded file sources (`AddFileSourceToThreadUseCase` — asserts the `ThreadsConstants.MAX_SOURCES` cap via the shared `assertThreadHasSourceCapacity` helper in `application/util/thread-source-capacity.ts` _before_ any processing starts, since object-storage uploads and enqueued jobs cannot be rolled back; `AddSourceToThreadUseCase` re-checks the same rule against a freshly loaded thread inside a transaction and remains authoritative for concurrent adds. Direct-upload completion (`CompleteThreadSourceUploadUseCase`) attaches all sources of an upload in one statement through `ThreadsRepository.attachSourcesWithinCapacity`, which takes a row lock on the thread and counts under it, so two completions racing for the last slots cannot push a thread past the cap and a multi-sheet workbook no longer reloads the thread once per sheet. It then detects the file type and starts async processing via the sources module: documents/audio through `StartDocumentProcessingUseCase`, CSV/spreadsheet files through `StartDataSourceProcessingUseCase`; every returned PROCESSING source is attached to the thread transactionally and filled by a background job), adding/removing knowledge bases from threads (`AddKnowledgeBaseToThreadUseCase`, `RemoveKnowledgeBaseFromThreadUseCase`), removing skill-originated KB assignments (`RemoveKnowledgeBaseAssignmentsByOriginSkillUseCase`), removing direct KB assignments (`RemoveDirectKnowledgeBaseFromThreadsUseCase`), removing skill-originated sources from threads, cleaning up stale direct thread sources (`CleanupStaleThreadSourcesUseCase`), generating titles via AI inference, and replacing models with user defaults. The add-knowledge-base use case resolves personal/shared access through the knowledge-bases module's exported `FindAccessibleKnowledgeBaseUseCase`, rather than its internal access service, and validates org-scoping (the knowledge base must belong to the caller's org) and deduplicates; the remove use case is idempotent when the knowledge base is not assigned. `CleanupStaleThreadSourcesUseCase` computes a 30-day cutoff, asks `ThreadsRepository.findSourcesWithOnlyStaleDirectAssignments(olderThan)` for source and owning-org IDs whose direct (non-skill) thread assignments all point to stale threads (a thread is stale when it has messages and its latest one predates the cutoff; the query resolves each thread's latest message once via the `messages (threadId, createdAt)` index rather than probing per assignment), then asks the sources module (`FindUnreferencedSourceIdsUseCase`) to filter down to sources not referenced by any skill or knowledge base. Sources are grouped by org and deleted in bounded batches (`STALE_SOURCE_DELETE_BATCH_SIZE`) through `DeleteSourcesUseCase`; the result records scanned / unreferenced / deleted / failed counts. `StaleThreadSourcesCleanupTask` runs this cleanup nightly at 2 AM via Nest schedule (staggered with `OrphanedImagesCleanupTask` at 3 AM) inside the AppSignal `stale_thread_sources_cleanup` cron check-in, skips overlapping executions with an in-memory guard, and logs success or failure counts. Threads carry a `lastActivityAt` timestamp (bumped by `RecordThreadActivityUseCase`, driven by the `ThreadActivityListener` on message-added events) that underpins data retention: `FindExpiredThreadRefsByOrgUseCase` (backed by `ThreadsRepository.findExpiredThreadRefsByOrg`) returns a stably-ordered, paged list of id/owner refs for threads in an org whose `COALESCE(lastActivityAt, createdAt)` predates a cutoff, which the **retention-policies** module consumes to delete aged conversations. Manual thread title updates use one owner-scoped update and return the same not-found response when the thread is missing or inaccessible. Thread title generation uses the language model to auto-summarize conversation content. The `ShareDeletedListener` listens for skill and knowledge base share deletion events: for skill shares it uses `RemoveSkillSourcesFromThreadsUseCase` and `RemoveKnowledgeBaseAssignmentsByOriginSkillUseCase` to clean up assignments that were attached via the revoked skill; for KB shares it uses `RemoveDirectKnowledgeBaseFromThreadsUseCase` to remove direct KB assignments — targeting only users who lost access (resolved via `ShareScopeResolverService.resolveLostAccessUserIds`). The `ThreadMapper` was refactored to use private helper methods (`mapModel`, `mapSourceAssignments`, `mapMcpIntegrationIds`, `mapKnowledgeBases`, `mapMessages`) for readability and to support the new `knowledgeBases` field. The `LocalThreadAssignmentsRepository` service handles all thread assignment persistence operations — source assignments, knowledge base assignments, MCP integrations, and the thread-scoped stale-assignment discovery used by scheduled cleanup — extracted to keep the main `LocalThreadsRepository` focused on core thread CRUD. Single-thread reads load independent relations with TypeORM's query strategy so messages, knowledge-base assignments, and MCP integrations do not multiply each other into a Cartesian result set. Source assignments use a dedicated joined query because TypeORM's nested query strategy fetches but fails to attach `DataSourceDetailsRecord` entities. Citation retrieval instead uses `FindThreadCitationContextUseCase` and one owner-scoped projection query that returns only workspace, source-assignment, and knowledge-base-assignment identifiers, avoiding message loading and token counting. Cross-module reachability (skill/agent/KB) is handled by the sources module, not here. The HTTP layer exposes `POST /threads/:id/knowledge-bases/:knowledgeBaseId` (add) and `DELETE /threads/:id/knowledge-bases/:knowledgeBaseId` (remove), both returning 204 No Content. MCP integrations are exposed the same way via `ThreadMcpIntegrationsController`: `POST /threads/:id/mcp-integrations/:mcpIntegrationId` (add) and `DELETE /threads/:id/mcp-integrations/:mcpIntegrationId` (remove), both 204. `AddMcpIntegrationToThreadUseCase` validates the integration exists in the caller's org (via the mcp module's `GetMcpIntegrationsByIdsUseCase`, throwing `McpIntegrationNotFoundError` otherwise) and deduplicates; `RemoveMcpIntegrationFromThreadUseCase` is idempotent when the integration is not assigned. The `GetThreadResponseDto` and `GetThreadDtoMapper` include the `knowledgeBases` array (as `KnowledgeBaseSummaryResponseDto`) and the `mcpIntegrations` array (as `McpIntegrationSummaryResponseDto` with `id`, `name`, and marketplace `logoUrl`); integration summaries are resolved in `ThreadsController.findOne` (not in `FindThreadUseCase`, which is on the run-execution hot path). The module integrates with **messages** for conversation content storage, **models** for model selection per thread, **agents** for agent-bound conversations, **sources** for attaching RAG data and deleting stale direct thread sources, **knowledge-bases** for attaching org-scoped knowledge bases to threads, **mcp** for validating MCP integrations before attaching them to threads (via `GetMcpIntegrationsByIdsUseCase`), **runs** which execute within thread context, **shares** indirectly through skill share deletion events, and **IAM** (users, teams) for resolving which users lost access on share revocation.

Domain events are defined in `application/events/`: `ThreadMessageAddedEvent` records message activity, while `ThreadDeletionRequestedEvent` lets listeners register cleanup before a thread row is removed. Each event exposes a static `EVENT_NAME` string for type-safe listener registration.

Per-thread object-storage cleanup (message-image attachments and generated-image blobs) is prefix-based: thread blobs live under `<orgId>/<threadId>/` and `generated-images/<orgId>/<threadId>/`, so `DeleteThreadUseCase` deletes the thread row first and then best-effort purges those prefixes via the storage module's `PurgeStoragePrefixesUseCase` (a failed delete never costs a surviving thread its blobs; a failed purge only leaks orphans, which the org-level purge sweeps on org deletion). `ThreadsUserDeletionRequestedListener` follows the two-phase deletion contract (`DeferredCleanupEvent`): on `UserDeletionRequestedEvent` it resolves the user's thread ids while the rows still exist and defers a prefix purge (`<orgId>/<threadId>/` and `generated-images/<orgId>/<threadId>/` via the storage module's `PurgeStoragePrefixesUseCase`) that the users module runs only after the row delete succeeds. It also resolves the ids of the sources uploaded directly into those threads (`ThreadsRepository.findDirectSourceIdsByUserId`) and defers `DeleteUnreferencedSourcesUseCase`: sources have no owner FK, so the cascade only drops their assignment rows and the stale-source sweep, which starts from assignments, would never reach their indexes or retained originals. Lookup failures are logged, not thrown, so deletion is never blocked.

Every thread has exactly one **origin** (`domain/thread-origin.ts`), a value object with one variant per kind, each carrying only its own details: `chat` (the default), `routine` (`routineId`, the routine whose run created it), `notification` (`notificationId`, the notification a "Chat about this" chat discusses) and `release_note` (`releaseNoteId`, the product update a chat was started from). Persistence keeps the kind in the `origin` enum column and the details in the `routineId`, `sourceNotificationId` and `sourceReleaseNoteId` columns (FKs to routines, notifications and release notes, ON DELETE SET NULL: deleting the routine, notification or release note keeps the thread and its kind and drops only the link); check constraints allow each detail column only on threads of its own kind, and `ThreadMapper` builds the origin from these columns. `CreateThreadCommand` takes an optional `origin` (a plain chat without one); routine execution passes `routine`, and `CreateThreadUseCase` stores the command's `title` (routine threads are named by the routines module, never generated) and, before anything is written, checks a notification origin's id with the notifications module's `FindNotificationUseCase` (another user's notification is a 404) and a release-note origin's id with the release-notes module's `FindReleaseNoteUseCase` (a missing note is a 404). The HTTP contract still has the flat fields: `POST /threads` maps `sourceNotificationId` to a `notification` origin and `sourceReleaseNoteId` to a `release_note` origin (both at once is a 400), and the list and detail responses derive `type` (`routine` for a routine thread, `chat` otherwise), `routineId`, `sourceNotificationId` and `sourceReleaseNoteId` from the origin (`presenters/http/mappers/thread-origin.mapper.ts`; the `ThreadType` enum lives in the presenter). "Routine thread" means `origin = routine` everywhere: `GET /threads` takes an optional `type` filter that the repository applies as `isRoutine` (`type=chat` lists every thread that is not a routine thread, so notification and release-note chats stay in the sidebar) and an optional `routineId` filter (the threads of one routine's runs, for the routine detail page; like every list filter it narrows the current user's threads, so another user's routine yields none). The origin only decides display and the run context; a user message in a routine thread runs as a normal chat. The migrations `AddOriginToThreads`, `BackfillThreadOrigin` and `ReplaceThreadTypeWithOrigin` (AYC-1986) replaced the former `type` column: routine threads became `routine`, chats with a live notification link `notification`, everything else (including chats whose notification was already deleted) `chat`; they refuse to run while a thread has both a routine and a notification. `AddReleaseNoteThreadOrigin`, `BackfillReleaseNoteThreadOrigin` and `CheckReleaseNoteThreadOrigin` then add the `release_note` kind, give chats with a release-note link that origin (refusing threads that already have another origin's link) and add its check constraint. Chat search skips nudge text (`isNudge`) as it skips skill instructions.

Threads can be filed under a **workspace** ("Projekt", see the workspaces module): `Thread.workspaceId` is nullable, `AssignThreadToWorkspaceUseCase` moves a thread in or out of one (`PATCH /threads/:id/workspace`, `null` detaches) and validates the target through the workspaces module's exported `AssertWorkspaceReadAccessUseCase` so a chat cannot be filed into a workspace the caller is not a member of — the FK alone would accept it. `FindAllThreadsQuery` gained a `workspaceId` filter. Chats stay private to their creator, and a workspace chat is reachable only while its creator is a member of that workspace (`workspace_members`). The condition sits in the persistence queries (`queries/personal-or-member-workspace.ts`), so every user-scoped read and write answers a non-member like a missing chat: lists and the workspace filter, detail, messages and images, runs and AI context, sources and citations, renaming, moving, knowledge-base, MCP and source assignments, and deletion. The chat keeps its `workspaceId` and becomes reachable again once its creator is added back; personal chats are unaffected. **Past chats (AYC-1820).** `FindPastChatsUseCase` and `FindPastChatUseCase` (exported, no HTTP endpoint) give a chat run the current user's earlier chats for the `chat_list`/`chat_read` tools. A `PastChatScope` names the run's own chat, which is never included, and its workspace: a workspace chat sees only that workspace's chats, any other chat all of the user's. Anonymous chats and routine threads (`origin = routine`) are never included; notification chats are, and the persistence query (`queries/past-chats.ts`) applies the same creator and workspace-membership condition as every other user-scoped read. The list is ordered by `COALESCE(lastActivityAt, createdAt)` and then ID, so pages never overlap, and an optional `[from, before)` range keeps chats with a user or assistant message in it. A chat outside the scope raises the same `ThreadNotFoundError` as a missing one; the single chat is loaded with its messages in creation order. `GrepPastMessagesUseCase` (AYC-1821, for `chat_grep`) starts from the same chats and reaches their messages through the `(threadId, createdAt)` index: user and assistant messages created in an optional `[from, before)` range whose searchable text matches a case-insensitive PostgreSQL regular expression (`~*`), newest first, one row per message, with the message's chat-wide number (counted like `findPastChat` orders messages) and an excerpt of up to 300 characters starting 100 before the first match (`regexp_instr`) of the first matching block. Which text counts is shared with the sidebar search (`queries/searchable-message-text.ts`: text blocks that are neither skill instructions nor nudges); the sidebar search still matches it with `ILIKE`. No index serves the regex: the statement timeout bounds a slow pattern. PostgreSQL's rejection of a pattern (`2201B`) becomes `InvalidPastMessagePatternError` with its reason, a cancelled statement (`57014`) `PastMessageSearchTimeoutError`. Two system paths stay scoped to the creator only: `updateModel` (replacing a deleted model) and `delete`, which `ThreadDeletionService` runs after the caller decided access. `DeleteThreadUseCase` decides it through the membership-scoped lookup; `DeleteExpiredThreadUseCase`, used by data retention, deletes an expired chat whether or not its creator is still a member. Thread favorites are owned by the favorites module; threads expose no pin state or pin-specific endpoint. `DeleteThreadUseCase` emits `ThreadDeletionRequestedEvent` before deleting the row and runs deferred cleanup afterward, allowing favorites to remove the reference without either module importing the other. Deleting a workspace deletes its threads through the `threads.workspaceId` ON DELETE CASCADE, while `ThreadsWorkspaceDeletionRequestedListener` uses the same two-phase cleanup contract to purge object-storage prefixes that the cascade cannot reach and to remove pinned-thread favorite rows for the cascaded chats (which never emit `ThreadDeletionRequestedEvent`). The dependency runs threads → workspaces and threads → favorites; workspaces and threads do not import each other through favorites, so favorites can resolve both modules without a cycle.

**Chat files for MCP tools (AYC-1878).** `ResolveThreadFileUseCase` (exported, no HTTP endpoint) turns a source ID named in a chat into the file object that the OpenAI Apps SDK `openai/fileParams` convention hands to an MCP tool: `{ download_url, file_id, mime_type, file_name }`. It loads the thread through the user-scoped `FindThreadUseCase` and accepts only a source the user attached to that thread: a skill's assignment (`originSkillId`) raises `ThreadFileAddedBySkillError`, and a source without a stored original (`storageKey` null, e.g. uploads through the legacy multipart endpoint) raises `ThreadFileNotStoredError`. An unknown ID, a file of another thread and another user's thread all raise the same `ThreadFileNotFoundError`, so nothing tells them apart. `file_id` is the source ID; `file_name` and `mime_type` describe the stored original (`Source.storedOriginal()`), so a sheet source yields its workbook. `download_url` is a GET signed through the storage module's `PresignDownloadUseCase` with a 5-minute expiry and a 2-minute signing window, so a retry within the window gets the identical file object. Access is checked when the URL is issued, not when it is fetched. The URL is a bearer credential and is never logged or put into error metadata.

For anonymous threads, `ThreadsController.findOne` embeds the thread's PII mask dictionary (via the thread-pii-masks module's `GetThreadPiiMasksUseCase`), and `POST /threads/:id/pii-masks/:maskId/unmask` (AYC-807) lets the thread owner permanently unmask one dictionary entry — the controller asserts ownership through `FindThreadUseCase` before delegating to `UnmaskThreadPiiMaskUseCase` and returns the full updated dictionary.

The threads module also manages generated images produced during conversations. The `GeneratedImage` entity represents an AI-generated image linked to a thread, stored via the `GeneratedImagesRepository` port (implemented by `LocalGeneratedImagesRepository`). `SaveGeneratedImageUseCase` persists a generated image record, and `DownloadGeneratedImageUseCase` checks thread ownership and returns the image bytes as a stream (refusing stored content types outside the image allow-list). `DownloadReferenceImagesUseCase` returns raw image bytes from a thread for use as image-generation references: previously generated images resolved by ID plus specific uploaded message images resolved by `(messageId, index)` refs, capped at 16 combined — the provider image-edit API's per-request limit. The `GeneratedImagesController` streams generated images with the stored allow-listed `Content-Type`, `Content-Disposition: inline` and `X-Content-Type-Options: nosniff`, mirroring `MessageImagesController`. Error classes `GeneratedImageNotFoundError` and `GeneratedImageSaveFailedError` handle failure cases for image lookup and persistence respectively.

**Future work:** MCP integrations on threads currently use a bare `@ManyToMany` join table (`thread_mcp_integrations`) without provenance tracking. When user-group-scoped MCP integration access is added, this table should be promoted to a proper entity (like `ThreadSourceAssignmentRecord`) with an `originSkillId` (or similar provenance) column, following the same pattern used for source assignments. This will enable the same cleanup-on-revocation behavior for MCP integrations.

Persistence adapters participating in synchronous `@Transactional()` paths resolve repositories through the ambient CLS transaction host at call time, with default-repository fallback for callers outside CLS. See [transaction enrollment](../../../TRANSACTIONS.md) for the convention and review checklist.

Chat search matches titles and persisted user/assistant text blocks case-insensitively, within the existing owner and workspace scope. System, tool, thinking, image metadata, and skill instructions are excluded. A correlated message EXISTS predicate preserves thread pagination and avoids duplicate results.

Source assignments are unique per `(threadId, sourceId)` at the database level. The application duplicate check provides a fast 409 response; the database constraint also rejects concurrent duplicate inserts, which map to the same `SourceAlreadyAssignedError`.

`GET /threads/:id/sources/progress` authorizes the thread through `GetThreadSourcesUseCase` before reading queue-derived source progress.
