Resource Ownership
Shared owner model for resources owned by a user, a workspace, a team or the organization.

Skills and knowledge bases are owned by exactly one of a user, a workspace, a team or the organization. This module holds the parts of that model the resources share, so each resource module keeps only its own domain subclasses (personal, workspace, team, org) and permissions. It has no Nest module: it provides types, an abstract application service and persistence helpers that the resource modules build on.

- `application/models/resource-owner.ts`: `ResourceOwner` (`personal | workspace | team | org`) and `TransferableResourceOwner`, the owners a resource can be moved between (workspace resources stay put). The per-resource owner types (`SkillOwner`, `KnowledgeBaseOwner`, …) alias them.
- `application/services/collective-resource-access.service.ts`: `CollectiveResourceAccessService`, the base of the per-resource collective access services (`CollectiveSkillAccessService`, `CollectiveKnowledgeBaseAccessService`). A subclass supplies the resource's permissions (`manage`, `team`, `org`), its not-found error and how to read the team or org owner from the entity. The policy itself stays in the teams module's `GetCollectiveOwnerAccessUseCase`; the base class only maps its result: not readable → the resource's not-found error (404), readable but not manageable → `UnauthorizedAccessError` (403), and `requireManage` forbids rather than hides for resources that do not exist yet.
- `infrastructure/persistence/single-owner-check.decorator.ts`: `@SingleOwnerCheck('<table>')` declares `CHK_<table>_single_owner` as `num_nonnulls("userId", "workspaceId", "teamId") + "isOrgOwned"::int = 1`. It assumes the knowledge-base column shape: `orgId` is the row's tenant and always set, organization ownership is the `isOrgOwned` flag.
- `infrastructure/persistence/collective-owner.db-query.ts`: `whereCollectiveOwner(query, alias, owners)`, the team/org owner condition for tables of that shape. Org ownership is always matched together with the organization ID, so a query without its own tenant filter can never reach another organization; omitting `orgId` leaves org-owned rows out.

Skills use a different representation (a nullable `orgId` set only for org-owned skills, constraint `num_nonnulls("userId", "workspaceId", "teamId", "orgId") = 1`) and therefore keep their own constraint and owner condition (`local-collective-skill.finder.ts`). Moving skills onto this shape needs a migration and is part of AYC-1780, which also moves the remaining owner logic (read/write access dispatch by owner type, owner-change rules) here.
