Recordings
Meeting recordings owned by a user, a workspace, a team or the organization

A recording has a name, an organization (`orgId`), exactly one owner, the user who created it (`createdByUserId`, null once that user is deleted), timestamps, at most one uploaded audio file with its transcript, and the summary generated from that transcript. The module is behind `FEATURE_RECORDINGS_ENABLED` (`recordingsEnabled`, off by default): with it off, every `/recordings` route returns 404 and no instance generates summaries (queued ones wait), while the permissions, the data and the deletion listeners stay.

**Ownership.** The domain subclasses `PersonalRecording` (`userId`), `WorkspaceRecording` (`workspaceId`), `TeamRecording` (`teamId`) and `OrgRecording` form the `Recording` union; `CollectiveRecording` is team or org, `TransferableRecording` every owner but a workspace. Persistence uses the shared owner shape from `src/domain/ownership/`: `@SingleOwnerCheck('recordings')` (one of `userId`, `workspaceId`, `teamId` or `isOrgOwned`) and `whereCollectiveOwner` for team and org rows. `application/models/recording-owner.ts` aliases the shared `ResourceOwner` types and builds the recording for an owner (`recordingOwnedBy`), which create and owner change share.

**Access.** `RecordingAccessService` decides from the persisted owner, after checking the organization:

- Personal: only the owner reads and manages.
- Team and org: `CollectiveRecordingAccessService` (a `CollectiveResourceAccessService` with `manage_recordings`, `manage_team_recordings`, `manage_org_recordings`) applies the teams module's `GetCollectiveOwnerAccessUseCase`: members of the team or organization read; managing also takes `manage_recordings` plus the team permission as resolved for the user's team role, or the org permission.
- Workspace: the exported workspace read and write access use cases.

Unreadable recordings are `RECORDING_NOT_FOUND` (404); readable but unmanageable team and org recordings are forbidden (403). `requireCreate` is for recordings about to exist for, or move to, an owner: an unmanageable team or organization is forbidden rather than hidden. Every managing route also requires `manage_recordings` (`@RequirePermission`).

**Audio and transcript.** The audio is a source of the sources module: a `FileSource` that keeps the retained original (`storageKey`), the formatted transcript text, its search index and the transcript segments, and points at its recording through `sources.recordingId` (unique, `ON DELETE CASCADE`). `CreateRecordingUploadUseCase` reserves a direct upload (target type `recording`) after `requireWrite`, only while the recording has no audio (`RECORDING_AUDIO_ALREADY_UPLOADED`, 409); the sources module accepts only audio (MP3, M4A, WAV, WebM) up to `AUDIO_MAX_UPLOAD_BYTES` and a permitted embedding model, so a doomed file is refused before bytes move. An upload that passes every check is charged to the uploader's recording fair-use quota (`QuotaType.FAIR_USE_RECORDINGS` through the quotas module's `CheckQuotaUseCase`, passed as the session's `admit` callback; default 5 per hour, set by super admins, skipped for usage-based subscriptions) before the session is saved; over the limit the upload is refused with `QUOTA_EXCEEDED` (429). Abandoned or failed uploads keep their charge. `CompleteRecordingUploadUseCase` runs `CompleteSourceUploadUseCase` and, in its transaction, locks the recording and attaches the source (`RecordingRepository.attachAudio`, guarded by `NOT EXISTS` and the unique index). The upload queueing marks recording jobs `keepTranscriptSegments`, so document processing transcribes them in one request with diarization (`TranscribeRecordingUseCase`), stores the timed segments with the provider's speaker label apart from the text and indexes whole speaker turns as chunks whose meta carries the time range (see the sources and transcriptions summaries). The recording's status comes from its audio source and summary (`recordingStatusOf` in `application/models/recording-details.ts`): no audio `uploading`, `PROCESSING` `transcribing`, `READY` `summarizing` while the summary is queued or running and `ready` otherwise (summary generated or failed); responses carry the summary only from then on, `FAILED` `failed` with the source's `processingErrorCode` as `failureCode` (`RECORDING_TOO_LONG` above `AUDIO_MAX_DURATION_SECONDS` or when the provider refuses it). Transient failures are retried by the document queue; a terminal one stays until the user deletes the recording and uploads again. `GetRecordingTranscriptUseCase` returns the segments as speaker turns (`toTranscriptTurns`: consecutive segments of one speaker merged, speakers numbered by first appearance) after `requireRead`. `RecordingDetailsService` adds the creator's name and the audio to list and detail results, one lookup each.

**Summary.** Every recording is summarized ("Protokoll") with one hard-coded template (`application/models/recording-summary-prompt.ts`: subject, participants as speaker labels, topics, decisions, action items with the person if named, open points; written in the language of the transcript; speaker labels are not names). One row per recording in `recording_summaries` (`RecordingSummary`, `RecordingSummaryRepository`; FK cascade with the recording; `triggeredByUserId` and `modelId` set null when their user or model is deleted) holds the run (`runId`, status `pending`/`running`/`ready`/`failed`), who it is billed to, the Markdown `content`, the model's id and display name, `generatedAt` and the `failure` reason. Every write is a conditional update on the run and its state, so a superseded, finished or deleted run writes nothing.

- _Trigger._ `CompleteRecordingUploadUseCase` creates the first run (`pending`, billed to the uploader) in the transaction that attaches the audio, so the recording reads as `summarizing` from the moment its transcript is ready and the run survives the uploader's deletion (`triggeredByUserId` null). `DocumentProcessingConsumer` emits the sources module's `TranscriptReadyEvent` once the audio turns READY, in whichever process transcribed it. `RecordingSummaryTriggerModule` (imported by `IngestionConsumersModule`, so it runs in the API or the separate ingestion worker) listens (`RecordingsTranscriptReadyListener`) and `StartRecordingSummaryUseCase` finds the waiting run (`findPendingForAudio`) and has `RecordingSummaryScheduler` queue its job; a job that cannot be queued, or whose uploader was deleted, fails the run (`SUMMARY_FAILED`), so a manager can try again. A process that dies between the READY update and the listener leaves the run pending (no sweep yet).
- _Queue._ Jobs go to their own BullMQ queue `recording-summary` (`RecordingSummaryQueueModule`, job id = run id, 3 attempts with backoff), apart from document processing. `RecordingSummaryConsumer` runs in the API (`RecordingsModule`) with `RECORDING_SUMMARY_CONCURRENCY` (default 2), only while `FEATURE_RECORDINGS_ENABLED` is on, wraps every attempt in `observeJob` and acts as the billed user (`orgId`, `userId` in the context). The queue is registered with queue inspection and queue telemetry.
- _Generation._ `GenerateRecordingSummaryUseCase` claims the run, then `RecordingSummaryWriter` resolves the model when the job runs (models module's `ResolveRecordingSummaryModelUseCase`: the admin's summary model, else the org default), formats the transcript turns with their speaker labels, refuses a transcript that does not fit into the model's context window with room for the summary (`TRANSCRIPT_TOO_LONG`, counted with the token counter) or has no speech (`TRANSCRIPT_EMPTY`), admits the call through `InferenceAdmissionGuard.ensureModelCallAllowed` for the billed user (org budget, personal and team credit limits; fair-use message quotas do not apply, and neither does the recording upload limit) and records its usage for that user (`CollectUsageAsyncService.collectCritical`; a paid call reporting no usage hands out no summary). The text is stored first (`saveContent`), so an attempt that fails later indexes it without generating and billing it again. The sources module's `IndexTranscriptSummaryUseCase` then indexes it under the audio source, in chunks whose meta is `{ kind: 'summary' }` (transcript chunks carry `start`/`end`/`speakers` instead), and the run is marked ready. A recording deleted meanwhile stops the run at its next write; the FK cascades remove its summary, chunks and index entries, so nothing is recreated.
- _Failure._ Expected failures (application errors below 500: no permitted model `NO_SUMMARY_MODEL`, org budget `CREDIT_BUDGET_EXCEEDED`, personal or team limit `CREDIT_LIMIT_EXCEEDED`, `TRANSCRIPT_TOO_LONG`, `TRANSCRIPT_EMPTY`) fail the run at once; other errors are retried and fail it after the last attempt (`PROVIDER_ERROR` for provider and inference failures, else `SUMMARY_FAILED`), via `FailRecordingSummaryUseCase`. Recording and transcript stay.
- _Try again._ `RetryRecordingSummaryUseCase` (`requireWrite`, so readers get 403) starts a new run of a failed summary billed to the caller (`restartFailed`, conditional on `failed`, keeping a text already generated); asking again while a run is queued or running starts nothing, and a generated summary is never replaced (`RECORDING_SUMMARY_NOT_RETRYABLE`, 409).

**Use cases.** `CreateRecordingUseCase` (any owner), `ListRecordingsUseCase` (personal scope: the user's own plus readable team and org recordings in one query; workspace scope: one workspace after read access), `FindRecordingUseCase`, `RenameRecordingUseCase`, `ChangeRecordingOwnerUseCase` and `DeleteRecordingUseCase`. List and find return the creator's name (`RecordingCreatorNameService`, through the users module). Rename, owner change and delete lock the row. An owner change moves between the caller, a team and the organization, needs the right to manage both owners, keeps id, creator and creation date, and rejects workspace recordings with `RECORDING_OWNER_CHANGE_NOT_ALLOWED` (only after access is checked).

**Deletion.** Rows go with their owner by FK cascade: deleting a user deletes their personal recordings and, with the workspaces they own, those workspaces' recordings; team and org recordings they created stay with `createdByUserId` set to null. Deleting a team, workspace or organization deletes its recordings. `RecordingCleanupService` is where every deletion path ends: `DeleteRecordingUseCase` calls it after its commit, and the user, team, workspace and organization deletion listeners snapshot the affected recordings before the cascade and defer it until the owner's row is gone. The FK cascade from the recording removes its audio source with the transcript text, segments and index entries; `RecordingCleanupService` snapshots the audio (`snapshot`, before the delete) and afterwards runs `CleanupSourceProcessingUseCase` per organization, which cancels a queued or running transcription, purges its processing results and removes the uploaded original once nothing references it. Listener failures are logged and never block the deletion.

**HTTP.** `RecordingsController` at `/recordings`: `POST /` (`ownerType` `personal`, `workspace` with `workspaceId`, `team` with `teamId`, or `org`), `GET /?ownerType=personal|workspace[&workspaceId=]`, `GET /:id`, `GET /:id/transcript` (speaker turns), `PATCH /:id` (rename), `PATCH /:id/owner` (`personal`, `team` with `teamId`, or `org`) and `DELETE /:id`. `RecordingUploadsController`: `POST /:id/uploads` and `POST /:id/uploads/:uploadId/complete` (both `manage_recordings`); the bytes go through the generic `/source-uploads/:id/sign` endpoints. `RecordingSummaryController`: `GET /:id/summary` (the Markdown of a generated summary for readers, else `RECORDING_SUMMARY_NOT_FOUND`) and `POST /:id/summary/retry` (`manage_recordings`). Responses carry `ownerType`, `workspaceId` or `teamId`, `creatorName`, `status`, `failureCode` (failed only), `summary` (`status` `summarizing`/`ready`/`failed`, with `modelName` and `generatedAt` when ready or `failureCode` when failed; absent until the transcript is ready) and timestamps. Every route is behind `@RequireFeature(FeatureFlag.Recordings)`.

**Wiring.** `RecordingsModule` imports `LocalRecordingRepositoryModule` (which also registers `SourceRecord` for the audio link and the summary repository), `RecordingSummaryQueueModule`, `SourcesModule`, `ModelsModule`, `QuotasModule`, `UsageModule`, `TokenCounterModule`, the transcription config, `ContextModule`, `TeamsApplicationModule`, `UsersModule` and `WorkspacesModule`. Transcription, and with it the summary trigger (`RecordingSummaryTriggerModule`), runs where the document consumers run (`IngestionConsumersModule`: the API, or the separate ingestion worker). `local-recording.repository.integration.spec.ts` runs the real migrations and proves the access query, the single-owner check, the deletion cascades (including the audio and its segments), one audio per recording and the permission backfill; `local-recording-summary.repository.integration.spec.ts` proves one waiting run per recording found by its audio, that only the current run writes and only once, the restart of a failed summary and that a deleted recording's run writes nothing.
