Content Retrieval
Extract content from files, URLs, and internet search results

Retrievers fetch and extract text content from external sources: parsing uploaded files (PDF, documents, audio), scraping web URLs, and performing internet searches for real-time information.

Provider-failure classification (AYC-538): the Mistral OCR handler wraps transport failures, upstream 5xx/504, and OCR 4xx into the shared `ProviderUnavailableError` family from `src/common/errors`, so Mistral outages group into stable AppSignal incidents per failure class. Three kinds of 4xx are excluded: 401/403 stay `FileRetrieverUnexpectedError` (an auth-config bug of ours must alert on first occurrence), and rejections Mistral attributes to the document itself stay document errors — `document_parser_too_many_pages` → `TooManyPagesError` (422, the actionable page-cap message; `PreflightCheckUseCase` only catches this upfront for direct PDF uploads with readable metadata) and `invalid_request_file` → `UnprocessableDocumentError`, because a corrupt file never succeeds on retry and must not be presented as an outage. `UnprocessableDocumentError` (422) is the shared classification for "we cannot read this document" — the Gotenberg converter uses it for a 400 rejection too — and its status is what makes `isExpectedFailure` skip AppSignal and `classifyJobFailure` settle the source without further attempts. `FileRetrievalFailedError` (500) is reserved for failures on our side of the boundary: Gotenberg unreachable or timing out, an empty OCR response. URL retrieval deliberately does NOT use that family — a dead customer URL is not a provider outage — but `UrlRetrieverRetrievalError` metadata carries the transport classification (failure class, errno, host) for debuggability.

The retrievers module is organized into three sub-modules: **file-retrievers**, **url-retrievers**, and **internet-search-retrievers**. File retrievers extract text from uploaded documents with a hybrid strategy: the native PDF text layer is read locally first (`PdfTextExtractorPort` → `PiscinaPdfTextAdapter`, a piscina worker pool running pdfjs-dist off the event loop; pdf-lib counts pages for the preflight cap), and only text-poor pages (scans) go to Mistral OCR — uploaded once per document and OCR'd in 25-page batches via `PageOcrPort` sessions, with `skipPages`/`onBatchExtracted` on `RetrieveFileContentCommand` enabling checkpointed resume and per-page progress for the sources pipeline. The document conversion pipeline is unchanged (Gotenberg for DOCX/PPTX → PDF, whose output always has a text layer, so office documents never hit OCR); audio files are transcribed via the **transcriptions** module (`TranscribeUseCase`) which the file-retriever module imports. URL retrievers scrape and parse web page content using Cheerio, or return plain text content directly for `text/plain` responses (`RetrieveUrlUseCase`); URLs that resolve to a PDF (by `application/pdf` content type, or a generic/absent content type with a `.pdf` path) are downloaded and routed through the file-retriever pipeline (`RetrieveFileContentUseCase`), so both single fetches and crawls index PDF text. They can also crawl same-site links starting from a root URL up to a configurable depth, returning the aggregated pages in breadth-first order (`CrawlUrlUseCase` with `CrawlUrlCommand`, bounded by `UrlCrawlConstants`). Internet search retrievers query a configurable web-search provider (`INTERNET_SEARCH_PROVIDER`: Brave, default; or Staan, an EU/GDPR provider) for web results. Each sub-module follows the port/adapter pattern with handler registries for extensibility. Key entities include `FileRetrieverResult`, `UrlRetrieverResult`, `UrlCrawlPage`, `UrlCrawlResult`, and `InternetSearchResult`. `UrlRetrieverModule` exports both `RetrieveUrlUseCase` and `CrawlUrlUseCase`. The module integrates with **sources** for providing raw content from uploaded files and URLs, **rag** as the downstream consumer that indexes extracted content into vector stores, **transcriptions** for audio-to-text extraction, and **tools** where the internet_search and website_content tool handlers invoke retrievers during conversation execution.
