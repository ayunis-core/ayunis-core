Content Retrieval
Extract content from files, URLs, and internet search results

Retrievers fetch and extract text content from external sources: parsing uploaded files (PDF, documents, audio), scraping web URLs, and performing internet searches for real-time information.

Provider-failure classification (AYC-538): the Mistral OCR handler wraps transport failures, upstream 5xx/504, and unrecognized OCR 4xx into the shared `ProviderUnavailableError` family from `src/common/errors`, so Mistral outages group into stable AppSignal incidents per failure class. Exceptions are 401/403, which stay `FileRetrieverUnexpectedError` because they indicate our auth configuration, and deterministic document rejections: `document_parser_too_many_pages` → `TooManyPagesError`; `invalid_request_file`, `document_parser_invalid_file`, and all semantic 422 responses → `UnprocessableDocumentError`. These document errors do not retry OCR, regardless of Mistral's varying 422 response body (AYC-813). For PDFs, document rejection or a zero-page OCR result first tries the existing local parser when the caller allows it (AYC-1059); only nonblank extracted text counts as recovery, otherwise the original OCR error remains terminal. Page-limit, authentication, and operational failures do not enter this fallback. The local `pdf-parse` adapter normalizes typed and generic message-prefixed PDF.js document exceptions through one classifier, also recognizing the distinctive corrupt flate-stream signature; it emits stable parser reason metadata while preserving unknown parser failures as operational errors (AYC-810). The local parser receives a copied plain `Uint8Array`, avoiding Node Buffer's view-based slice semantics in bundled PDF.js. Callers handling untrusted files synchronously may disable local PDF parsing and bound the external OCR page window; their OCR rejection remains terminal without local parsing. Mistral bounding-box annotations transcribe visible text inside embedded images and append it to the corresponding page, making screenshot-based PDFs searchable without returning large base64 image payloads. Gotenberg 400 responses are document errors. A 503 whose body is Gotenberg's time-limit sentence ("The request exceeded the time limit…") becomes `DocumentConversionTimeoutError`, an `UnprocessableDocumentError`. The document queue retries it once after 30 s and fails the document when that attempt times out too (`classifyJobFailure` compares against the previous attempt's `failedReason`), so a timed-out document is converted at most twice; synchronous callers get the 422 at once (AYC-1641, AYC-1741). Blaming the document is only right while every replica runs with `--libreoffice-max-queue-size=1` (one request per replica, so none spends its time limit waiting behind another) and `--libreoffice-restart-after=1` (otherwise LibreOffice keeps working on a timed-out document and the next ones on that replica time out too); the bundled Compose files set both. Any other 503 becomes `DocumentConversionUnavailableError` with an actionable message and a distinct AppSignal code. `GotenbergConverterService` keeps at most `GOTENBERG_MAX_CONCURRENT_CONVERSIONS` conversions in flight per process through `ConversionGate`, so queued documents wait in the app, where no time limit runs. An occupied replica answers 429 at once; because Node's keep-alive would send a retry to that same replica, `sendToFreeReplica` resolves the service name to its replica addresses and tries each once, and only when all are occupied does the 429 become `DocumentConverterBusyError`, a `DocumentConversionUnavailableError`. The document queue retries that subclass after 60 s and 120 s instead of the standard 5 s and 10 s (`documentRetryDelayMs`), still within the shared three-attempt bound. Other Gotenberg outages stay `FileRetrievalFailedError`. URL retrieval deliberately does not use that family — a dead customer URL is not a provider outage — but `UrlRetrieverRetrievalError` metadata carries the transport classification (failure class, errno, host) for debuggability.

The retrievers module is organized into three sub-modules: **file-retrievers**, **url-retrievers**, and **internet-search-retrievers**. File retrievers extract text from uploaded documents using pluggable handlers (Mistral OCR, pdf-parse) and a document conversion pipeline (Gotenberg for DOCX/PPTX → PDF, then Mistral OCR for text extraction); audio files are transcribed via the **transcriptions** module (`TranscribeRecordingUseCase`) which the file-retriever module imports. Emails are flattened to a header block plus body: `.eml` in-process with `mailparser`, Outlook `.msg` through `MsgParserPort`, whose `PiscinaMsgParserAdapter` parses in a heap-capped (256 MB), 30-second piscina worker because a few KB of crafted CFBF can drive the parser into unbounded allocation (AYC-1003); a worker parse error, timeout or out-of-memory becomes `UnprocessableDocumentError`, while worker start-up failures are rethrown. URL retrievers scrape web pages using Cheerio and convert visible HTML blocks of the page's main content into line-addressable plain text while preserving block boundaries (AYC-1607: the outermost `<main>`/`[role=main]` elements, else the outermost `<article>`s, without nested navigation, asides, forms and dialogs; pages without a landmark, or whose landmark carries less than a third of the remaining text, drop navigation, header, footer, aside, form and dialog elements instead, keeping forms that contain headings or paragraphs (decided before chrome inside them is stripped) because ASP.NET WebForms pages wrap everything in one; if nothing remains the whole body is used; links are still collected from the whole page), or return plain text content directly for `text/plain` responses (`RetrieveUrlUseCase`); URLs that resolve to a PDF (by `application/pdf` content type, or a generic/absent content type with a `.pdf` path) are downloaded and routed through the file-retriever pipeline (`RetrieveFileContentUseCase`), so both single fetches and crawls index PDF text. Fetched PDFs are bounded on two axes (AYC-332): the download is capped while streaming by `URL_RETRIEVER_MAX_DOWNLOAD_BYTES` (25 MB, `UrlRetrieverContentTooLargeError` 413), and the buffered bytes then pass through `PreflightCheckUseCase` — the same `PROCESSING_MAX_PDF_PAGES` guard uploads get — so a small-but-thousand-page PDF is rejected with `TooManyPagesError` (422) before an expensive OCR job starts. A single fetch surfaces that error; discovered PDF files record their own failed status while their URL source remains ready. They can also crawl same-site links starting from a root URL up to a configurable depth, returning the aggregated pages in breadth-first order (`CrawlUrlUseCase` with `CrawlUrlCommand`, bounded by `UrlCrawlConstants`). Internet search retrievers query a configurable web-search provider (`INTERNET_SEARCH_PROVIDER`: Brave, default; or Staan, an EU/GDPR provider) for web results. Brave requests include `extra_snippets`, returned as `extraSnippets` on each result so the model can often answer without fetching the page. Each search request is aborted after 10 seconds or when the caller's signal (the run's cancellation) fires. Each sub-module follows the port/adapter pattern with handler registries for extensibility. Key entities include `FileRetrieverResult`, `UrlRetrieverResult`, `UrlCrawlPage`, `UrlCrawlResult`, and `InternetSearchResult`. `UrlRetrieverModule` exports both `RetrieveUrlUseCase` and `CrawlUrlUseCase`. The module integrates with **sources** for providing raw content from uploaded files and URLs, **rag** as the downstream consumer that indexes extracted content into vector stores, **transcriptions** for audio-to-text extraction, and **tools** where the internet_search and website_content tool handlers invoke retrievers during conversation execution.

PDF downloads within one active CLS request reuse successful extraction by organization, final URL, and SHA-256 of the fetched bytes (AYC-1348), so different URLs that resolve to the same document, or reads beyond the URL cache below, do not repeat OCR; changed bytes trigger fresh extraction. The cache retains at most four results of up to 2 MiB serialized each, shares in-flight loads, discards failures and oversized results, and bypasses caching without an active context. Weak request-context keys prevent cross-request reuse and require no replica coordination. In front of it, `RetrieveUrlUseCase` retrieves each URL at most once per CLS request — a chat run — through `UrlRetrievalCachePort` (`RequestUrlRetrievalCacheService`, AYC-1607), keyed by organization, requested URL and private-destination policy, so continuation pages and repeated reads of HTML, text or PDF URLs do not fetch again. The crawl gate still runs for the requested URL on every read, and again for a differing final (redirect) URL, so revoked grants take effect immediately. It keeps at most twelve results of up to 2 MiB serialized each, shares in-flight loads, and does not keep failures, so a retry fetches again. Both caches share the bounded `RequestScopedResultCache`.

Crawls collect up to 25 unique PDF links per crawl, separately from HTML traversal (AYC-1031). Discovery checks every visited page, including depth zero and pages at the final depth or HTML budget. PDF links are identified by a decoded `.pdf` path or an explicit PDF anchor media type, keep the link label (falling back to the filename), ignore fragments for deduplication, and are not subject to the HTML same-site filter or 25-page budget. The crawler returns their URLs without fetching them; the sources pipeline retrieves them through `RetrieveUrlUseCase`, retaining crawl-domain grants, redirect checks, download/page limits, and PDF parsing. Retrieval results distinguish actual PDFs from HTML responses so login pages cannot become ready PDF files.

Discovered PDF retrieval requires an explicit grant to the requesting organization for private or reserved destination addresses, including DNS answers and redirects. Public destinations use a separate dispatcher that validates DNS again at connection time to reject rebinding; approved intranet requests retain the normal transport. The existing ordinary URL/tool retrieval policy is unchanged.

The discovered-PDF destination guard decodes IPv4 embedded in the well-known NAT64 prefix before applying private/reserved IPv4 rules, during both initial destination admission and connection-time DNS checks. Public IPv4 through NAT64 remains allowed.

PDF OCR requests pass through `BatchedPdfOcrHandler`: `QpdfPdfBatcherAdapter` cuts the document with the `qpdf` command-line tool into valid PDFs bounded by pages and encoded bytes, and the batches of a document run in parallel under a per-process OCR semaphore (`OCR_MAX_CONCURRENCY`, AYC-1800). A document may use every slot, but it never has more batches waiting or running than there are slots, which bounds the batch bytes it holds and lets another document's batch in after one batch rather than after the whole document. When a batch fails no further batch starts, the ones already sent are awaited so their results are saved, and the first failure is thrown. One OCR attempt may take 120 s; failures are retried only while the batch is younger than 125 s (three retries for quick failures such as 429 and 5xx, one for a timeout), so a provider that stops answering fails a batch in about four minutes instead of eight and the queue's retry continues from the saved batches. `OCR_IMAGE_TEXT_ENABLED=false` leaves the image-text annotation out of the request. Original page numbers and image-text annotations are preserved. The optional processing context saves completed results in source-scoped MinIO checkpoints; converted Office files use the original upload identity so repeated conversions can reuse completed OCR. Uploaded recordings use `TranscribeRecordingUseCase`; microphone transcription keeps its original path. The document stays on disk while it is split (AYC-1729): the document consumer stages PDFs and office files in a temporary directory and passes a `LocalFile` (path, size, sha256) instead of bytes through `RetrieveFileContentCommand.localFile`, the page check counts pages with qpdf, office files are converted from and to disk (`DocumentConverterPort.convertFileToPdf`), and memory per job is bounded by the batch byte limit rather than the file size. Callers that still pass a buffer (chat reads, email attachments, crawled PDFs) are written to a work file and take the same path. Only the local pdf-parse fallback reads the whole document, when OCR is unavailable or rejected it. An encrypted document (empty-password protection from office suites) is rewritten by qpdf, so OCR receives readable pages; one that needs a password, or that qpdf cannot read, is an `UnprocessableDocumentError`, as is a saved batch that no longer parses (the batch is redone). A missing `qpdf` binary or a timeout is an ordinary error, never a document rejection. When the processing context has `onPagesExtracted`, the handler hands page texts on in document order, each batch as soon as every batch before it has answered, including batches restored from checkpoints (AYC-1813).
