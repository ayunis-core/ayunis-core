Content Retrieval
Extract content from files, URLs, and internet search results

Retrievers fetch and extract text content from external sources: parsing uploaded files (PDF, documents, audio), scraping web URLs, and performing internet searches for real-time information.

Provider-failure classification (AYC-538): the Mistral OCR handler wraps transport failures, upstream 5xx/504, and unrecognized OCR 4xx into the shared `ProviderUnavailableError` family from `src/common/errors`, so Mistral outages group into stable AppSignal incidents per failure class. Exceptions are 401/403, which stay `FileRetrieverUnexpectedError` because they indicate our auth configuration, and deterministic document rejections: `document_parser_too_many_pages` → `TooManyPagesError`; `invalid_request_file`, `document_parser_invalid_file`, and all semantic 422 responses → `UnprocessableDocumentError`. These document errors do not retry OCR, regardless of Mistral's varying 422 response body (AYC-813). For PDFs, document rejection or a zero-page OCR result first tries the existing local parser when the caller allows it (AYC-1059); only nonblank extracted text counts as recovery, otherwise the original OCR error remains terminal. Page-limit, authentication, and operational failures do not enter this fallback. The local `pdf-parse` adapter normalizes typed and generic message-prefixed PDF.js document exceptions through one classifier, also recognizing the distinctive corrupt flate-stream signature; it emits stable parser reason metadata while preserving unknown parser failures as operational errors (AYC-810). The local parser receives a copied plain `Uint8Array`, avoiding Node Buffer's view-based slice semantics in bundled PDF.js. Callers handling untrusted files synchronously may disable local PDF parsing and bound the external OCR page window; their OCR rejection remains terminal without local parsing. Mistral bounding-box annotations transcribe visible text inside embedded images and append it to the corresponding page, making screenshot-based PDFs searchable without returning large base64 image payloads. Gotenberg 400 responses are document errors, while 503 responses become `DocumentConversionUnavailableError` with an actionable message and a distinct AppSignal code. The converter performs one request per BullMQ attempt, leaving the shared three-attempt queue policy as the single retry bound instead of multiplying retries in the adapter. Other Gotenberg outages stay `FileRetrievalFailedError`. URL retrieval deliberately does not use that family — a dead customer URL is not a provider outage — but `UrlRetrieverRetrievalError` metadata carries the transport classification (failure class, errno, host) for debuggability.

The retrievers module is organized into three sub-modules: **file-retrievers**, **url-retrievers**, and **internet-search-retrievers**. File retrievers extract text from uploaded documents using pluggable handlers (Mistral OCR, pdf-parse) and a document conversion pipeline (Gotenberg for DOCX/PPTX → PDF, then Mistral OCR for text extraction); audio files are transcribed via the **transcriptions** module (`TranscribeUseCase`) which the file-retriever module imports. Emails are flattened to a header block plus body: `.eml` in-process with `mailparser`, Outlook `.msg` through `MsgParserPort`, whose `PiscinaMsgParserAdapter` parses in a heap-capped (256 MB), 30-second piscina worker because a few KB of crafted CFBF can drive the parser into unbounded allocation (AYC-1003); a worker parse error, timeout or out-of-memory becomes `UnprocessableDocumentError`, while worker start-up failures are rethrown. URL retrievers scrape web pages using Cheerio and convert visible HTML blocks into line-addressable plain text while preserving block boundaries, or return plain text content directly for `text/plain` responses (`RetrieveUrlUseCase`); URLs that resolve to a PDF (by `application/pdf` content type, or a generic/absent content type with a `.pdf` path) are downloaded and routed through the file-retriever pipeline (`RetrieveFileContentUseCase`), so both single fetches and crawls index PDF text. Fetched PDFs are bounded on two axes (AYC-332): the download is capped while streaming by `URL_RETRIEVER_MAX_DOWNLOAD_BYTES` (25 MB, `UrlRetrieverContentTooLargeError` 413), and the buffered bytes then pass through `PreflightCheckUseCase` — the same `PROCESSING_MAX_PDF_PAGES` guard uploads get — so a small-but-thousand-page PDF is rejected with `TooManyPagesError` (422) before an expensive OCR job starts. A single fetch surfaces that error; discovered PDF files record their own failed status while their URL source remains ready. They can also crawl same-site links starting from a root URL up to a configurable depth, returning the aggregated pages in breadth-first order (`CrawlUrlUseCase` with `CrawlUrlCommand`, bounded by `UrlCrawlConstants`). Internet search retrievers query a configurable web-search provider (`INTERNET_SEARCH_PROVIDER`: Brave, default; or Staan, an EU/GDPR provider) for web results. Each sub-module follows the port/adapter pattern with handler registries for extensibility. Key entities include `FileRetrieverResult`, `UrlRetrieverResult`, `UrlCrawlPage`, `UrlCrawlResult`, and `InternetSearchResult`. `UrlRetrieverModule` exports both `RetrieveUrlUseCase` and `CrawlUrlUseCase`. The module integrates with **sources** for providing raw content from uploaded files and URLs, **rag** as the downstream consumer that indexes extracted content into vector stores, **transcriptions** for audio-to-text extraction, and **tools** where the internet_search and website_content tool handlers invoke retrievers during conversation execution.

Repeated PDF URL reads within one active CLS request reuse successful extraction by organization, final URL, and SHA-256 of the fetched bytes (AYC-1348). Every read still checks crawl grants, redirect destinations, HTTP status, and download limits before reuse; changed bytes trigger fresh extraction. The cache retains at most four results of up to 2 MiB serialized each, shares in-flight loads, discards failures and oversized results, and bypasses caching without an active context. Weak request-context keys prevent cross-request reuse and require no replica coordination. HTML and plain text are not cached.

Crawls collect up to 25 unique PDF links per crawl, separately from HTML traversal (AYC-1031). Discovery checks every visited page, including depth zero and pages at the final depth or HTML budget. PDF links are identified by a decoded `.pdf` path or an explicit PDF anchor media type, keep the link label (falling back to the filename), ignore fragments for deduplication, and are not subject to the HTML same-site filter or 25-page budget. The crawler returns their URLs without fetching them; the sources pipeline retrieves them through `RetrieveUrlUseCase`, retaining crawl-domain grants, redirect checks, download/page limits, and PDF parsing. Retrieval results distinguish actual PDFs from HTML responses so login pages cannot become ready PDF files.

Discovered PDF retrieval requires an explicit grant to the requesting organization for private or reserved destination addresses, including DNS answers and redirects. Public destinations use a separate dispatcher that validates DNS again at connection time to reject rebinding; approved intranet requests retain the normal transport. The existing ordinary URL/tool retrieval policy is unchanged.

The discovered-PDF destination guard decodes IPv4 embedded in the well-known NAT64 prefix before applying private/reserved IPv4 rules, during both initial destination admission and connection-time DNS checks. Public IPv4 through NAT64 remains allowed.
