Content Retrieval
Extract content from files, URLs, and internet search results

Retrievers fetch and extract text content from external sources: parsing uploaded files (PDF, documents, audio), scraping web URLs, and performing internet searches for real-time information.

Provider-failure classification (AYC-538): the Mistral OCR handler wraps transport failures, upstream 5xx/504, and unrecognized OCR 4xx into the shared `ProviderUnavailableError` family from `src/common/errors`, so Mistral outages group into stable AppSignal incidents per failure class. Exceptions are 401/403, which stay `FileRetrieverUnexpectedError` because they indicate our auth configuration, and deterministic document rejections: `document_parser_too_many_pages` → `TooManyPagesError`; `invalid_request_file`, `document_parser_invalid_file`, `invalid_file` code `1901`, and 422 `Invalid file format` responses → `UnprocessableDocumentError`. These 422 document errors are terminal and do not retry. A successful zero-page OCR response first triggers the local `pdf-parse` fallback; it remains `UnprocessableDocumentError` only when local parsing also extracts no text. Gotenberg 400 responses are document errors, while 503 responses become `DocumentConversionUnavailableError` with an actionable message and a distinct AppSignal code. The converter performs one request per BullMQ attempt, leaving the shared three-attempt queue policy as the single retry bound instead of multiplying retries in the adapter. Other Gotenberg outages stay `FileRetrievalFailedError`. URL retrieval deliberately does not use that family — a dead customer URL is not a provider outage — but `UrlRetrieverRetrievalError` metadata carries the transport classification (failure class, errno, host) for debuggability.

The retrievers module is organized into three sub-modules: **file-retrievers**, **url-retrievers**, and **internet-search-retrievers**. File retrievers extract text from uploaded documents using pluggable handlers (Mistral OCR, pdf-parse) and a document conversion pipeline (Gotenberg for DOCX/PPTX → PDF, then Mistral OCR for text extraction); audio files are transcribed via the **transcriptions** module (`TranscribeUseCase`) which the file-retriever module imports. URL retrievers scrape and parse web page content using Cheerio, or return plain text content directly for `text/plain` responses (`RetrieveUrlUseCase`); URLs that resolve to a PDF (by `application/pdf` content type, or a generic/absent content type with a `.pdf` path) are downloaded and routed through the file-retriever pipeline (`RetrieveFileContentUseCase`), so both single fetches and crawls index PDF text. They can also crawl same-site links starting from a root URL up to a configurable depth, returning the aggregated pages in breadth-first order (`CrawlUrlUseCase` with `CrawlUrlCommand`, bounded by `UrlCrawlConstants`). Internet search retrievers query a configurable web-search provider (`INTERNET_SEARCH_PROVIDER`: Brave, default; or Staan, an EU/GDPR provider) for web results. Each sub-module follows the port/adapter pattern with handler registries for extensibility. Key entities include `FileRetrieverResult`, `UrlRetrieverResult`, `UrlCrawlPage`, `UrlCrawlResult`, and `InternetSearchResult`. `UrlRetrieverModule` exports both `RetrieveUrlUseCase` and `CrawlUrlUseCase`. The module integrates with **sources** for providing raw content from uploaded files and URLs, **rag** as the downstream consumer that indexes extracted content into vector stores, **transcriptions** for audio-to-text extraction, and **tools** where the internet_search and website_content tool handlers invoke retrievers during conversation execution.
