# OParl Module

Keeps a complete, current mirror of council information systems (Ratsinformationssysteme, RIS) that expose the [OParl](https://oparl.org) API 1.0/1.1. A super-admin adds a system by its URL; the mirror then holds all of its bodies' data, full history included, as rows of their own, and makes it searchable: the text of its documents and of its papers, meetings and agenda items, in chunks with a German full-text index and vectors (AYC-2059). Orgs that linked a body search and read it in chat (AYC-2061).

Everything here is behind the `oparlEnabled` feature flag (`FEATURE_OPARL_ENABLED`, off by default). With the flag off the HTTP routes answer 404, the sweep's schedule is removed, queued runs end without doing anything, and the mirrored data stays.

## Global data — an exception to org scoping

The mirror is installation-wide, keyed by the system URL: no table here has an `orgId`, and one system is mirrored once however many organizations use it. Mirrors are never deleted automatically. Organizations reach the data only through links to bodies (`oparl_body_links`, see Org links), which every org-facing access must check: the catalog of bodies (names and systems) for linking, and the reads of the chat tools (see Reading for chat), which look the links up on every call.

## Domain

- **`OparlSystem`** — the catalog entry and the OParl `System`: `url` (normalized by `normalizeOparlSystemUrl`: http(s), no credentials or fragment, no trailing slash; unique), `oparlId` (unique), name, vendor, product, version, `raw`, and its sync state: `nextSyncAt`, `lastDeltaSyncAt` / `lastFullSyncAt` (start of the last successful delta / initial import or full reconciliation), `lastRunStatus`, `lastRunFinishedAt`, `lastError`, `consecutiveFailures`. `health`: `pending` (nothing finished yet), `healthy`, `suspicious`, `failing` (by the last finished run).
- **`OparlSyncRun`** — `kind` (`initial` | `delta` | `full`), `status` (`running` | `succeeded` | `suspicious` | `failed`), `modifiedSince`, start, end, `error` and `stats` (pages, objects written and deleted per type, why a reconciliation removed nothing).
- **Schedule** (`oparl-sync-schedule.ts`) — initial import until one succeeded; then a full reconciliation when the last one is a week old, else a delta with `modified_since` = start of the last successful sync less an hour. A finished run is due again a day after it started; a failed one after 1, 2, 4 … hours (at most a day).
- **Reconciliation** (`oparl-reconciliation.ts`) — a full listing removes what it no longer contains only after it read every list without error and without skipping an object for lack of an ID, and only if no type loses more than 10 % of its rows, counting the rows that cascade from removed objects (memberships of a person, agenda items of a meeting, everything of a body); otherwise nothing is removed and the run is `suspicious`. A run abandoned by a lost worker is ended as failed by the next one, which also drops what it had listed.

## The mirror

All 11 OParl types besides `System` are tables of their own: `oparl_bodies`, `oparl_legislative_terms`, `oparl_organizations`, `oparl_persons`, `oparl_memberships`, `oparl_meetings`, `oparl_agenda_items`, `oparl_papers`, `oparl_consultations`, `oparl_files`, `oparl_locations`. Every row has its own UUID, a unique `(systemId, oparlId)`, `web`, `oparlCreated`, `oparlModified`, the object as received in `raw` (jsonb) and the columns of `OPARL_TYPE_SPECS` (`application/models/oparl-type-specs.ts`). Everything but bodies belongs to the body it was listed under (`bodyId`). Meetings are indexed by body and start, papers by body and date.

- **Stable IDs** — objects are upserted on their OParl ID (`INSERT … ON CONFLICT ("systemId", "oparlId") DO UPDATE`) and never deleted and re-inserted, so a row keeps its UUID for good (a later recording ↔ meeting link depends on it).
- **References** — a reference to one object is two columns, `<ref>OparlId` and the row `<ref>Id`; references to many are join tables (`oparl_meeting_organizations`, `…_participants`, `…_auxiliary_files`, `oparl_agenda_item_auxiliary_files`, `oparl_paper_related_papers`, `…_superordinated_papers`, `…_subordinated_papers`, `…_auxiliary_files`, `…_locations`, `…_originator_persons`, `…_originator_organizations`, `…_under_direction_of`, `oparl_consultation_organizations`) with `ownerId`, `targetOparlId` and `targetId`. The row is linked once the target is mirrored (`linkReferences`, after a body's lists and at the end of a run), so lists can arrive in any order. Back-references (a file's `paper`, a location's `meetings`) stay in `raw`; their forward references are mirrored.
- **Cascades** — deleting a system, a body or an object removes what depends on it: agenda items with their meeting, consultations with their paper, memberships with their person or organization, join rows with their owner. Other references are set to `NULL` and keep their OParl ID, so they are linked again if the object reappears.
- **Counts** — a RIS's lists may hold fewer objects than its objects embed (Sternberg's file list omits the files only attached to meetings and agenda items, which are real objects); those are mirrored too, so a type's count can exceed its list's `totalElements`. A RIS may also report an object as modified on every request (Sternberg's body location); it is then written on every sync.
- **Embedded objects** (agenda items in meetings, consultations in papers, memberships in persons, files and locations anywhere) are mirrored like listed ones, with the parent as their reference where they omit it. One object can arrive in several forms: a listed form is written when its original or references changed, or the row holds an embedded form (`fromListing`); an embedded form replaces a listed one only when newer by `modified`, and another embedded form also when it is new or, without `modified`, changed, so a shorter embedded form never overwrites the listed one back and forth. A second sync without remote changes writes nothing.
- **Persons without contact data, organizations without address** — `email`, `phone`, `location` and `locationObject` are removed from every person, and `location` and `locationObject` from every organization (for a small body such as an Ortsbeirat the RIS gives its chair's home; AYC-2066), also inside other objects' `raw`, before anything is stored; organizations have no location reference. Location lists also hold these addresses without marking them as such, so a listed location becomes a row only as the place of a body, meeting or paper (embedded locations are such places already), and a full reconciliation removes a location that is no longer one, though the location list still holds it. The location count is therefore lower than the location list's `totalElements` by the addresses it holds. The migration `RemoveOparlOrganizationLocations` removed organizations' addresses, and the locations only they referred to, from mirrors made before.
- **Files** — metadata (name, file name, MIME type, date, size, checksums, access/download URLs, license, master file); their text is read by the document jobs (see Search index).
- **Deletions** — an object reported with `deleted: true` (listed or embedded) is hard-deleted with its dependents.

## Sync

- **`OparlSyncService`** — the listing of a run: refreshes the system object, lists its bodies (`writeBodies`), then each body's lists in `OPARL_BODY_LISTS` order, two fetched at a time, locations last; page by page (`links.next`, resolved against the URL of the page it came from) through `OparlPageWriter.writePage`, which writes a page and what it embeds in one transaction (deduplicated per OParl ID, the listed form first). A run writes one page at a time, so two lists embedding the same objects never lock rows in opposite orders. A delta adds `modified_since` to each list; a list that answers it with 400 (Aarbergen's locations) is listed completely instead, with changes detected per object, while the other lists keep the filter — decided per list and per run, not remembered, so the next delta tries the filter again; a 404 on the first filtered page (Sternberg's answer for a list without changes) counts as no changes once the unfiltered list is confirmed to exist. A remote failure (unreachable, HTTP error, invalid JSON, a pagination loop) ends the listing and is reported as `listingError`, not thrown; an item without ID is skipped and counted (`invalidObjects`), so the listing goes on but is not complete. After each page the list's next URL is saved in the run's progress.
- **`RunOparlSyncUseCase`** — one run without a user: starts a run as the schedule says (ending a run left `running` by a lost worker as failed) or resumes the run its progress names. A delta or initial import whose listing stopped is `failed`; an initial import and a full reconciliation reconcile (see Domain), so one that is complete but skipped objects without ID is `suspicious`. Any failure is recorded on the run and the system, with the next attempt scheduled; it is not thrown. On shutdown it throws `OparlSyncInterruptedError` and leaves the run running.
- **`SyncDueOparlSystemsUseCase`** — the sweep: claims up to 100 due systems (`nextSyncAt <= now`, `FOR UPDATE SKIP LOCKED`, moving `nextSyncAt` six hours on, so a run lost with its queue is queued again then) and queues a run for each. It also queues the document job of every other system with document work left — files not read as of their current metadata (not failed ones, which later jobs retry) or, with an OParl embedding model, chunks without its vector — and no run queued or running (asked of the queue, not of `oparl_sync_runs`, whose `running` row a lost job leaves behind; the run's end queues the job), so a document job that failed for good is back within the sweep's interval.
- **`AddOparlSystemUseCase`** — normalizes the URL (`OPARL_INVALID_SYSTEM_URL` 400), answers 409 `OPARL_SYSTEM_ALREADY_EXISTS` for a URL already in the catalog (also for the same OParl ID, atomically), fetches it without retries and requires an OParl `System` (`OPARL_NOT_AN_OPARL_SYSTEM` / `OPARL_INVALID_RESPONSE` / `OPARL_REQUEST_FAILED` 422, `OPARL_HOST_BLOCKED` 400), lists its bodies and stores system and bodies in one transaction, then queues the initial import (if that fails, the sweep takes it: the system is due).
- **`ListOparlSystemsUseCase`** — every system with bodies, counts per type and the running run (`OparlSystemOverviews`, four queries however many systems).
- **`SyncOparlSystemNowUseCase`** — queues a run (`OPARL_SYSTEM_NOT_FOUND` 404).

## Search index

Platform work: no org context, nothing charged to an org (extraction, OCR and embeddings are platform costs).

- **`oparl_file_texts`** — one row per file once it was read: `status` (`extracted` | `skipped` | `failed`), `skipReason` (`too_large` | `too_many_pages` | `unsupported_type` | `unreadable`), `error`, `contentHash` (SHA-256 of the bytes), `pageCount`, the `pages` themselves (jsonb, for chunking again and reading a document page by page), `chunkCount`, `sourceFingerprint` (md5 of the metadata the content depends on: URLs, size, checksums, MIME type, `modified`), `attempts`, `readAt`. Goes with its file. A file is pending without a row, when its fingerprint changed, or when it failed fewer than three times and before the current job started. A file whose metadata is unchanged is not downloaded again; one whose bytes are unchanged (same hash) is not extracted again.
- **Reading a file** (`OparlFileTextReader`) — skipped without download for a declared size over the upload limit (25 MB, `MAX_SOURCE_FILE_SIZE_BYTES`) or a type whose text is not read (only PDF, Word/PowerPoint/OpenDocument text and presentations, plain text and HTML are); downloaded through `OparlHttpClient` (same SSRF guard, limiter and retries; stopped at 25 MB); PDFs pass the upload page limit (`PreflightCheckUseCase`, `PROCESSING_MAX_PDF_PAGES`). Text via `RetrieveFileContentUseCase` with `pdfTextLayerFirst` (the local text layer page by page when at least four in five pages carry text, else OCR; converted office files too) and `onBehalfOfPlatform`. Limits and documents the parser or OCR rejects, or without any text, are `skipped` with their reason; unreachable files and provider failures are `failed` (tried again by later jobs, up to three times per fingerprint); a failure keeps the text and chunks read before.
- **`oparl_chunks`** — `text` (1000 characters, 200 overlap, files page by page with `pageNumber`), `source` (`paper` | `meeting` | `agenda_item` | `file`), `ordinal`, references to `bodyId` (B-tree on `(bodyId, id)`), `paperId`, `meetingId`, `agendaItemId`, `fileId`, and `date` (the paper's date, the meeting's day in Europe/Berlin, or the file's date, else its paper's or meeting's). `searchVector` is generated as `to_tsvector('german', text)` with a GIN index. Vectors go in `embedding1024` / `embedding1536` / `embedding2560` (`halfvec`, by the model's dimensions; the others are cleared), each with a partial HNSW index (`halfvec_cosine_ops`, `WHERE … IS NOT NULL`); `embeddingModelId` names the model (search uses only vectors of the current one; deleting the catalog model sets it `NULL`). The GIN and HNSW indexes are created by the migration `CreateOparlDocumentTables` (TypeORM cannot express them; the record names them with `synchronize: false`).
- **References and deletes** — every reference cascades, so deleting a body, file, paper, meeting or agenda item removes its chunks. A file chunk's paper (the paper whose main file or attachment it is, or the paper of the consultation of the agenda item it belongs to), agenda item (resolution file or attachment) and meeting (invitation, protocols, attachment, or the agenda item's) are set (`oparl-documents-sql.ts`) when the file is chunked and again on every job, so a link that arrives later is picked up. A file whose chunks went with a deleted paper or meeting is chunked again from its stored pages.
- **Objects** (`OparlObjectIndexer`) — papers (reference, name, paper type), meetings (name) and agenda items (number and name, result, resolution text; HTML stripped) become chunks; `sourceHash` records the text they were cut from, so an unchanged object keeps its chunks and vectors.
- **Embeddings** (`OparlChunkEmbedder`) — with the installation's OParl embedding model (platform config `OPARL_EMBEDDING_MODEL_ID`, a catalog embedding model that is not archived), through `EmbedTextUseCase` in the lowest lane of `EmbeddingsThrottleService` (`REINDEXING`), 64 chunks per request, body by body. Every chunk whose `embeddingModelId` differs from the current model is embedded, so a model change embeds everything again; the model is checked before every batch, so a change during a pass (also after a provider failure) goes on with the new one. Without a model nothing is embedded; chunks are still full-text searchable. A provider failure ends the pass; the next job goes on.
- **`ProcessOparlDocumentsUseCase`** — one system's document job: chunks the objects, then reads pending files (ten per query, two at once) and embeds in turns: reads for up to five minutes, embeds what lacks a vector until the slice ends (at least a minute, even when reading overran), and reads on if time is left; once every file is read it repairs chunks, refreshes file context and embeds the rest. So papers, meetings and agenda items have vectors from the first slice on, and files as they are read. Works in ten-minute slices and then goes back to the queue with its progress (`OparlDocumentsProgress`), so syncs waiting for a slot go first. Starts over when a sync of the system finished while it ran. Queued at the end of every sync run (whatever its outcome), for every system when the embedding model changes, and by the sweep for a system with document work left.
- **`SetOparlEmbeddingModelUseCase` / `GetOparlEmbeddingModelUseCase`** — the setting: `OPARL_EMBEDDING_MODEL_NOT_FOUND` (404) for a model that is not a non-archived catalog embedding model; a change queues every system's document job. Get answers `null` while none is chosen or the chosen one left the catalog or was archived.
- **`HasOparlVectorsOfModelUseCase`** — whether any chunk holds a vector of a catalog embedding model; the models module's `UpdateEmbeddingModelUseCase` asks it before a name or dimensions change (resolved through `ModuleRef`, since this module imports the models module).
- **Stats** — the system list adds per system the files by state (pending as of current metadata, extracted, failed, skipped per reason, the last error) and the index size (chunks, chunks embedded with the current model).

## Org links

- **`OparlBodyLink`** — `oparl_body_links`: one row per org and body (unique `(orgId, bodyId)`), `linkedByUserId` (set `NULL` when the user is deleted) and `createdAt` (when it was linked). Cascades with the org (deleting an org removes its links and nothing else) and with the body (a body deleted from the RIS takes its links along). Unlinking deletes the row only; the mirror stays. Links outlive the flag: switching it off keeps them.
- **`ListOparlCatalogBodiesUseCase`** — every body of the catalog with its system's name and whether the current user's org linked it (`linkedAt`); nothing about other orgs' links.
- **`LinkOparlBodiesUseCase`** — links bodies to the current user's org in one statement (`INSERT … ON CONFLICT DO NOTHING`): a body already linked keeps its link and date; a body not in the catalog fails the whole request with `OPARL_BODY_NOT_FOUND` (404) and links nothing.
- **`UnlinkOparlBodyUseCase`** — deletes the current org's link only; `OPARL_BODY_NOT_LINKED` (404) when the org has none, so another org's link can never be removed.
- **`FindLinkedOparlBodiesUseCase`** (exported) — an org's linked bodies with their system's name: the scope every org-facing read of the mirror (the chat capability, AYC-2061) must stay within.
- The super-admin system list shows per body the orgs that linked it (`linkedOrgs`, joined through the link record's org relation).

## Reading for chat

The use cases behind the chat's council tools (AYC-2061; the runs module's `OparlCapability`, the tools module's `oparl_*` tools). Each reads the current org from the request context (`getRequiredOrgId`) and, through `OparlReadScopeService`, its linked bodies on every call, so a link removed during a chat applies to the next call. A body filter keeps only linked bodies; one that names none of them reads nothing. An ID of another body is "not found" (`null`), exactly like a missing one, and a filter on another body's organization or person matches nothing. Every referenced row in a result (related papers, files, meetings, members) must be of a body in the scope too, so nothing of an unlinked body is named; a membership or consultation whose other side is of a body outside the scope is left out entirely.

- **`SearchOparlUseCase`** — up to five queries with filters (bodies, date range on the chunk's `date`, organization: its meetings and the papers it submitted or deliberated through a consultation, whose meeting may come only through its agenda item; person: the papers they submitted and the meetings they took part in; paper type: part of the RIS's type name, case-insensitive, also for agenda items through their consultation's paper). An agenda item's paper comes through the consultation it names or, failing that, one that names it, since a RIS may fill in only one of the two references. Per query: German full text (`plainto_tsquery('german', …)` with its words OR-ed, ranked by `ts_rank` normalized by the log of the chunk length) and, with an OParl embedding model, the nearest chunks of that model (`<=>` on the model's `halfvec` column, `hnsw.iterative_scan = relaxed_order`, `ef_search` 100, `max_scan_tuples` 50,000, re-sorted by distance); 40 candidates each, fused by reciprocal rank (`fuseRankings`, k = 60), the best 10 returned with their paper, meeting, agenda item, file (with page) and the queries that found them. The query is embedded in the throttle's retrieval lane, as platform work. Without a model, or when its provider fails, full text alone (`mode: 'full_text'`). Postgres chooses between the HNSW index and the body B-tree with an exact sort per query; there is no switch in code. Measured on 112k embedded chunks (AYC-2061): HNSW for every scope without filters, also a 3k-chunk body (top-10 overlap with an exact scan ≥ 0.96, 4–32 ms median), the B-tree with an exact sort for that body with a date filter.
- **`GetOparlObjectUseCase`** — a paper (main and auxiliary files, originators, organizations under whose direction, related, superordinated and subordinated papers, consultations in meeting order with their meeting, agenda item, result and resolution text), a meeting (location, organizations, participants, invitation and protocols, auxiliary files, agenda items in order with paper, result, resolution text and files), an organization (memberships, current first, with the person) or a person (memberships with the organization).
- **`ReadOparlFileUseCase`** — a file's stored pages from a page on, as many as fit 20,000 characters (a longer page is cut), with `nextPage`; a file not read yet, skipped or failed comes with its state and no text.
- **`ListOparlObjectsUseCase`** — meetings (latest first; name, day range in Europe/Berlin, organization), organizations (name or short name) or persons (name, membership in an organization), 20 per page with the total. Name filters match literally (LIKE wildcards are escaped).
- **`PostgresOparlReadRepository`** — raw SQL (`oparl-read-sql.ts`, `oparl-object-sql.ts`), one statement per object with its references as JSON.

## Outbound HTTP (`OparlHttpClient`)

http(s) on public hosts only (`src/common/util/network-address-policy.ts`): every URL and every redirect target is resolved and checked before the request, and connections go only to checked addresses (the dispatcher's lookup checks again, so DNS rebinding cannot reach a private address). Identifying User-Agent (`OPARL_USER_AGENT`); at most two requests per host at once in a process (`HostRequestLimiter`, shared by all systems on a host); 120 s per request; responses up to 32 MB; files (`downloadFile`) up to the caller's limit (`OparlFileTooLargeError`, by the declared length or while streaming). 408, 429, 5xx and network failures are retried after 5 s, 30 s, 2 min and 5 min, or after `Retry-After` (up to 15 min). Requests and waits stop when the run's signal aborts.

## Queue

`oparl-sync` (BullMQ), worked by `OparlSyncConsumer` in `IngestionConsumersModule` (API or ingestion worker), concurrency `INGESTION_OPARL_CONCURRENCY` (default 3), so a slow or unreachable system does not hold up the others. Document jobs (`oparl-documents`, ID `oparl-documents-<systemId>`, priority 10) share the queue below the runs (which have no priority and so come first) and give their slot back after each slice. One run job per system, ID `oparl-system-<systemId>`: BullMQ adds nothing under an ID it holds, so a system has at most one run queued or running however often the sweep or "Sync now" asks; jobs are removed when they end. The job data holds the run's progress, so a job retried or recovered after a stall resumes where it stood. On shutdown the consumer aborts its runs between pages and moves their jobs back to the queue without spending an attempt (a run of hours must not hold up a deploy). `OparlSyncScheduler` upserts the sweep's job scheduler (`oparl-sync-due-systems`, every 15 minutes) on every boot, or removes it with the flag off. Listed in queue inspection and telemetry.

## Infrastructure

- `PostgresOparlMirrorRepository` — set-based SQL built from `OPARL_TYPE_SPECS` (`oparl-mirror-sql.ts`, `oparl-mirror-tables.ts`): one `INSERT … SELECT FROM jsonb_to_recordset … ON CONFLICT DO UPDATE … WHERE <changed> RETURNING` per type and form, join rows replaced only for owners written, deletes and reconciliation as `WITH d AS (DELETE …) SELECT count(*)`. `oparl_sync_listed_objects` records what a full listing contained (per run, removed when it ends), so an interrupted reconciliation resumes.
- `PostgresOparlDocumentsRepository` — raw SQL (`oparl-documents-sql.ts`); a write for an object deleted meanwhile (foreign-key violation) is dropped and done again by the next job.
- `PostgresOparlSystemsRepository`, `PostgresOparlSyncRunsRepository`, `PostgresOparlBodyLinksRepository` — TypeORM (the catalog and linked bodies as raw SQL joins).
