File Storage
Object storage abstraction for file uploads and downloads

Storage provides a MinIO-backed object storage layer for uploading, downloading, and managing files with presigned URLs. It abstracts bucket operations and metadata handling behind a clean port interface.

The storage module abstracts file persistence behind an `ObjectStoragePort` interface, currently implemented by MinIO. Key domain entities include `StorageObject` (stored file reference), `StorageObjectUpload` (upload payload with metadata), `StorageBucket` (container), `PresignedUrl` (temporary access URL), `StorageUrl` (object location), and `ObjectMetadata` (file attributes). Use cases cover uploading objects, downloading objects, deleting objects, listing objects by prefix, retrieving object info, and generating presigned URLs for direct client access. The module exposes no HTTP endpoints: all reads and writes go through the exported use cases, and file delivery to clients happens via feature-specific, ownership-checked endpoints in the consuming modules (e.g. message images and generated images in **threads**, letterheads in **letterheads**). The module integrates with **sources** for persisting uploaded data source files, **messages** for storing image attachments in conversations, and **rag** indirectly through sources for document content that feeds the ingestion pipeline.

**Org deletion purge.** Because MinIO blobs live outside the database, they are not removed by the org `ON DELETE CASCADE` chain. `PurgeStoragePrefixesUseCase` is the generic best-effort prefix sweep (list + delete every object under given key prefixes, requiring no database rows); `PurgeOrgStorageUseCase` delegates to it to remove every object under an org's storage prefixes (`<orgId>/` for message images and document-processing temp files, `generated-images/<orgId>/` for model-generated images, and `letterheads/<orgId>/` for rendered letterhead PDFs). `StorageOrgDeletionRequestedListener` defers it on `OrgDeletionRequestedEvent` (via the event's `deferCleanup`); the orgs module's `DeleteOrgUseCase` runs the deferred purge only after the org row delete succeeds, so a failed delete never costs a surviving org its blobs. Both are best-effort — a missing object counts as already purged, and other failures are logged and counted rather than thrown, so a storage error never blocks org deletion. The org-scoped prefix layout (`<orgId>/`, `generated-images/<orgId>/`, `letterheads/<orgId>/`) is owned by `domain/org-storage-layout.ts` — `orgStoragePrefixes(orgId)` builds the purge prefixes and `extractOrgIdFromKey(key)` recovers the org id for the sweep, so adding a new org-scoped layout in one place keeps purge and sweep in sync.

**Orphan-blob sweeper.** Deferring the org purge until after the row delete trades loss for leak: if that deferred purge fails or the process dies post-delete, the blobs belong to a nonexistent org and nothing else ever reaches them (unbounded leak). `SweepOrphanStorageUseCase` closes that gap. Driven nightly at 2 AM by `OrphanStorageSweepTask` (staggered before the 3 AM orphaned-images and 4 AM retention cleanups), it lists every object with its last-modified time (`ObjectStoragePort.listObjectsWithMetadata`), extracts the org id embedded in each key (via `extractOrgIdFromKey`), and resolves that set against the live org ids from `FindAllOrgIdsUseCase`. Prefixes whose org no longer exists are purged via `PurgeOrgStorageUseCase` — but only when the org's newest blob is older than `ORPHAN_STORAGE_SAFETY_WINDOW_MS` (24h), so a race with org creation never purges freshly written blobs. Purged/skipped counts are logged for the deletion-concept audit trail (DSGVO Art. 17, OPS.2.2.A15). This is why the storage module imports `OrgsModule`.
