File Storage
Object storage abstraction for file uploads and downloads

Storage provides a MinIO-backed object storage layer for uploading, downloading, and managing files with presigned URLs. It abstracts bucket operations and metadata handling behind a clean port interface.

The storage module abstracts file persistence behind an `ObjectStoragePort` interface, currently implemented by MinIO. Key domain entities include `StorageObject` (stored file reference), `StorageObjectUpload` (upload payload with metadata), `StorageBucket` (container), `PresignedUrl` (temporary access URL), `StorageUrl` (object location), and `ObjectMetadata` (file attributes). Use cases cover uploading objects, downloading objects, deleting objects, listing objects by prefix, retrieving object info, and generating presigned URLs for direct client access. The module exposes no HTTP endpoints: all reads and writes go through the exported use cases, and file delivery to clients happens via feature-specific, ownership-checked endpoints in the consuming modules (e.g. message images and generated images in **threads**, letterheads in **letterheads**). The module integrates with **sources** for persisting uploaded data source files, **messages** for storing image attachments in conversations, and **rag** indirectly through sources for document content that feeds the ingestion pipeline.

**Org deletion purge.** Because MinIO blobs live outside the database, they are not removed by the org `ON DELETE CASCADE` chain. `PurgeStoragePrefixesUseCase` is the generic best-effort prefix sweep (list + delete every object under given key prefixes, requiring no database rows); `PurgeOrgStorageUseCase` delegates to it to remove every object under an org's storage prefixes (`<orgId>/` for message images and document-processing temp files, `generated-images/<orgId>/` for model-generated images, and `letterheads/<orgId>/` for rendered letterhead PDFs). `StorageOrgDeletionRequestedListener` defers it on `OrgDeletionRequestedEvent` (via the event's `deferCleanup`); the orgs module's `DeleteOrgUseCase` runs the deferred purge only after the org row delete succeeds, so a failed delete never costs a surviving org its blobs. The prefix sweep treats missing objects as already purged and counts both list and delete failures. The deletion listener rejects its deferred task when any prefix or object could not be purged; the super-admin deletion path reports this incomplete cleanup instead of returning success. Other internal deletion callers retain best-effort cleanup. The org-scoped prefix layout (`<orgId>/`, `generated-images/<orgId>/`, `letterheads/<orgId>/`) is owned by `domain/org-storage-layout.ts` — `orgStoragePrefixes(orgId)` builds the purge prefixes and `extractOrgIdFromKey(key)` recovers the org id for the sweep, so adding a new org-scoped layout in one place keeps purge and sweep in sync.

**Orphan-blob sweeper.** Deferring the org purge until after the row delete trades loss for leak: if that deferred purge fails or the process dies post-delete, the blobs belong to a nonexistent org and nothing else ever reaches them (unbounded leak). `SweepOrphanStorageUseCase` closes that gap. Driven nightly at 2 AM by `OrphanStorageSweepTask` under the AppSignal `orphan_storage_sweep` process monitor (staggered before the 3 AM orphaned-images and 4 AM retention cleanups), it lists every object with its last-modified time (`ObjectStoragePort.listObjectsWithMetadata`), extracts the org id embedded in each key (via `extractOrgIdFromKey`), and resolves that set against the live org ids from `FindAllOrgIdsUseCase`. Prefixes whose org no longer exists are purged via `PurgeOrgStorageUseCase` — but only when the org's newest blob is older than `ORPHAN_STORAGE_SAFETY_WINDOW_MS` (24h), so a race with org creation never purges freshly written blobs. Purged/skipped counts are logged for the deletion-concept audit trail (DSGVO Art. 17, OPS.2.2.A15). This is why the storage module imports `OrgsModule`.

**Upload failure classification.** `UploadObjectUseCase` routes raw SDK failures through `wrapUploadFailure`: transport errors (via the shared `classifyTransportError`), upstream 5xx/408/429 statuses (via `extractUpstreamStatus`), and known transient S3 codes (`SlowDown`, `ServiceUnavailable`, `InternalError`, `RequestTimeout`, `XMinioServerNotInitialized`) become `StorageUnavailableError` (503, `STORAGE_UNAVAILABLE`); everything else stays `UploadFailedError` (500, `UPLOAD_FAILED`). The two are distinct classes so AppSignal groups outages apart from bugs. Both carry only allowlisted upstream name, code, and status in message and metadata — never the SDK message, object path, or request id — and 5xx client responses stay generic. The sources module maps `StorageUnavailableError` to `PROCESSING_UNAVAILABLE` so a source whose upload hit an outage is shown as unavailable rather than failed.

**Organisation-scoped uploads.** `UploadObjectUseCase` remains a generic storage primitive and does not infer ownership from object keys. Organisation-owned callers use `UploadOrgObjectUseCase` with an explicit `orgId`. It checks that the organisation is active, uploads without holding a database transaction or connection, then checks that the same lifecycle generation is still active. If archive or deletion won during the upload, it deletes the late object and fails the request. If the process dies between the upload and that second check, the nightly orphan sweep is the recovery path; because the sweep runs at 2 AM and waits until the newest object is at least 24 hours old, a fresh orphan can remain for nearly 48 hours. New organisation-owned upload paths must use this wrapper rather than the generic primitive.
