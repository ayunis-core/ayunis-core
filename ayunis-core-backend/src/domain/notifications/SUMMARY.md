Notifications
A per-user inbox of messages from routine runs and release notes, with read state

A notification is a message in one user's inbox. Routine runs post them: a routine sends its findings with the `send_notification` tool, and the system posts an error notification when a routine run fails. Release notes of Ayunis arrive as notifications too: the **release-notes** module syncs them from Announcable and sends each new note to every user. From a notification the user can start a chat about it ("Chat about this").

The `Notification` entity belongs to its recipient (`userId`, FK ON DELETE CASCADE, so deleting a user deletes their notifications) and their organization (`orgId`, CASCADE). It carries a `type` (`routine` for a routine's own finding, `routine_error` for a failed run, `release_note` for a release note), `headline` (≤ 200 characters), an optional `subheadline` (≤ 300; release notes have none), a markdown `body` (≤ 10,000, may contain links), optional `media` (an image stored in the **storage** module, kept as its storage key and content type, or a Loom video kept as its embed URL; a check constraint keeps the four media columns consistent), the origin `routineId` and `routineThreadId` (both FK ON DELETE SET NULL: deleting the routine or the routine thread keeps the notification and drops only the link), the announced `releaseNoteId` (FK ON DELETE CASCADE: deleting the release note deletes its notifications), `readAt` (null while unread) and `createdAt`. The table is indexed on `(userId, createdAt)` for the inbox, `(orgId, createdAt)` for retention, and on the origin and release-note columns.

`CreateNotificationUseCase` (exported) takes the recipient in the command, because notifications are posted by the system (a routine run acting for its owner, or the routine sweep without any user context), not by the recipient. It trims the texts and rejects empty or over-long ones, Loom URLs that do not start with `https://www.loom.com/embed/`, and images without a storage key or with a content type outside the image allow-list (all `NOTIFICATION_INVALID`); the media rules live in `notificationMediaViolation` (domain), which the release-note sync applies too; a subheadline may be left out, but a given one must not be blank. With `limitPerRoutineThread` it creates the notification only while the routine thread has fewer than that many (`NOTIFICATION_LIMIT_REACHED`, 409, otherwise): the repository counts and inserts in one transaction behind a PostgreSQL advisory lock on the thread, so concurrent tool calls of one run cannot exceed the limit.

The inbox endpoints (`NotificationsController`, `/notifications`) are behind the `routines` feature flag (disabled → 404) and are not gated by the `manage_routines` permission, so notifications stay readable when it is revoked. Every read and write filters by the current user; another user's notification answers 404 (`NOTIFICATION_NOT_FOUND`), like a missing one.

`NotifyUsersOfReleaseNoteUseCase` (exported) sends a release note to every user there is right now whose org is not archived, in one `INSERT … SELECT` from users (never one job or statement per user); users who join later do not get it. `UpdateReleaseNoteNotificationsUseCase` (exported) shows an edited release note in every notification sent for it, in one `UPDATE`, creating none and keeping read state. Both copy headline, body and media as given: the release-notes module has already applied the notification rules.

`DeleteExpiredNotificationsUseCase` (exported) deletes, or in a dry run counts, an org's notifications created before a cutoff; the retention-policies module calls it from its nightly enforcement with the same cutoff it uses for threads.

Consumers, all through exported use cases: **tools** (`SendNotificationToolHandler` → `CreateNotificationUseCase` with a limit of 3 per routine thread), **routines** (`RoutineFailureNotifier` → `CreateNotificationUseCase` for failed and interrupted runs), **threads** (`CreateThreadUseCase` checks a `sourceNotificationId` with `FindNotificationUseCase`), **runs** (`NotificationContextCapability` reads the notification a chat is about), **release-notes** (`SyncReleaseNotesUseCase` → `NotifyUsersOfReleaseNoteUseCase` and `UpdateReleaseNoteNotificationsUseCase`) and **retention-policies**. The module imports the **storage** module for `DownloadObjectUseCase`; its record references users, orgs, routines, threads and release notes only for the foreign keys, and the repository reads users and orgs for the release-note fan-out. Image objects are not owned by a notification: deleting notifications (retention, user or org deletion) leaves the stored image to whoever stored it.
