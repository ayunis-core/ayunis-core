Uploads
Resumable, chunked file uploads via the tus protocol

The uploads module hosts a [tus](https://tus.io) server (`@tus/server` + `@tus/file-store`) under `POST/HEAD/PATCH/OPTIONS/DELETE /api/uploads/tus[/:uploadId]`, protected by the global JWT guard like every other route. `TusUploadService` wraps the tus server: chunks land in the same `./uploads` directory multer uses, the authenticated user id is stamped into the upload metadata server-side (`onUploadCreate` — a client-supplied value is always overwritten), and uploads are capped at the shared `MAX_SOURCE_FILE_SIZE_BYTES`. A completed upload is consumed by finalize endpoints on the thread, skill, and knowledge-base controllers (e.g. `POST /threads/:id/sources/uploads/:uploadId`): `resolveCompletedUpload(uploadId, userId)` verifies the id shape (traversal guard), completeness (409 while transferring), and ownership (foreign ids report 404), then returns a multer-equivalent `UploadedFileRef` so the existing `AddFileSource*`/`AddDocument` flows run unchanged; the finalize endpoint removes the data and info files afterwards via `cleanupUpload`. `TusUploadCleanupTask` sweeps expired partial uploads hourly (24h expiration window, in-flight guard against overlapping runs). The classic multipart endpoints remain for external API consumers — tus is the app frontend's upload path (chunked transfer also passes reverse proxies with small `client_max_body_size`).
