Knowledge Pipeline
Retrieval-augmented generation with text splitting and vector indexing

RAG provides the ingestion pipeline for enhancing AI context: splitting documents into chunks via configurable splitters, then indexing those chunks with embeddings for semantic search and retrieval.

`EmbedTextUseCase` (`embeddings/application/use-cases/embed-text`) is the error choke point for embeddings provider failures: `ApplicationError` passes through, transport failures and upstream 5xx become the shared `ProviderUnavailableError` family via `wrapProviderFailure` from `src/common/errors` (stable AppSignal grouping per provider+failure-class, AYC-538), and unrecognized errors rethrow raw so internal bugs stay distinct. When `MOCK_INFERENCE=true`, embedding requests use deterministic local vectors while provider availability still reflects configured credentials. Embeddings handlers are registered for `openai`, `mistral`, `ayunis` (`AYUNIS_BASE_URL` with its bearer token) and `ollama` (`OLLAMA_BASE_URL`, no auth); both Ollama handlers share `BaseOllamaEmbeddingsHandler`. `AssertEmbeddingsProviderAvailableUseCase` resolves a provider's handler the way an embed would (mock handler under `MOCK_INFERENCE`) and throws `EmbeddingsProviderNotFoundError` or `NoEmbeddingsProviderAvailableError` otherwise; their codes are prefixed `EMBEDDINGS_` because upload clients map them.

The RAG module is organized into two sub-modules: **splitters** and **indexers**. Splitters handle text chunking with pluggable strategies (recursive and line-based), producing `SplitResult` entities from raw text via a handler registry. Indexers manage vector-based content storage using a parent-child index architecture where documents are split into parent and child chunks with embeddings for semantic search. Key entities include `IndexEntry`, `ParentChunk`, and `ChildChunk`. Use cases cover content ingestion, deletion, and semantic search. Search takes several queries across several documents: all queries are embedded in a single embedding call, one vector search runs per query vector, and the results are merged into `IndexMatch`es deduplicated by source chunk, ranked by their best cosine distance, and tagged with every query that matched. Each vector search ranks child chunks filtered by their own `relatedDocumentId` (a copy of their parent's, written on insert and B-tree indexed, so no join with `parent_chunks` is needed) by exact cosine distance, and loads only the nearest ones with their parents; the document IDs are bound as one array parameter, so a scope is not capped by the 65,535 bind parameters of a statement (AYC-2055). The `parent_chunks.relatedDocumentId` FK to `sources` cascades on source deletion, so parent/child chunks are removed automatically when their source is deleted. The indexer infrastructure uses PostgreSQL with pgvector for embedding storage. The module integrates with **models** for embedding model access, **sources** for document content to ingest, **retrievers** for content extraction before indexing, and **tools** (source_query, knowledge_query and recording_search tools) for runtime semantic search during conversations. `PrepareContentEmbeddingsUseCase` computes, without storing anything, the vectors an ingestion of given contents would need, as `PreparedContentEmbeddings` (vectors keyed by exact text plus catalog ID, provider, model name and dimensions); `IngestBulkContentCommand.precomputedEmbeddings` passes them back so ingestion reuses only vectors from a matching model configuration and embeds the rest. In the parent-child index both go through `ChildChunkEmbedder`, which cuts a parent into child texts and embeds them in parallel batches (AYC-1803, AYC-1813). Ingestion returns the catalog ID of the embedding model it indexed with (resolved also for no entries), which the sources module records per source. Ingestion and preparation take an optional `EmbeddingPriority`; `EmbeddingsThrottleService` runs retrieval before ingestion and ingestion before `REINDEXING`, the lane re-indexing after a model change uses so it never delays uploads (AYC-1919).

Persistence adapters participating in synchronous `@Transactional()` paths resolve repositories through the ambient CLS transaction host at call time, with default-repository fallback for callers outside CLS.
