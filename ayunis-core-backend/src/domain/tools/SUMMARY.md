# Extensible Tools

Pluggable tool system with JSON schema validation and execution.

Tools provide an extensible capability system where AI agents invoke typed actions—HTTP calls, code execution, chart generation, image generation, source queries, internet search, email, calendar, document editing/export preparation, spreadsheet creation and updates, and MCP operations—during conversations.

The tools module implements a polymorphic tool system with JSON schema-based parameter validation. The abstract `Tool` entity specializes into concrete types including `HttpTool`, `CodeExecutionTool`, `InternetSearchTool`, `WebsiteContentTool`, source and knowledge retrieval tools, email and calendar tools, chart and GeoJSON map tools, MCP tools, `ProductKnowledgeTool`, `ActivateSkillTool`, document tools, `CreateSpreadsheetTool`, `UpdateSpreadsheetTool`, `GenerateImageTool`, and `MarketplaceSearchTool` (handled by `MarketplaceSearchToolHandler`, which lists published skills, integrations and categories through the marketplace module's use cases, projects the generated DTOs down to the fields a recommendation needs plus an in-app install link, and turns a marketplace outage into a plain tool error the model can relay). `InstallMarketplaceSkillTool` is externally handled: the run ends with the tool call and the chat renders an install card, so nothing is installed until the user confirms; installs go through the skills module's marketplace install endpoint under the user's own permissions. `CreateRoutineTool` (`create_routine`: name, task, daily time as `HH:mm`, internet) and `EditRoutineTool` (`edit_routine`, created with the user's routine IDs mapped to one-line summaries, which restrict `routine_id`; empty text fields mean unchanged) are externally handled like the skill widgets: the chat renders a form and the user saves through the routines endpoints. `AddAnonymizationExceptionTool` (`add_anonymization_exception`: `category`, `word`) proposes an org whitelist exception for a word the admin no longer wants masked. The word is taken literally; the model cannot supply a pattern. Its handler resolves `{{pii:…}}` placeholders in `word` to the thread's original values, validates the exception through the anonymization-settings module's `ValidatePiiWhitelistExceptionUseCase` and turns a rejection into an error the model can relay, which does not depend on a masked value beyond whether the rule already exempts it; on success it returns `{"status":"awaiting_confirmation"}` without any value, and the chat offers its confirmation card only for that result. Nothing is saved by the tool. `FinishRoutineTool` (`finish_routine`) ends an unattended routine run: it has no parameters, ignores any arguments the model adds so a finished routine is never kept running by a validation error, and has no handler — the runs module treats it as externally handled. `SendNotificationTool` (`send_notification`, headline ≤ 200, subheadline ≤ 300, markdown body ≤ 10,000 characters) is created with the routine a run belongs to (`SendNotificationOrigin`); `SendNotificationToolHandler` posts it to the inbox of the user the run acts for through the notifications module's `CreateNotificationUseCase`, with the run's thread as the routine thread and a limit of 3 per thread (`SEND_NOTIFICATION_LIMIT_PER_RUN`); invalid input and the limit come back to the model as tool errors, the latter telling it to call `finish_routine`. `GetMemoryTool` (`get_memory`) and `SetMemoryTool` (`set_memory`: key, content ≤ 2,000 characters, optional description ≤ 150) read and write the run user's memory through the memory module's use cases: an unknown key is a successful result that lists the existing keys, empty content removes the entry (a reserved key is cleared), an omitted description keeps the stored one, and invalid keys, over-long content and a full memory come back to the model as tool errors. `ChatListTool` (`chat_list`: `page`, `from`/`to` as UTC dates, the `to` day included) and `ChatReadTool` (`chat_read`: `threadId`, `messageNumber`, `turns` 1–10, default 3) are created with the run's `PastChatScope` and read the user's earlier chats through the threads module's `FindPastChatsUseCase` and `FindPastChatUseCase`. `chat_list` returns 10 chats per page, most recently active first, with ID, title, creation and last activity. `chat_read` returns whole turns (a user message and everything up to the next one) with chat-wide message numbers, `nextMessageNumber` and the total message count; only user and assistant text is included, without tool calls and results, thinking, skill instructions or nudges, and a message is cut after 4,000 characters (`readPastChatTurns`). A chat outside the scope is an ordinary "not found" result; invalid parameters and a `messageNumber` past the end come back to the model as tool errors. `ChatGrepTool` (`chat_grep`: `pattern`, a case-insensitive PostgreSQL regular expression of 1–200 characters, and `from`/`to` like `chat_list`, filtering on when a message was written) greps the same chats through the threads module's `GrepPastMessagesUseCase` and returns up to 10 matching messages, newest first, with thread ID and title, message number (for `chat_read`), role, time and excerpt, plus `moreMatches` when more messages match, so the model makes its pattern or time range more specific (there is no paging). Its description teaches PostgreSQL regex syntax (`\y` word boundary, `\m`/`\M`, word forms by alternation). No match, an invalid pattern (with PostgreSQL's reason) and a search that hits the statement timeout are successful results the model can act on; an over-long pattern is a tool error. `ToolBox` groups tools by type, while `ConfigurableTool` adds configuration data. Tool entities own schemas and validation only; frontend rendering and runtime continuation are selected independently by their respective adapters.

Each tool type has a dedicated handler for execution. Tool classes and their handlers are paired once in `application/tool-handler.entries.ts`, which registers the handlers and feeds `ToolHandlerRegistry`; the registry returns the first pair whose tool class matches with `instanceof`, so a new handler only needs a pair there. Document tools manage versioned artifacts during conversations, including letterhead assignment and surgical search-and-replace edits. Spreadsheet tools create and fully replace spreadsheet artifacts from columns and rows, including text, numbers, and Excel formulas; `create_spreadsheet` can instead take a `data_source_id` and import every row of a READY CSV data source attached to the current thread (uploaded or written by `code_execution`) server-side, so large tables never pass through model output — plain numeric strings and decimal-comma amounts with one or two decimals (optionally dot-grouped, e.g. `1.234,56`) become numbers, empty strings become null, and zero-padded, over-long, or more than 15-significant-digit values stay text so nothing is silently rounded; their handlers serialize the grid through the artifacts module's spreadsheet content helpers. A version conflict on `update_document`, `edit_document`, `update_diagram` or `update_spreadsheet` is returned to the model as the artifacts module's error, which names the read tool for the artifact's type. `read_diagram` and `read_spreadsheet` return the current version of a diagram or spreadsheet and reject an artifact of another type with the read tool that fits it; the lookup is the same as `read_document`'s (`FindArtifactWithVersionsUseCase`), so an artifact the user cannot access is reported as not found. `GenerateImageTool` accepts a prompt, an optional `background` of `transparent` (only after the user confirms it), plus optional reference-image parameters (`reference_uploaded_image_ids` with `<messageId>:<index>` refs taken from the `[image ref: …]` labels the inference mapper injects next to every uploaded image, `reference_generated_image_ids` to iterate on earlier generations). `GenerateImageToolHandler` resolves the permitted image model, resolves requested reference images to raw bytes via the threads module's `DownloadReferenceImagesUseCase`, then enforces the image quota — references before quota, so a failed reference lookup (exposed to the model for a corrected retry) never consumes a quota slot — generates and stores the image, and reports usage when applicable.

`AuthorizedCsvSourceResolverService` is the shared application boundary for CSV-consuming tools. It resolves sources through the current owner-scoped thread, rejects unattached and non-ready IDs before any CSV is serialized or execution transport is invoked, and supports both uploaded and newly generated CSV attachments. Generic source repository lookups intentionally remain caller-agnostic.

The module includes tool assembly, runtime execution, embedding and text-extraction utilities, and validation helpers. MCP tools and resources expose stable canonical names derived from their capability kind, upstream name, and the first eight characters of the immutable integration ID; descriptions retain the readable integration name, and tool execution sends the preserved upstream name to the MCP server. A tool that declares file fields (`McpTool.fileParams`, from `_meta["openai/fileParams"]`) shows the model, per field, the ID of a file attached to this chat (a single file object, after resolving local `$ref`s) or a list of such IDs (an array of file objects), required or optional as declared; `toModelFacingSchema` (`domain/value-objects/mcp-file-fields.ts`) builds that schema and `McpIntegrationTool.validateParams` validates against it. A declaration whose field is missing or neither an object nor an array of objects throws `InvalidMcpFileParamsError`, and the runs module does not offer the tool. Before the call, `McpFileHandoverService` turns each set file field into `{ download_url, file_id, mime_type, file_name }` through the threads module's `ResolveThreadFileUseCase` (the user's own upload to this chat, with a stored original). An anonymous chat, another chat's or user's file, a skill-assigned file, a file without a stored original or a non-ID value fails the whole call with a tool error naming the rule, and the server is not called; omitted optional fields stay omitted. The signed URL exists only in the arguments sent to the server: the logged, persisted and streamed input keeps the model's source IDs, and a URL the server echoes back is replaced in the result. `website_content`, `read_document` and `read_diagram` return bounded, line-addressable pages, expose a complete next-page input, and preserve oversized single-line content by treating it as multiple pagination lines; `read_document` and `read_diagram` pages hold at most 500 lines and a 20,000-character encoded text budget (the `source_get_text` limits), `read_spreadsheet` pages hold at most 500 data rows within the same character budget (column headers included) and return `columns` and `rows` in the shape `update_spreadsheet` takes; a single row or header set above the result cap is named in the error, which tells the model not to replace a spreadsheet it cannot fully read, while `website_content` has its own budget of 2,000 lines and 60,000 characters (AYC-1607) so a cleaned article page usually arrives in one call, and its continuation inputs repeat the requested (pre-redirect) URL so they reuse the run's retrieval; website links are fetched through their own bounded section, while every document page retains its version for edit round-trips. `ExecuteToolUseCase` removes schema-disallowed explicit nulls before dispatching calls. `ToolExecutionContext.signal` carries the run's cancel signal to handlers, and calls of one turn may run concurrently. `internet_search` passes it to the search provider request, the MCP and HTTP handlers abort their outgoing request with it, and `ExecuteToolUseCase` rethrows the cancellation instead of wrapping it as a tool failure. Validation errors are formatted in plain language for model recovery instead of exposing raw AJV output (AYC-646). Most entities delegate validation to `validateToolParams`; `McpIntegrationTool` handles third-party schemas leniently, and `GenerateImageTool` uses the same formatted errors within its tool-execution error contract. `MapTool` is registered as an always-available tool with a versioned schema that accepts RFC 7946 FeatureCollections with point, line, polygon, and corresponding multi-geometries; it bounds feature/property counts, payload bytes, coordinate count/ranges, and polygon closure before acknowledging the widget. `CreateCalendarEventTool.validateParams` adds date checks the JSON schema cannot express (`start`/`end` parseable as ISO 8601, `end` after `start`). Runtime tools that do not use a backend handler validate through the runtime's `validateInput` seam, so malformed widget input is fed back to the model instead of reaching the client (AYC-675).

The module integrates with **agents** for tool assignment, **runs** for runtime execution, **sources**, **rag**, **knowledge-bases** and **recordings** for retrieval, **mcp** for protocol-bridged tools, **retrievers** for search and content tools, **marketplace** for the catalogue behind `marketplace_search`, **artifacts** for document and spreadsheet persistence, **skill-templates** for skill activation, **models** for model resolution and image generation, **quotas** for fair-use enforcement, **threads** for generated image storage, reference-image resolution and chat files handed to MCP tools, **notifications** for posting a routine run's `send_notification` calls (`CreateNotificationUseCase`), **memory** for `get_memory` and `set_memory`, and **threads** for the past chats behind `chat_list`, `chat_grep` and `chat_read`, **thread-pii-masks** and **anonymization-settings** for `add_anonymization_exception`.

The `source_query` (`sourceIds[]`, up to 20) and `knowledge_query` (`knowledgeBaseIds[]`, up to 20) retrieval tools each take up to five `queries[]` and search every query across every selected target in one call; each result is tagged with the `matchedQueries` that found it. Retrieval results expose each persisted source chunk's canonical `chunkId` for assistant citations. Results also identify whether they are citable; system-only source content is marked non-citable, while `source_query` includes the canonical source id and name alongside existing line/file/URL metadata.

The Outlook pane's tools live in `domain/tools/outlook/`: `outlook__read_email` (no parameters), `outlook__read_attachment` (`attachmentId` or `name`, at least one), `outlook__draft_email` (`body`, optional `subject`), `outlook__move_email_to_composer` (`body`) and `outlook__save_email_to_draft` (no parameters). They have no handler: the pane executes them with Office.js against the email open in Outlook, and their descriptions tell the model that nothing is sent. Every one rejects parameters it does not define; bodies follow the plain-text rules of `send_email`. The two read tools return mailbox content and so report `returnsPii`. The runs module offers them only to a run of its Outlook profile (`OutlookAddInCapability`).

`recording_search` (`RecordingSearchTool`, offered by the runs module's `RecordingsCapability`) searches the transcripts and summaries of every recording the user can read through the recordings module's `SearchRecordingsUseCase`. It takes up to five `queries[]` and an optional upload time range (`uploadedFrom`, `uploadedTo`: ISO 8601 date-times checked in `validateParams`, since strict-mode providers reject `format: 'date-time'`; a reversed range is refused). The chat's workspace comes from the tool's `RecordingSearchScope`, set when the run is assembled, never from the model. Results are citable and carry `recordingId`, `recordingName`, `uploadedAt` and `position`: `transcript` with `start`, `end` (`HH:MM:SS.mmm`) and `speakers` (`Speaker N`, as in the transcript text), or `summary`.

`CreateFileTool` is always available for CSV, XML, JSON and TXT downloads (up to 100,000 content characters and 200 filename characters). It validates its schema and is acknowledged by the runtime so the answer continues; the chat builds the UTF-8 download from persisted tool arguments, resolving thread PII masks locally. CSV restoration parses cells before resolving values and reserializes with CSV quoting, preserving delimiters and row boundaries. No file storage, endpoint or execution handler is used.

`source_get_text` and `knowledge_get_text` preserve physical citation line numbers and expose `nextPage` with `startLine` and a zero-based `startCharacter` within that line. This makes existing single-line transcripts fully readable without reprocessing. Source reads retain their catalog/source-ID enum restriction and check existence on each call; knowledge reads retain the thread/user authorization lookup. Database line slices are bounded before retrieval. `read_document`, `read_diagram`, `read_spreadsheet`, `source_get_text` and `knowledge_get_text` count JSON escaping and reject serialized responses at the shared 30,000-character anonymous-mode cap rather than returning broken or silently cut JSON; `website_content` keeps its own 60,000-character budget (AYC-1607).
