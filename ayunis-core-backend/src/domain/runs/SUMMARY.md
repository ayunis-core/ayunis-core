AI Execution
Orchestrate AI inference runs with streaming message responses

Runs execute AI conversations by coordinating model inference, message creation, tool execution, and response streaming. Each run processes user or tool-result input within a thread context.

The runs module is the central orchestrator for AI conversation execution. The `Run` entity (currently minimal) represents an execution instance, while `RunInput` differentiates between `RunUserInput` (text and images) and `RunToolResultInput` (tool call responses). The primary use case `ExecuteRun` resolves the thread, reauthorizes its catalog model against the authenticated user's current effective organization/team grants, builds tools and instructions from the run profile named on `ExecuteRunCommand` (see *Run profiles and capabilities*), resolves the provider, delegates admission-time fair-use gating to `InferenceAdmissionGuard.preflight`, and executes every conversation through `@ayunis/agent-runtime`. Monetary policy is checked separately immediately before every paid provider call, including retries, later tool turns, and inherited child-run calls. Credit-budget and credit-limit gating is skipped for models that do not consume credits (`LanguageModel.consumesCredits === false` — free open-source models with no configured token costs, e.g. German-hosted "DE" models), so they stay usable after the org's monthly credit budget is exhausted; the fair-use quota still applies to them. `ExecuteRunAndSetTitle` extends this to auto-generate thread titles on first messages: once the run is admitted, the title is generated from the user message alongside the run (after its own `InferenceAdmissionGuard.ensureModelCallAllowed` check, since the run's credit gate only runs before its first model call) and emitted as soon as it is ready, but the stream never waits for it — a title still generating when the answer completes is saved in the background and reaches the client with the next thread refresh. `SendMessage` is the endpoint-level use case behind `POST /runs/send-message`: it consumes a trial message when the command asks for it (fire-and-forget with a caught, logged failure; orgId from `ContextService`) and delegates to `ExecuteRunAndSetTitle`.

The HTTP layer (`presenters/http/`) is split into focused units: `RunsController` (thin endpoint — cross-field validation, command construction, delegation), `ThreadAiContextController` (`GET /threads/:threadId/ai-context` — owner-scoped summaries of the active personal/shared and workspace resources available to that chat), `SendMessageRequestValidator` (multipart rules DTO decorators cannot express), `RunEventResponseMapper` (run event → response DTO), and `RunSsePresenter` (owns the SSE transport: headers, event framing, heartbeat, disconnect/error tracking, and teardown — every write path is guarded because it runs outside NestJS exception filters). `GetThreadAiContextUseCase` composes the policy in the runs application layer, rechecks access to attached knowledge bases, and omits stale assignments. Run error events use `ApplicationError.toClientResponse()`: expected 4xx metadata such as quota `retryAfterSeconds` remains available to clients, while 5xx messages and metadata stay server-side.

### Services

Chat image transport uses Multer with `TotalSizeLimitedMemoryStorage`: per-file uploads are capped at 20 MiB, and aggregate image bytes are counted while streaming, with HTTP 413 once the 80 MiB total is exceeded. The storage engine hands Multer an `UploadBytes` holder instead of a Buffer, because Multer keeps a second copy of every completed file record for the life of the request; `RunInputMapper` takes the bytes out of that holder into the one-shot run input, which empties both of Multer's copies. The run releases those images after input persistence, before inference, and on preparation failure or cancellation. `ImageUploadAdmission` bounds the raw upload bytes held in memory per process (HTTP 429 with `Retry-After` once `IMAGE_UPLOAD_BYTE_BUDGET` would be exceeded); a request is charged for each chunk the storage engine retains, never for its declared Content-Length, so a stalled or chunked upload holds only what it has sent; until the route handler takes ownership it is freed when the response closes (uploads Multer rejects), afterwards only when the run releases its images or the handler returns, so a client that disconnects mid-normalization cannot free it early and an open answer stream does not keep it. Decoded frames are bounded separately by the messages module's normalization concurrency cap.

- **RunTelemetryService** — Records the existing attempted-run activity signal and wraps the selected execution stream so each run emits exactly one low-cardinality terminal outcome and end-to-end duration, including preparation errors and consumer abandonment.
- **EffectiveRunModelResolverService** — Matches a thread's stored catalog model against the authenticated user's current effective language grants before inference. It returns the current permit row (including its current anonymous-only policy) and rejects revoked models before provider access.
- **ArtifactToolAssemblerService** — Assembles the artifact tools for `ArtifactsCapability` (create/update/edit document, create/update diagram, create/update spreadsheet). Enriches each update tool's description with the thread's matching artifact IDs and titles — spreadsheets additionally carry `(current version N)` so the model always has a fresh `expected_version` even after user edits in the grid — and appends org-scoped letterhead IDs to the document tools.
- **McpToolAssemblerService** — Discovers and assembles MCP tools and resources for a thread's attached integrations, including those added through skill activation for `McpCapability`. Tolerates unavailable integrations (`Promise.allSettled`, warn and skip) and filters malformed exact duplicates. MCP capabilities use stable canonical names containing the capability kind, upstream name, and the first eight characters of the immutable integration ID, so built-ins and same-named capabilities from different integrations remain available together. The original upstream tool name is retained for MCP execution, while provider packages convert canonical names to wire-safe names through `ToolNameCodec` in `packages/inference`.
- **ToolResultCollectorService** — Falls back to an MCP tool's plain upstream name when a model call (typically copied from pre-namespace history) does not match any canonical name. Settles pending tool calls when a client submits an externally handled result. It preserves mixed-batch semantics by settling backend siblings exactly once, accepts explicit frontend results without revalidating historical widget parameters, emits tool usage telemetry, anonymizes PII results, caps ordinary tool output at a 200,000-character prefix, and limits anonymous PII output to `MAX_ANONYMOUS_TOOL_RESULT_LENGTH` (30,000 characters, deliberately separate from the anonymizer's 60,000-character input cap) before redaction.
- Paid-call admission (fair-use quota, organization credit budget, user/team/API-key credit limits) comes from `InferenceAdmissionGuard` in the `quotas` module. `UsageHookFactory` records what each model call consumed through the usage module's `CollectUsageAsyncService`.
- **ThreadRunLock** — Lets one run at a time read and write a thread. `ExecuteRunUseCase` opens each run (reading the thread history in `prepareRun`) inside `holdWhile`. A run on a busy thread waits in arrival order for up to 15 seconds, enough for a stopped run to finish its in-flight tool call, and otherwise fails with `RunThreadBusyError` (409, `RUN_THREAD_BUSY`), which the chat shows as "please send again". The lock is released when the run's stream completes, fails or is closed. It is process-local, which is correct for the current single backend instance; AYC-1258 tracks shared coordination before scaling past one replica (AYC-1259).
- **MessageCleanupService** — Cleans up threads after a failed or interrupted run by rolling the incomplete turn back to the most recent assistant response without tool calls. It deletes only the messages the failed run itself persisted (its seeded input plus every message `PersistenceHookFactory` reports through `onMessagePersisted`), so a failure never removes another run's messages on the same thread (AYC-1259). Successful runs leave the thread in a valid state by design. Completed tool phases, tool-result continuations, `RunToolRepeatedlyFailingError`, and `RunMaxIterationsReachedError` skip cleanup because rollback would re-arm pending tool calls; a credit rejection before the first call for a newly seeded user message still removes that seed.
- **UnmaskedTermsService** — Applies a thread's manually unmasked PII dictionary entries to cloned inference-bound history before `RuntimeHistoryMaterializer` maps and trims it, so the model sees those terms in clear text while persisted messages remain tokenized.
- **xml-escape.ts** — Escapes XML-sensitive characters in workspace instructions, thread file names and advertised skill names/descriptions before capabilities insert them into the system prompt.

### Helpers

- **skill-slug.ts** — Located in `src/common/util/`. Pure functions for slugifying skill names (`slugify` with German transliteration), building prefixed slugs (`buildSkillSlug`), parsing slugs back to prefix + slug (`parseSkillSlug`), and building collision-safe slug→name maps (`buildSlugMap`). Defines `SYSTEM_PREFIX` (`system`) and `USER_PREFIX` (`user`) constants.

### Run profiles and capabilities

Every run is built from a **run profile**, chosen by the entry point through `ExecuteRunCommand.profile` — a typed union of the profile id plus any input only that profile needs (`RunProfileInput`; today only `{ id: 'chat' }`, passed by `ExecuteRunAndSetTitleUseCase` for the web chat). A profile (`application/run-profiles/`) is an id, a preamble, an optional closing line, an ordered list of capabilities and a completion policy (`done` for chat: the run ends when the model stops calling tools). Profiles are NestJS providers resolved by `RunProfileRegistry`; `ExecuteRunUseCase.prepareRun` resolves the command's profile, runs the quick-action skill activation, and hands the profile to `RunProfileAssembler`.

A **capability** (`application/run-capabilities/capabilities/`) owns one concern and checks its own conditions (model `canUseTools`, org settings, anonymous runs, configured providers). It contributes tools, prompt sections and runtime hooks. `RunCapabilityContextFactory` builds the shared `RunCapabilityContext` once per assembly: thread, model, user/org, anonymous flag, current time, the workspace context (only for workspace threads), deduplicated thread sources, and lazily loaded, memoized knowledge bases (thread, workspace and the user's active personal/shared knowledge bases merged by ID) and skill catalog. The skill catalog builds the unified slug map (`user__<slug>` for personal/shared skills, `workspace__<slug>` for workspace skills, `system__<slug>` for always-on templates; collisions and un-slugifiable names drop only that entry; a templates outage is logged and skipped) and maps editable personal and workspace skills from slug to immutable ID. Workspace skills are advertised as on-demand candidates; their instructions and resources load only on activation.

`RunProfileAssembler` runs the capabilities in profile order. Each one receives the tool names contributed before it, so `McpCapability`, which must stay last, drops MCP tools whose names built-ins already took. Capability order also sets the tool order and the section order within a prompt slot. `composeRunInstructions` renders the prompt as: profile preamble, then the fixed slots `FRAMING`, `TOOL_USAGE` (wrapped in `<tool_usage>` and followed by every tool's long description), `RESOURCES`, `POLICIES`, `CUSTOM_INSTRUCTIONS`, the profile closing, and `RUN_NOTES`. Stable content stays at the front so the provider's prompt cache keeps matching; the chat preamble and the date-only `<context>` from `DateTimeCapability` always come first. Capability hooks are created once per run with a handle whose `refresh` re-reads the thread, reassembles the profile and swaps the new tools (including the run's integration registry) and instructions into the running loop. Core hooks stay in `RunAssemblyService` and cannot be removed by a profile; profile hooks run after tool usage and before context budgeting.

The chat profile (`ChatRunProfile`) uses these capabilities, in order:

- **DateTimeCapability** — current date (no time of day) in `FRAMING`.
- **DataHandlingCapability** — privacy, document-processing and multi-tenant policies.
- **AnonymizationCapability** — the PII placeholder rules, only in anonymous runs.
- **BehaviorCapability** — behavior instructions (`FRAMING`), generic tool guidance (`TOOL_USAGE`), response guidelines with the source citation and URL reference markers described below, and platform information.
- **LegalReferencesCapability** — structured German federal and state legal-reference markers, only in assistant chat text.
- **CustomInstructionsCapability** — org-wide then user-level system prompts (`GetOrgSystemPromptUseCase`, `GetUserSystemPromptUseCase`).
- **CodeExecutionCapability** — `code_execution` with the thread's READY data sources only, matching the pending/failed listing in the prompt.
- **EmailCalendarCapability** — the email and calendar widgets.
- **FilesChartsMapCapability** — `create_file`, bar/line/pie charts and the GeoJSON map widget, plus the downloadable-file guidance.
- **ArtifactsCapability** — artifact tools via `ArtifactToolAssemblerService`, plus document, diagram and spreadsheet guidance.
- **SkillsCapability** — `create_skill`, `edit_skill` (when editable skills exist), `activate_skill` (when the catalog is not empty), the `<available_skills>` catalog, the `<already_activated_skill>` run note for quick actions, and the skill-activation hook: after a successful `activate_skill` call (whose handler already copied the skill's sources, MCP integrations and knowledge bases onto the thread) it refreshes the run so the new tools are offered on the next model call.
- **InternetCapability** — `website_content` and `internet_search`, only while the org chat settings allow internet access (`GetOrgChatSettingsUseCase`); web search additionally needs `internetSearch.isAvailable`.
- **MarketplaceCapability** — `marketplace_search` and the externally handled `install_marketplace_skill`, only when a marketplace is configured, so self-hosted installations never see them.
- **ImageGenerationCapability** — `generate_image`, only when an image-generation model is effectively available to the user (`GetPermittedImageGenerationModelUseCase`, team-override aware); conflicting team grants drop the tool with a warning, other failures propagate.
- **ThreadSourcesCapability** — `source_query`/`source_get_text` for thread text sources, and the listing of attached files by status (available text files, data sources for code execution, pending and failed uploads).
- **KnowledgeBasesCapability** — `knowledge_query`/`knowledge_get_text` and the `<available_knowledge_bases>` listing for the merged knowledge bases.
- **WorkspaceInstructionsCapability** — the workspace's always-on instructions from `BuildWorkspaceRunContextUseCase`.
- **McpCapability** — tools and resources of the thread's MCP integrations via `McpToolAssemblerService`.

Without `canUseTools` the chat offers no tools and omits the skill catalog and knowledge-base listing; the date, behavior, tool and artifact guidance, policies, thread files, workspace and custom instructions remain.

### Agent runtime adapters

The `application/agent-runtime/` directory adapts the package runtime to backend models, tools, persistence, usage, and SSE. `inference-message.mapper.ts` maps provider-agnostic inference messages back to backend assistant and tool-result messages, `run-event-stream.adapter.ts` folds runtime-owned, accumulated tool-call snapshots into the existing `RunStreamItem` stream while preserving the terminal `completed` or `aborted` outcome, and `masks-event.ts` defines the custom event name used for PII-mask updates. Streaming deltas only update the adapter's turn state; `SnapshotThrottle` sends the rebuilt message snapshot at most once per 75 ms, starting with the first delta, and a trailing timer sends a held snapshot when the provider pauses. The latest snapshot is always sent before any other item (assistant message, tool results, masks), before a run error surfaces, and when the stream ends or fails, so SSE events and bytes per turn grow with elapsed time rather than with tokens. Streaming tool-call snapshots carry raw `argumentsJson` with empty params; the runtime parses tool input once, when the call finalizes. The runtime's `tool_call_started` event adds a streaming placeholder call (name, empty arguments) to the turn while its snapshots are still held back, so a tool-only turn shows which tool is being prepared without making the call ineligible for retry; the call's revealed snapshot replaces its placeholder, and the first text or thinking of the turn drops any placeholder a rejected attempt left behind (AYC-1613).

Provider failures, empty responses, malformed tool calls, and the final tool-disabled fallback share the runtime's single per-turn retry budget; retries are prohibited after visible text, thinking, or tool snapshots, but not after `tool_call_started`. Rejected attempts stay internal, and exhausted malformed output becomes `MALFORMED_TOOL_CALL`, which `malformed-tool-call-error.helper.ts` maps to `InferenceMalformedToolCallError` (400, `malformedReason` plus tool names and provider/model in the metadata; a tool call cut off at the output token limit is labelled `token_limit_reached` even when its arguments did not parse), so no corrupted tool call is executed with guessed input and the failure stays out of AppSignal error incidents while the `Model call rejected` warn log keeps it observable (AYC-646, AYC-811, AYC-851, AYC-1012, AYC-1315).

Every durably persisted runtime message is passed through `AddMessageToThreadUseCase`, preserving `ThreadMessageAddedEvent` and activity semantics. An aborted outcome triggers orphan-message cleanup without becoming a client error frame; an aborted or failed first run aborts its title call (the signal reaches the provider request) and discards the title unless it was already saved.

`ExecuteRunUseCase` passes the transformed provider returned by `ResolveModelProviderUseCase` directly to the runtime with the runtime's documented retry defaults. The runtime owns each actual call's retry/recovery budget, request sanitation, cancellation, abortable backoff, and idle timeout. Every streaming provider disables its SDK's nested retry loop so these runtime-owned attempts remain the complete request budget (AYC-1013).

A run-local `RuntimeModelRegistry` is attached to `RunContext` and resolves each actual provider object to its backend `LanguageModel`; child-run creators retrieve it with `RuntimeModelRegistry.fromContext(...)` and register alternate providers before `runChild`.

The inherited `CreditGateHookFactory` checks persisted monetary usage immediately before every provider attempt, and `UsageHookFactory` critically persists each reported attempt before retry evaluation; a completed or consumed paid attempt without usage stops tools, retries, and later calls while preserving already-emitted text. Usage and model-call observability explicitly inherit into child runs; transcript persistence opts out so child-internal assistant turns and tool results cannot enter the parent thread or its pending persistence state.

The best-effort `ModelCallObservabilityHookFactory` records privacy-safe request diagnostics (tool names, per-schema and tool-set SHA-256 fingerprints, total schema bytes, and MCP integration identity without raw descriptions or parameter schemas) and emits one `InferenceCompletedEvent` with call identity, trigger, outcome, duration, and the actual backend model/provider for every call. Every rejected attempt (empty, missing answer, malformed, or invalid fallback) is logged as `Model call rejected` with its trigger, attempt position, output visibility, rejection and malformed reasons, tool names, content types, finish reason, and token counts, never arguments or content (AYC-1164).

The run-event adapter maps terminal portable provider facts and monetary-policy errors to the established backend error families and AppSignal grouping while preserving status, safe request ID, privacy-safe rejection code/type/parameter/reason diagnostics, retry timing, runtime idle stalls, and actionable rejection reasons carried in portable facts. Context-length and oversized-image errors do not depend on the in-process observability registry. Recovered calls never become consumer-facing error events (AYC-900, AYC-1012, AYC-1013).

Anonymous runs also preserve classified anonymization provider outages directly instead of collapsing connection, timeout, and server failures into `RUN_ANONYMIZATION_UNAVAILABLE`; post-detection and thread-mask failures retain stage-specific AppSignal grouping across the tool-runtime serialization boundary while clients still receive that same privacy-safe run error. Presidio detection retries one classified timeout before surfacing the final outage, deterministic oversized input remains the dedicated 422, and all failures stay fail-closed before message persistence or inference.

Runtime hooks collect usage for every actual call before retry evaluation, emit best-effort call observability next, persist only the terminal logical turn (including visible partial text/thinking without unexecuted tool calls), collect tool usage, and run the profile's capability hooks (for chat, the skill-activation refresh, which keeps any quick-action skill note). Grouped tool results are durably flushed by the final `afterToolCall` hook before their message event is exposed; a parent-thread foreign-key race aborts the run without emitting an unpersisted result, while unrelated persistence failures remain critical. Critical finalization failures are logged with hook attribution and override the host-facing error while retaining the runtime's original terminal status; if the last result flush fails, cleanup rolls the incomplete turn back to the previous completed assistant response.

`RunAssemblyService.assemble()` resolves the provider, materializes budgeted history, and wires hooks around a lazy runtime generator. Its input types live beside the service; `ExecuteRunUseCase` prepares input and streams the outcome. `RuntimeHistoryMaterializer` selects complete backend turns before mapping downloads image bytes, so excluded history incurs no image download.

History budgeting uses pure arithmetic in `common/token-counter`, `selectCompleteTurns`, and separate backend/runtime message-pricing adapters. The configured context window defaults to 200,000 tokens when unset. The budget leaves tokenizer headroom and subtracts instructions and tool definitions. The hook prices each actual call, including evolving skill instructions, tool results, and recovery prompts. Materialization and runtime use the provider's optional `tokenEstimator`; the long-chat warning uses an approximate shared estimate. Stored transcripts are never trimmed by this policy.

`RUN_RETRY_CONFIG` opts into context-length recovery within the runtime's shared retry budget. After rejection, the budget reduction is based on the actual rejected request and reported overflow, with fallback headroom when counts are absent. That reduction persists across the run. A latest-turn fallback must be smaller than the rejected request and is scoped to its logical turn; later tool turns cannot reuse stale rejection evidence. Exhaustion or an oversized latest turn becomes `RunContextBudgetExceededError`. It sets no `retryAfter` override: the Retry-After cap and jitter come from the runtime's `DEFAULT_RETRY_CONFIG.retryAfter` (AYC-1268). Direct inference does not retry; its caller owns retries (AYC-1050).

Model-call observability runs after request-mutating hooks and compares the final request estimate with provider-reported input usage, including cached input. Portable rejection facts determine consumer error families; additional safe diagnostics come from the stored cause when available. Provider packages classify their own errors, so the run path and OpenAI-compatible API do not parse provider wording.

Runtime iteration caps count complete model-and-tool iterations. A final tool phase remains persisted on `max_iterations` or `TOOL_REPEATEDLY_FAILING`, preventing cleanup from re-arming tool calls. The backend builds `@ayunis/agent-runtime` with the inference provider packages.

`BackendToolAdapter` is the single runtime-facing tool assembly boundary. Every assembled tool has optional `validateInput` and `execute` callbacks: charts and maps validate and return a successful display acknowledgement without invoking `ExecuteToolUseCase`; email, calendar, and create/edit skill widgets validate but omit `execute`, making their settled tool phase terminal; backend tools delegate exactly once, with the runtime's tool abort signal in the execution context, and expose their normal result; hybrid artifact tools delegate exactly once and replace successful raw output with the display acknowledgement. The generic runtime knows only that missing `execute` means external handling and contains no Ayunis tool names or UI concepts. Mixed phases settle every sibling before continuation or termination, and invalid external input remains model-actionable and retryable (AYC-675, AYC-704).

The runtime executes a turn's tool calls concurrently (at most eight at a time) while keeping hooks, `masks` events, results and the persisted tool-result message in call order. `requiresExclusiveExecution` in `runtime-tool-policy.ts` marks `activate_skill` and artifact updates (`update_document`, `edit_document`, `update_diagram`, `update_spreadsheet`) as exclusive, so they run apart from their siblings in call order. The adapter passes the run's cancel signal to tool handlers through `ToolExecutionContext.signal`; MCP tool calls and HTTP tools abort their request with it. A handler failure after cancellation is reported to the runtime as the cancellation, so the call ends as `aborted`. A call that completes despite the cancellation keeps its real result. Concurrent anonymous redactions on one thread are serialized by `thread-pii-masks` (AYC-1608). `ToolResultCollectorService`, which only settles calls left pending in a thread's last message, still processes them one at a time.

`RunSsePresenter` reports opened chat SSE responses under the AppSignal `streaming` namespace so run-length durations stay out of `web` latency alerts; pre-stream validation failures remain in `web`. It creates the run event source with an `AbortSignal`. Response close, socket error, and failed heartbeat writes abort it immediately; the optional signal is propagated through the run commands and passed to `@ayunis/agent-runtime`. Normal completion does not synthesize a cancellation.

Note: **SkillActivationService** (which handles copying skill sources, MCP integrations, and returning instructions to the thread) lives in the **skills module** (`src/domain/skills/application/services/skill-activation.service.ts`) and is consumed by both the runs module (`ExecuteRunUseCase`) and the tools module (`ActivateSkillToolHandler`).

Domain events are defined in `application/events/`: `RunExecutedEvent` retains the user/org-scoped activity signal; `RunTerminalEvent` emits exactly once with the `agent_runtime` path, terminal outcome, and end-to-end duration; `InferenceCompletedEvent` includes the explicitly supplied execution path alongside model, provider, streaming flag, duration, optional error, and optional runtime call identity/trigger/outcome; `RunToolCompletedEvent` captures low-cardinality success/error/aborted outcomes without identifiers; and `ToolUsedEvent` retains detailed tool and MCP integration identity for existing analytics/webhooks. `RunTelemetryService` wraps the selected generator so preparation failures, normal completion, aborts, max-iteration errors, and abandoned client streams share one terminal measurement. Each event class exposes a static `EVENT_NAME` string for type-safe listener registration. Usage persistence emits `RunUsageCollectionEvent` with an optional run execution path from the **usage** module; OpenAI-compatible and image-only usage omit it rather than inventing a third path value.

The module integrates with **threads** for conversation context, **workspaces** for workspace instructions, skill candidates and independently enabled knowledge bases (`BuildWorkspaceRunContextUseCase`), **messages** for creating and reading conversation history, **models** for inference routing, **tools** for executing tool calls during runs, **agents** for loading agent configurations, **skills** for on-demand skill activation and source/MCP injection, **mcp** for fetching integration metadata (`GetMcpIntegrationsByIdsUseCase`, `MarketplaceMcpIntegration`), **quotas** for paid-call admission, credit and fair-use enforcement (`InferenceAdmissionGuard`), **usage** for recording what each model call consumed (`CollectUsageAsyncService`), **chat-settings** for org-wide and user-level system prompt injection (`GetOrgSystemPromptUseCase`, `GetUserSystemPromptUseCase`), **artifacts** for discovering thread artifacts during tool assembly, and **letterheads** for listing org-scoped letterheads that can be attached to document tools.

The chat response guidelines define source citation markers as `{{source:<chunk UUID>|<plain-text label>}}`. It permits only canonical `chunkId` values returned by retrieval tools, excludes results marked non-citable and system-only sources, and confines markers to assistant chat text rather than tool arguments or generated artifacts.

Source citations are resolved lazily through `GET /threads/:threadId/source-chunks/:chunkId`. `GetThreadSourceCitationUseCase` first applies owner-scoped thread access, then permits only READY, non-system text sources in the user's current model-visible context. Direct thread uploads remain available through their assignment; skill-originated sources are reauthorized on every request; personal and shared knowledge-base documents remain available while directly attached or currently active and are reauthorized before exposure; workspace-owned knowledge-base documents are reauthorized through the current workspace runtime context. Missing, inaccessible, stale, unrelated, and system-only targets share the same 404 response.

Runtime completion recovery distinguishes output-limit exhaustion without an answer, provider refusal, and paused turns from unexplained empty responses. These terminal outcomes keep per-call usage accounting and map to classified `INFERENCE_FAILED` errors. Refused/paused tool calls are never executed and visible tool snapshots end invalid. Safe visible refusal/pause text is persisted without tool calls. Classified terminal completions preserve earlier completed tool phases, while first-turn no-output failures retain cleanup. Paused-turn continuation is not supported.

Both backend tool execution paths identify tool-result callers for the optional AYC-1434 reuse study. Fingerprints remain in bounded process memory; only global aggregate numeric metrics are exported, without tool names or tenant identity.

The chat response guidelines instruct web-page references in assistant chat to use `{{url:<url>}}` with complete HTTP(S) URLs supplied by users or tools, retaining the path, query and fragment. Generated artifacts and tool arguments use ordinary URLs.
