Release Notes
Ayunis' copy of the release notes written in Announcable, synced every hour and shown to every user as product updates

Release notes are written in Announcable. This module keeps a copy of them, sends them to the notifications inbox and serves them to every signed-in user as product updates, with a read state per user.

A `ReleaseNote` is one Announcable note, unique on its Announcable `id` (`announcableId`). It has a `headline` (Announcable's `title`, ≤ 200 characters), a markdown `body` (`text`, with `cta_href_override` appended as a markdown link labelled `cta_label_override` or "Mehr erfahren"; only http(s) links), optional `media` in the shape of notification media (the Loom URL of `media_link` if it passes the rules, otherwise the image of `imageSrc` stored in the **storage** module), `imageSourcePath` (the image URL without its expiring signature, set exactly when the media is a stored image) and `lastUpdateOn` (Announcable's `last_update_on`, compared verbatim). It also has `announced` (see below), `publishedOn` (Announcable's `date` of the note, `DD.MM.YYYY` in the feed, stored as a date; null when Announcable sends none) and `createdAt` (when it was first synced, which decides for whom it is unread). The date shown for a note, and the order of the list, is `publishedOn`, or the day of `createdAt` without one. Headline and body keep the notification limits, and media must pass the notification media rules (`notificationMediaViolation` from **notifications**, whose media shape and constants this module reuses): a note whose text breaks the rules is skipped (an edited one stays as stored), and a note whose media breaks them is stored without it; both are logged.

`SyncReleaseNotesUseCase` does nothing, not even a request, without the `releaseNotesEnabled` feature toggle: it needs `ANNOUNCABLE_ORG_ID` (`releaseNotes.announcableOrgId`) and routines on (`FEATURE_ROUTINES_ENABLED`), because release notes arrive in the routines' inbox and no notifications are created with routines off. Otherwise it reads the whole feed (`AnnouncableFeed`, implemented by `AnnouncableHttpFeed` over `GET https://release-notes.locaboo.de/api/release-notes/{orgId}?for=widget&page=N`; `ANNOUNCABLE_URL` points it at a stand-in for the e2e tests; the feed has 10 notes per page and repeats its last page past the end, so reading stops at the first page without a new note), then inserts notes it has not stored, updates those whose `lastUpdateOn` or `publishedOn` changed (so notes stored before their date was kept get it on the next sync) and deletes those no longer in the feed, in one transaction together with their notifications: each inserted note is `announced` and goes to every user there is right now, except those of archived orgs (`NotifyUsersOfReleaseNoteUseCase`, one statement per note however many users there are), an edited note is shown in the notifications already sent without sending it again or changing their read state (`UpdateReleaseNoteNotificationsUseCase`), and deleting a note deletes its notifications and read marks (foreign keys). Users who join later do not get earlier notes. When no note is stored yet (the first sync, also when routines are turned on later), the notes are recorded unannounced and without notifying anyone, because the feed is old news then. An edited note keeps its `announced` flag, its `createdAt` and its read marks, so an edit never makes it unread again. A feed without notes while notes are stored counts as a failed read (`ANNOUNCABLE_FEED_INVALID`) and changes nothing, so an outage on Announcable's side cannot delete every release-note notification and read mark. Downloads and uploads happen before that transaction and the image cleanup after it, so no database connection is held across a request. A feed that cannot be read completely, or an image that cannot be downloaded right now (connection, timeout, server error), fails the sync before anything is written; the next sync tries again. Redirects are not followed. An image Announcable refuses (client error or redirect), one from another host, over 10 MB or of an unsupported type (sniffed from its bytes) is left out.

Images (`ReleaseNoteMediaService`) are downloaded only when their path without the signature changes, and stored with `UploadSystemObjectUseCase` under `release-notes/<announcableId>/<hash of the path><ext>`, outside every org-scoped layout, so the org purge and the orphan sweep leave them alone. The stored note owns its image and its notifications only reference it, so images keep loading after the signed URL has expired: after each sync every object under `release-notes/` that no stored note uses is deleted, which removes replaced images, those of deleted notes, and any a failed sync left behind.

`ReleaseNoteSyncConsumer` runs the sync once an hour for all replicas together: a BullMQ job scheduler on its own `release-note-sync` queue (like the routine sweep), so it never waits behind document ingestion. Without release notes on (no Announcable org ID, or routines off) the scheduler is not registered and the worker does not start. The queue is listed in the super-admin queue inspection.

## Reading

A note is **unread** for a user when it is `announced`, was created after the user (`release_notes.createdAt > users.createdAt`, so nobody gets the notes from before they joined) and the user has no row in `release_note_reads` (`userId`, `releaseNoteId`, unique together; both FK ON DELETE CASCADE). Every signed-in user may read every note: notes are the same for all orgs, only the read state is per user.

`ReleaseNotesController` (`/release-notes`) is behind the `releaseNotesEnabled` feature flag (disabled → 404).

| Method | Path                          | Use case                                                                                                                         |
| ------ | ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| GET    | `/release-notes`              | `FindMyReleaseNotesUseCase` — the newest 100 notes, newest first, each with `unread` for the current user; not paged             |
| GET    | `/release-notes/unread-count` | `CountUnreadReleaseNotesUseCase` — for the bell's dot; counts within the same newest 100 the list shows                          |
| GET    | `/release-notes/:id`          | `FindReleaseNoteUseCase` — 404 `RELEASE_NOTE_NOT_FOUND`                                                                          |
| GET    | `/release-notes/:id/image`    | `DownloadReleaseNoteImageUseCase` — streams the stored image with `nosniff`; without an image 404 `RELEASE_NOTE_IMAGE_NOT_FOUND` |
| POST   | `/release-notes/:id/read`     | `MarkReleaseNoteReadUseCase` — one `INSERT … SELECT … ON CONFLICT DO NOTHING`, so a second read or a deleted note writes nothing |

The read state is independent of the read state of the note's notifications until release notes leave the inbox.
