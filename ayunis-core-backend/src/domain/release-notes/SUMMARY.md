Release Notes
Ayunis' copy of the release notes written in Announcable, synced every hour

Release notes are written in Announcable. This module keeps a copy of them and sends them to the notifications inbox; it has no endpoints of its own.

A `ReleaseNote` is one Announcable note, unique on its Announcable `id` (`announcableId`). It has a `headline` (Announcable's `title`, ≤ 200 characters), a markdown `body` (`text`, with `cta_href_override` appended as a markdown link labelled `cta_label_override` or "Mehr erfahren"; only http(s) links), optional `media` in the shape of notification media (the Loom URL of `media_link` if it passes the rules, otherwise the image of `imageSrc` stored in the **storage** module), `imageSourcePath` (the image URL without its expiring signature, set exactly when the media is a stored image) and `lastUpdateOn` (Announcable's `last_update_on`, compared verbatim). Headline and body must fit a notification, and media must pass the notification media rules (`notificationMediaViolation` from **notifications**), because notifications copy them without `CreateNotificationUseCase`: a note whose text breaks the rules is skipped (an edited one stays as stored), and a note whose media breaks them is stored without it; both are logged.

`SyncReleaseNotesUseCase` does nothing, not even a request, without the `releaseNotesEnabled` feature toggle: it needs `ANNOUNCABLE_ORG_ID` (`releaseNotes.announcableOrgId`) and routines on (`FEATURE_ROUTINES_ENABLED`), because release notes arrive in the routines' inbox and no notifications are created with routines off. Otherwise it reads the whole feed (`AnnouncableFeed`, implemented by `AnnouncableHttpFeed` over `GET https://release-notes.locaboo.de/api/release-notes/{orgId}?for=widget&page=N`; `ANNOUNCABLE_URL` points it at a stand-in for the e2e tests; the feed has 10 notes per page and repeats its last page past the end, so reading stops at the first page without a new note), then inserts notes it has not stored, updates those whose `lastUpdateOn` changed and deletes those no longer in the feed, in one transaction together with their notifications: each inserted note goes to every user there is right now, except those of archived orgs (`NotifyUsersOfReleaseNoteUseCase`, one statement per note however many users there are), an edited note is shown in the notifications already sent without sending it again or changing their read state (`UpdateReleaseNoteNotificationsUseCase`), and deleting a note deletes its notifications (foreign key). Users who join later do not get earlier notes. When no note is stored yet (the first sync, also when routines are turned on later), the notes are recorded without notifying anyone, so nobody gets the old ones. A feed without notes while notes are stored counts as a failed read (`ANNOUNCABLE_FEED_INVALID`) and changes nothing, so an outage on Announcable's side cannot delete every release-note notification. Downloads and uploads happen before that transaction and the image cleanup after it, so no database connection is held across a request. A feed that cannot be read completely, or an image that cannot be downloaded right now (connection, timeout, server error), fails the sync before anything is written; the next sync tries again. Redirects are not followed. An image Announcable refuses (client error or redirect), one from another host, over 10 MB or of an unsupported type (sniffed from its bytes) is left out.

Images (`ReleaseNoteMediaService`) are downloaded only when their path without the signature changes, and stored with `UploadSystemObjectUseCase` under `release-notes/<announcableId>/<hash of the path><ext>`, outside every org-scoped layout, so the org purge and the orphan sweep leave them alone. The stored note owns its image and its notifications only reference it, so images keep loading after the signed URL has expired: after each sync every object under `release-notes/` that no stored note uses is deleted, which removes replaced images, those of deleted notes, and any a failed sync left behind.

`ReleaseNoteSyncConsumer` runs the sync once an hour for all replicas together: a BullMQ job scheduler on its own `release-note-sync` queue (like the routine sweep), so it never waits behind document ingestion. Without release notes on (no Announcable org ID, or routines off) the scheduler is not registered and the worker does not start. The queue is listed in the super-admin queue inspection.
