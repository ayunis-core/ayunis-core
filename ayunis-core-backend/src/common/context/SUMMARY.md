Request Context
Provide request-scoped user identity via continuation-local storage service.

The context module wraps `nestjs-cls` to expose a `ContextService` that stores and retrieves the authenticated principal's identity (`userId` or `apiKeyId`, plus `orgId`, `systemRole`, and `role`) throughout a request lifecycle. It is globally available and used by all use cases to access authentication context without parameter passing.

The context module is a thin global wrapper around the `nestjs-cls` `ClsService`, typed with `MyClsStore` interface containing `userId`, `apiKeyId`, `orgId`, `systemRole`, and `role` fields. The `ContextModule` is decorated `@Global()` and provides `ContextService` by aliasing it to `ClsService` via `useExisting`. The authentication `UserContextInterceptor` populates the store early in the request pipeline after the relevant Passport strategy has resolved the principal: a user-backed request (JWT or local) sets `userId`, `orgId`, `role`, and `systemRole`; an API-key-backed request sets `apiKeyId` and `orgId`. Use cases then read the authenticated identity from the injected `ContextService` rather than passing auth context through controller parameters, commands, or queries. Required reads go through the accessors described below, not through a hand-rolled `get(...)` plus `if (!x) throw` pair; the raw `get('userId' | 'apiKeyId' | 'orgId')` calls remain for the flows where a missing value is a supported state. The store also carries `systemRole` for super-admin checks and `role` for organization-level authorization decisions on user-backed requests.

Most operations do not need a missing-context branch of their own. `required-context.ts` exports two fail-fast readers that take the `ContextService` as an argument and throw `UnauthorizedAccessError` when the context is incomplete: `getRequiredUserContext(context)` returns `{ userId, orgId }` for operations that require an authenticated human user, and `getRequiredOrgId(context)` returns the `orgId` alone for operations that also accept API-key principals (those carry `orgId` and `apiKeyId` but intentionally no `userId`, so the user helper would reject them). They are free functions rather than `ContextService` methods for the same reason `OrgContextRunner` is a separate injectable: the injected `ContextService` is a `useExisting` alias of `ClsService`, so subclass methods would be undefined at runtime. Flows where missing context is a supported state — background jobs, optional personalization — keep using the plain optional `get(...)`.

The module also provides `OrgContextRunner`, a small standalone service for entry points that run *without* an authenticated request (crons, event listeners, queue consumers): `runForOrg(orgId, fn)` executes `fn` inside a fresh context scoped to the given organization and discards it afterwards, so downstream use cases can keep reading `orgId` from the context as usual, and `runForUser(userId, orgId, fn)` does the same while acting as a specific user, for listeners that create resources on behalf of someone who is not the request's principal. It is deliberately a separate injectable rather than a method on `ContextService`, because `ContextService` is only a `useExisting` alias of `ClsService` — methods added to the subclass would not exist on the runtime instance. Consumed by `iam/budget-alerts` (`BudgetAlertEvaluator`, the single evaluation entrypoint that both the token-consumption listener and the daily sweep cron delegate to) and by `domain/workspaces` (`WorkspaceTutorialUserCreatedListener`, which provisions the tutorial as the newly created user).
