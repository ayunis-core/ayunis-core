Database Layer
TypeORM datasource, migrations, fixtures, and seed scripts for PostgreSQL.

The db directory manages the PostgreSQL database lifecycle. It contains the TypeORM `DataSource` initialization (with pgvector support), sequential schema and data migrations, a minimal development fixture, and seed scripts that directly use TypeORM repositories to populate test data outside of NestJS dependency injection.

The `datasource.ts` file creates and exports a standalone TypeORM `DataSource` used by both the application and migration CLI. It applies a hack to register `vector` as a supported column type for pgvector compatibility. The `migrations/` directory contains chronologically ordered migration files covering the full schema evolution: initial tables, subscriptions, models, permitted providers, legal acceptances, agents, threads, sources, RAG vectors, MCP integrations, shares, skills, teams, usage tracking, multi-provider support, document letterhead support, and versioned data transformations. The custom MCP credential migration converts legacy bearer and custom-header ciphertext into organization configuration values without decrypting it, normalizes the legacy auth row, and fails transactionally on unsupported legacy data; its reversible transformation helpers live in `migration-utils/`. The `fixtures/` directory holds `minimal.fixture.ts` defining a canonical development dataset (a seat-based Demo Org and a usage-based Usage Org with admin users, language models across the Bedrock, Anthropic, Azure, OpenAI, Mistral, and Gemini providers, a Mistral embedding model, an Azure image-generation model, active subscriptions with permitted models, and three demo workspaces for the Demo Org). It also carries the academy dataset: one quiz-enabled chapter with a module and three questions (platform-wide content, so a certificate can actually be earned locally), the academy add-on on the Usage Org only — Demo Org stays add-on-free so both the enabled and the "org cannot take the certificate" paths have a login — and per-member completion offsets expressed as `completedDaysAgo` rather than absolute dates, so the same fixture keeps producing valid / expiring-soon / expired members however long after it was written. The `scripts/seed-minimal/` directory holds the standalone minimal seed, split into focused modules: `seed-manager.ts` is both the CLI entry point and the orchestrator (the `SeedManager` class), `seed-types.ts` holds shared types, and `seed-state.ts` exposes a `SeedState` context that wraps `minimal.fixture.ts` and provides accessors (e.g. `getOrg`/`getAdmin`) shared across seeders. `seeders/` contains one idempotent seeder per concern, all extending `BaseSeeder` (which provides the shared `repo()` and `findOrCreate()` helpers): global seeders (`ModelSeeder`, `PlatformConfigSeeder`, `AcademyContentSeeder`) run once, then per-org seeders (`OrgUserSeeder`, `BillingSeeder`, `UsageSeeder`, `CreditLimitSeeder`, `AcademyAccessSeeder`, `WorkspaceSeeder`) run for each org in the fixture. `AcademyAccessSeeder` runs after `OrgUserSeeder` because its per-chapter progress rows need both the org's users and the chapters `AcademyContentSeeder` created, which it reads from `SeedState` via `getAcademyChapters()`. `WorkspaceSeeder` seeds the Demo Org's demo workspaces ("Projekte", AYC-700) for the org admin — invisible until `FEATURE_WORKSPACES_ENABLED` is on — and gives each `pinned` fixture a favorites row (appended after the admin's existing favorites, in fixture order), since sidebar pin state lives in the favorites module and direct inserts skip the auto-favorite that `CreateWorkspaceUseCase` performs in the app; chats are deliberately not seeded. Seeding is sequential — global seeders first, then each org's seeders in order. It initializes the datasource directly and uses raw TypeORM repositories (bypassing NestJS DI). The seed supports a `--clean` flag to truncate all tables before seeding. Shared `scripts/utils/` helpers provide a `SeedRunner` (initialization, password hashing, production-environment guards, `truncateAll`) and logging (`log`/`logLine`). The usage-based "Usage Org" is additionally enriched with extra users, teams, overlapping memberships, and per-user usage (so per-user and per-team credit limits can be exercised locally); that logic lives inside `usage-seeder.ts` (with a module-private `makeUsageRow` row builder), not a standalone module, and reads from the same `minimal.fixture.ts`.
